## 0. Короткий ответ

1. **Стартовать с `vehicle-reid-0001`, а не с ImageNet.** Веса достаются из ONNX прямым
   сопоставлением имён параметров (проверено лично: внутри 559 тензоров с именами
   torch state_dict) — это те самые веса, что уже дают 0,657 на ваших данных.
2. **Главная поправка к постановке задачи: «только кросс-камерные пары» — наполовину
   вредный рецепт.** Кросс-камерным должен быть **позитив**. Негатив должен быть,
   наоборот, **из той же камеры**. Замер: ограничение сложнейшего негатива чужими
   камерами даёт **−7,7 и −9,4 mAP**, ограничение своей камерой — **+24,6 и +9,8**
   (MCNL, AAAI'20, Табл. 3 ✔).
3. **Проверьте конфиг провалившегося прогона на Random Erasing.** Снятие REA с готового
   рецепта в кросс-доменном режиме даёт **+10,7 mAP** (BoT, Табл. 3 ✔). Ваш симптом —
   «внутри камеры 0,976, между камерами 0,379» — ровно то, что REA производит.
4. **Дообучение делать трёхступенчатым (LP → частичная разморозка → стоп), а не
   «30 эпох всего подряд».** Полное дообучение теряет **−7 % OOD** против линейного
   пробинга, LP-FT даёт **+10 % OOD** (arXiv:2202.10054).
5. **Чужие данные брать нельзя** — ни один публичный vehicle-re-id датасет не чист
   коммерчески, и наивное смешивание в любом случае измеряется как **−3,8 mAP**
   (arXiv:2004.10547, Табл. 2).
6. **Лучшее применение ваших `camera_id` — не в лоссе, а в пост-обработке**: отдельная
   camera-re-id сеть, её схожесть вычитается из матрицы расстояний. **+3,8 mAP / +5,0 R1**
   (VOC-ReID, CVPRW'20, Табл. 3 ✔), `camera_id` на инференсе не нужен.
7. **Честная оценка: 0,73–0,77 mAP с переранжированием.** 0,80 — верхняя граница,
   достижимая только если камерный штраф перенесётся в полную силу. Вероятность
   оказаться **ниже** нынешних 0,694 — реальная; поэтому план содержит стоп-правило.

## 1. Главная поправка: «кросс-камерные триплеты» — это не то, что вы думаете

Бриф формулирует приём как «формирование батчей и триплетов **только кросс-камерными
парами**». Единственная работа, которая мерила это напрямую, показывает, что половина
этого рецепта не нейтральна, а активно вредна.

**Single Camera Training / MCNL, AAAI 2020, [arXiv:1909.10848](https://arxiv.org/abs/1909.10848), Табл. 3** ✔
(ResNet-50, батч-хард триплет, три варианта выбора сложнейшего негатива):

| вариант | Duke-SCT R1 / mAP | Market-SCT R1 / mAP |
|---|---:|---:|
| Triplet (негатив откуда угодно) | 21,2 / 11,3 | 39,7 / 18,2 |
| Triplet-**other** (негатив только из **чужих** камер) | 9,9 / **3,6** *(−7,7)* | 25,2 / **8,8** *(−9,4)* |
| Triplet-**same** (негатив только из **своей** камеры) | 54,6 / **35,9** *(+24,6)* | 51,3 / **28,0** *(+9,8)* |
| MCNL (d⁺ < d⁻ᵈᵣᵤᴦᴀя < d⁻ᶜʙᴏя) | 66,4 / 45,3 | 66,2 / 40,6 |

Механизм прозрачен и ровно ваш. Если сложнейший негатив всегда из другой камеры, сеть
разделяет его **по камере** — это дешевле, чем по машине. Если негатив из своей камеры,
фон у якоря и негатива одинаковый, и камерный признак бесполезен: разделить их можно
только по автомобилю.

Та же статья меряет «выученность камеры» напрямую — pseudo-F (Calinski–Harabasz)
разделимости признаков по камерам, Рис. 3: Triplet **8,433** → Triplet-other **16,683**
→ Triplet-same **0,404** → MCNL **0,255**. У нулевой гипотезы (признаки не зависят от
камеры) матожидание CH = 1,0 (проверено симуляцией: n=1110, d=512, k=96 → 1,000 ± 0,006).
То есть обычный триплет даёт в 8,4 раза больше камерной структуры, чем случайность,
а исправленный — **ниже случайности**.

### Оговорка, без которой число будет обманом

Duke-SCT и Market-SCT — сеттинг **Single Camera Training**: в Табл. 2 той же статьи
прямо стоит «With cross-camera persons? **False**», каждая личность видна ровно одной
камерой, и обучающих кадров там 5 993 / 3 561. **У вас не так**: у каждой машины ≥2
камеры. Значит **+24,6 mAP к вам не переносится** — это величина для случая, когда
кросс-камерных позитивов нет вовсе. Переносится знак и механизм: направление выбора
негатива. Реалистичный ожидаемый эффект у вас — единицы пунктов, не десятки.

Косвенное подтверждение на **транспорте**: выброс одно-камерных кластеров при обучении
поднимает **VeRi-776 с 38,2 до 45,3 mAP** (ICLR 2025, [arXiv:2502.10195](https://arxiv.org/abs/2502.10195), Табл. 6).

### Что это значит для сэмплера

Нужен батч, в котором одновременно есть (а) **кросс-камерные позитивы** и (б)
**внутрикамерные негативы**. Обычный P×K-сэмплер не гарантирует ни того, ни другого.
Конструкция (у MCNL она именно такая: «randomly select 8 cameras, and sample 4 identities
for each selected camera» ✔):

```
C камер → для каждой камеры P' машин, снятых этой камерой
       → для каждой машины K кадров: ≥1 из этой камеры, ≥1 из любой другой
батч = C · P' · K
```

При C=4, P'=4, K=4 → батч 64. Тогда у каждого якоря в батче есть 3 внутрикамерных
негатива (другие машины с той же камеры) и ≥1 кросс-камерный позитив. Ваши данные это
позволяют: у 100 % машин ≥2 камеры (`context-split.md`, §1).

## 2. С каких весов стартовать

### 2.1. Почему ImageNet не мог сработать — и это было предсказуемо

**LUPerson, CVPR 2021, [arXiv:2012.03753](https://arxiv.org/abs/2012.03753), Табл. 6a.**
Единственная опубликованная кривая «сколько обучающих данных → какое качество» рядом
с вашим масштабом (MGN, Market1501):

| доля обучающей выборки | ImageNet-init mAP | доменный претрейн mAP | Δ |
|---|---:|---:|---:|
| **10 % (75 ид. / 1 170 кадров)** | **53,1** | **64,6** | **+11,5** |
| 30 % | 75,2 | 81,9 | +6,7 |
| 50 % | 81,5 | 85,8 | +4,3 |
| 90 % | 86,9 | 90,5 | +3,6 |

Выигрыш доменного старта максимален именно на малых выборках и монотонно тает с ростом
данных. У вас 1 171 ид. / 7 248 кадров — ближе к верхней строке, чем к нижней.

**VehicleNet, [arXiv:2004.06305](https://arxiv.org/abs/2004.06305), Табл. II.** Цель
CityFlow (26 803 кадра): ImageNet-init **37,65 mAP** → +VeRi-776 43,47 → +CompCars 48,71
→ +VehicleNet (434k кадров / 31,8k ид.) **57,35 (+19,70)**.

То есть ваши 0,433 — не неудача реализации, а ожидаемый результат для ImageNet-инициализации
на такой выборке.

### 2.2. Третий контроль: 0,657 — это норма, а не «повезло»

Zero-shot перенос между vehicle-датасетами меряется так: VERI-Wild → VeRi-776 =
**63,1–63,9 mAP** ([arXiv:2606.01981](https://arxiv.org/abs/2606.01981), Табл. II),
DINOv3-ConvNeXt после дообучения на VERI-Wild → VeRi-776 = **66,02**
([arXiv:2607.22068](https://arxiv.org/abs/2607.22068)). Ваши **0,6566** у готовых весов
лежат ровно в этом коридоре. А **0,4332** после дообучения — на 22 пункта ниже уровня
«никак не адаптированной чужой модели». Это подтверждает диагноз: дообучение не просто
не помогло, оно активно испортило переносимый признак.

### 2.3. Рекомендуемый старт — веса `vehicle-reid-0001`, вынутые из ONNX

**Это выполнимо, я проверил лично.** Скачал `osnet_ain_x1_0_vehicle_reid.onnx`
(8 836 743 Б, sha256 `4aaad3e5db648618b0df3d2ff21c61323985ff9e50194c3d2edd4fb87c92d91f`)
и просканировал байты: внутри **559 тензоров с именами обычного torch `state_dict`** —
`conv1.conv.weight`, `conv2.0.IN.weight`, `conv2.0.conv2.0.layers.0.bn.running_mean`,
`pool2.0.conv.weight`, `pool3.0.bn.weight`, плюс строка `pytorch` в поле producer.
Это не «граф, который надо реверсить конвертером», а экспорт torch-модели с сохранёнными
именами параметров.

Архитектура-донор существует и открыта: **[sovrasov/deep-person-reid, ветка `vehicle_reid`](https://github.com/sovrasov/deep-person-reid/tree/vehicle_reid)**
(MIT, HTTP 200 ✔) — там есть и `input_IN`, и `pool2`/`pool3`, которые видны в ONNX.
Процедура: собрать `nn.Module` из этой ветки, прочитать инициализаторы ONNX, разложить
по именам в `state_dict`, загрузить.

Почему именно этот старт:

| довод | число |
|---|---|
| уже измерен **на ваших данных** | mAP 0,6566 / R1 0,6310 |
| заявленное качество на VeRi-776 | 85,15 mAP / 96,31 R1 (OMZ README) |
| вход совпадает с сервисом 1:1 | 208×208, менять препроцессинг не надо |
| размер | 2 189 686 параметров, 8,4 МБ |
| лицензия | MIT — единственный из кандидатов, чистый для коммерции |
| в `input_IN` уже стоит instance-norm | тот самый механизм против смены стиля камеры |

**Обязательная приёмка перед обучением:** torch-модель, собранная из ONNX, должна
воспроизвести **0,6566 mAP** вашим контуром и дать косинус ≥ 0,9999 с выходом ONNX.
У вас эта машинерия уже написана — в прошлой сессии вы так сверяли 62 боевых кропа.
Если число не сошлось — сборка неверна, дальше идти нельзя.

### 3.1. Что именно применимо, когда `camera_id` есть только в обучении

**Применимо без оговорок** (метка нужна только на этапе обучения — для сэмплера, для
выбора негатива, для веса лосса):
сэмплер по камерам, MCNL / выбор негатива из своей камеры, кросс-камерный позитив,
GRL-голова, MixStyle, IBN, SNR.

**Неприменимо** (метка нужна на инференсе — у вас её нет):
**CBN** (цитата §4.1: «collect several unlabeled images and calculate the camera-related
statistics **per testing camera**»), **SIE** (в коде TransReID вызов —
`model(img, cam_label=camids, view_label=target_view)`), camera-specific feature
normalization, camera verification.

**Отдельный класс — пост-обработка, которая использует камеру, не зная её на входе:**
см. §3.5. Это самое ценное, что можно выжать из ваших 96 меток.

### 3.2. Стоимость отсутствия `camera_id` на инференсе — числом

AI City 2021, Табл. 4: пост-обработка с камерной информацией поднимает **66,8 → 76,0 mAP**.
То есть примерно **9,2 пункта mAP** вам недоступны в принципе. Это не повод унывать, а
повод правильно ставить цель: ваши 0,8 — это уровень, который решения AI City достигают
**с** камерной пост-обработкой на тесте.

### 3.3. Состязательная голова (GRL): да, но не в первом прогоне

Приросты есть: +0,9 mAP (Market) и +4,3 (MSMT17) у CCAFL, Табл. IV; +2,9…+4,4 у CANU,
Табл. IV. Но там же задокументированы три способа всё сломать:

- CANU, Табл. III: вес состязательного лосса µ=1,8 роняет **57,0 → 2,9 mAP**;
- CCAFL, Рис. 8: запуск adversarial без разогрева даёт ~47,2 против **54,6 вообще
  без adversarial**;
- ACAN, Рис. 10: на Duke GRL «almost assigns all images into one camera» — вырождается
  тем сильнее, чем больше камер. У вас 96.

Условия, при которых это стоит пробовать: **только после того, как заработал сэмплер**,
разогрев ≥60 % эпох без состязательного лосса, λ ≤ 0,1, и обязательный откат, если
честный mAP падает.

**Критично про измерение.** Elazar & Goldberg (EMNLP 2018) показали: состязательная
голова во время обучения показывала **49,0 %** при случайном уровне 50 %, а post-hoc
проба на **тех же самых** замороженных признаках доставала **56,0 %** (пять голов —
59,7 %). Вывод авторов дословно: «do not rely on adversarial training to achieve
invariant representation». Значит **лосс состязательной головы не является измерением
камерной инвариантности** — мерить надо отдельной пробой (§8, проверка F3).

### 3.4. IBN: помогает тем сильнее, чем больше камер — но это не бесплатно

fast-reid MODEL_ZOO: R50 → R50-ibn даёт +0,5…+1,5 mAP на Market (6 камер), +0,9…+2,6
на Duke (8 камер), **+2,2…+4,2 на MSMT17 (15 камер)**. Зависимость от числа камер
монотонная, а у вас их 96.

Но противоположных замеров четыре, и все крупные: чистый IN роняет supervised-качество
на **−21,8 mAP**, «BN+IN пополам» — на −14,0 (MetaBIN, Табл. 5); IBN на Duke — −16,0
(IICS, Табл. 2) и −9,6 (CBN, Табл. 6). Вывод: **IBN обязателен к A/B, а не к внедрению
по умолчанию.**

По памяти IBN бесплатен: расчёт даёт для R50-IBN-a @208 батч 32 те же **3 134 МБ**,
что и для обычного R50 (`torch.split` и `.contiguous()` не сохраняют вход, живут те же
две карты активаций). Для трека OSNet-AIN вопрос не стоит — instance-norm там уже есть
в `input_IN`, это и есть «A» в названии AIN.

### 3.5. Самое выгодное применение ваших `camera_id` — камерный штраф в пост-обработке

**VOC-ReID, CVPRW 2020, Табл. 3** ✔ (CityFlow, валидация):

| конфигурация | mAP | Rank-1 |
|---|---:|---:|
| RECT-Net (базовая) | 44,4 | 65,3 |
| + штраф по ориентации | 47,0 | 70,5 |
| **+ штраф по камере** | **50,8** | **75,5** |

Камерный штраф поверх ориентационного — **+3,8 mAP / +5,0 R1**; весь механизм — +6,4 mAP.

Как это работает и почему подходит именно вам: обучается **отдельная сеть camera-re-id**
(та же архитектура, но классы = 96 камер), она даёт камерный эмбеддинг. На инференсе
схожесть камерных эмбеддингов вычитается из схожести машинных. `camera_id` на входе
**не нужен** — сеть предсказывает камеру сама. Метки нужны только при обучении этой
второй сети, и они у вас есть, все 96.

Это ровно ваш случай: болезнь — ранжирование тянет вверх кадры со своей камеры; лекарство —
вычесть камерную компоненту из ранга. И, как и переранжирование, это постпроцессинг
матрицы расстояний, а не изменение модели.

**Честная цена, которую надо назвать сразу.** Это вторая модель и второй проход по
изображению. Если заказчик меряет время «кроп → эмбеддинг» (а по `context-vesa.md` §7
он меряет именно это), вторая сеть удваивает замеряемое время. Смягчение: камерной сетью
может быть `osnet_x0_25` (~0,2 M параметров) — тогда прибавка к латентности единицы
процентов. Объединять обе головы на одном стволе **нельзя**: ствол тогда обязан кодировать
камеру, то есть ровно то, от чего мы избавляемся.

### 3.6. CamStyle — отвергнуто, и это считается

Прирост есть: +2,85 mAP на Market, +1,65 на Duke. Цена — C(N,2) моделей CycleGAN.
Авторская цитата: «C(6,2)=15 and C(8,2)=28». Для ваших **96 камер это 4 560 CycleGAN**,
а раздутая обучающая выборка — 95 подделок на кадр = **688 560 изображений**. На вашей
карте это годы. И даже если бы железо было — у вас в среднем ~75 кадров на камеру,
CycleGAN на 75 кадрах не обучится.

Плюс в самой статье задокументировано затухание эффекта с ростом числа камер:
2 камеры → +17,1 R1, 6 камер → **+0,7 R1**. При 96 камерах ожидаемый эффект — около нуля.

Отдельно: без прочих аугментаций CamStyle даёт всего **+0,76 mAP**, тогда как один
Random Erasing — +4,40 (Табл. 3). То есть он и в своей-то работе не главный приём.

### 3.7. Отрицательные результаты, которые надо знать до старта

- На **своём** домене с сильной моделью камерное дебиасирование уходит в минус:
  SOLIDER −0,1, TransReID −1,1, CAJ −1,5, PPLR-CAM −0,9 mAP
  ([2502.10195](https://arxiv.org/abs/2502.10195), Табл. 3a). Ваша валидация —
  свои камеры, так что часть приёмов может не дать ничего.
- Приросты **не складываются**. Та же работа, §5.4, прямым текстом: у метода с
  камеро-осведомлённым лоссом выигрыш от дебиасинга «relatively small… because it uses
  a camera-aware loss function». Складывать Δ из разных таблиц нельзя — после исправления
  сэмплера эффект от GRL будет заметно меньше табличного.
- Ориентир «дебиасинг сработал» из той же работы: превышение над случайным уровнем падает
  примерно **вдвое**, а не до нуля (камерный NMI 17,1 → 11,2 при нуле 6,4, mAP 22,5 → 30,0).

## 4. Аугментации: главная из них — та, которую надо убрать

### 4.1. Random Erasing, скорее всего, часть вашей болезни

**Bag of Tricks, [arXiv:1903.07071](https://arxiv.org/abs/1903.07071), Табл. 1 и 3** ✔
(один и тот же рецепт, слева свой домен, справа чужой):

| шаг рецепта | Market mAP (свой домен) | M→D mAP (чужой домен) |
|---|---:|---:|
| Baseline | 74,0 | 12,9 |
| +warmup | 75,2 | 14,1 |
| **+REA** | **79,3** *(+4,1)* | **10,2** *(−3,9)* |
| +label smoothing | 80,3 | 11,3 |
| +stride=1 | 81,7 | 11,8 |
| +BNNeck | 85,7 | 15,2 |
| +center loss | 85,9 | 15,0 |
| **−REA** (снять REA с готового рецепта) | — | **25,7** *(+10,7)* |

Rank-1 при этом идёт 27,5 → **41,4**. Авторская формулировка дословно: «REA **does harm**
to models in cross-domain ReID task… REA masking the regions of training images lets the
model learn **more knowledge in the training domain**».

Независимое подтверждение: MixStyle, Табл. 2 — добавление Random Erasing даёт **−5,0 mAP**
(M→D, ResNet-50), −4,3 (D→M), −5,4 (OSNet M→D).

Ваш симптом — качество внутри своей камеры 0,976 и провал между камерами 0,379 — это
буквально «модель выучила больше знаний о тренировочном домене». **Первое действие:
посмотреть конфиг провалившегося прогона.** Если REA там был — контрольный прогон без
него стоит ноль и может дать больше, чем весь остальной список.

> Оговорка о честности: я не могу проверить ваш конфиг — его нет в выданных материалах.
> Если REA не использовался, этот пункт снимается, но проверить надо первым делом, потому
> что цена проверки нулевая, а ставка — до 10 пунктов.

### 4.2. Подавление фона: вероятностное — да, жёсткое — нет

**[arXiv:1910.06613](https://arxiv.org/abs/1910.06613) «Background Segmentation for
Vehicle Re-Identification», Табл. 1 и 2** ✔ — это **vehicle** re-id, VeRi-776:

| режим | mAP | top-1 |
|---|---:|---:|
| baseline (исходные кадры) | 65,78 | 86,29 |
| **Seg** — все кадры с вырезанным фоном | **57,53** *(−8,25)* | 81,70 |
| Seg+Post | 64,79 | 86,89 |
| **BIR, k = 0,2** — сегментированные с вероятностью 0,2, остальные исходные | **70,74** *(+4,96)* | 90,46 |
| BIR, k = 0,5 | 69,65 | 89,27 |
| BIR, k = 0,9 | 67,22 | 87,72 |

Определение k (стр. 262 статьи, дословно): «All images has a probability of k (k ∈ [0,1])
to be selected to use their images with background segmentation. These segmentation images,
together with other 1−k ratio original images, are put into CNN to train».

Смысл: **вероятностная смесь работает, детерминированное удаление фона — хуже, чем ничего.**
Убрав фон у всех кадров, вы отнимаете у сети и полезный контекст (масштаб, ракурс, часть
контура), и ошибки сегментации попадают в каждый кадр.

Аналог на людях, **Tian et al., CVPR 2018** (насколько силён фон вообще):
обычная модель при подмене фона на тесте падает **87,2 → 64,0 top-1** (−23,2); модель,
обученная со случайными фонами, теряет **1,4**. Сеть, обученная **только на фоне** (объект
вырезан), даёт top-1 **25,9 %** — фон сам по себе опознаёт личность. Цена устойчивости:
−2…3 пункта на «родном» тесте. Онлайн-замена фона даёт **+3,9 top-1**, а заранее
сгенерированный набор — всего **+0,5**: подставлять фон надо каждую эпоху заново.

**Цена для вас.** Маски считаются один раз и кешируются: 7 248 кропов 208×208 — минуты
CPU-времени лёгким сегментатором. Это не блокер.

### 4.3. MixStyle — самый дешёвый приём в списке

### 6.1. Память — расчёт, а не догадка

Модель памяти: параметры + градиенты + два момента Adam + активации + рабочие буферы.
Калибровка расчёта: для R50 @208 батч 32 она даёт **3 134 МБ**, и это сходится с фактом,
что у вас такая конфигурация работает. Бюджет карты ~3 500 МБ (4 096 минус дисплей и
контекст CUDA). Полный вывод — `research/E-hardware.md`.

| конфигурация | оценка, МБ | вердикт |
|---|---:|---|
| R50 @208, батч 32, Adam | 3 134 | **влезает** (подтверждено фактом) |
| **R50-IBN-a @208, батч 32** | **3 134** | **влезает, IBN бесплатен по памяти** |
| OSNet-AIN @208, батч 32 | 3 908 | на грани / не влезает — мерить |
| OSNet-AIN @208, батч 24 | ~2 930 | влезает |
| R50 @256, батч 32 | 4 454 | нет |
| fast-reid R50-IBN @256, батч 64 (штатный конфиг) | 8 373 | нет |
| ViT-B/16 @224, батч 16 / 32 | 3 906 / 6 369 | нет |
| TransReID @256×128, батч 32 | 6 777 | нет |
| CLIP-ReID ViT-B, батч 32 | 4 498 | нет |
| DINOv2-L, батч **1** | 5 322 | нет (одни веса+градиенты+Adam = 4 644 МБ) |

Неочевидное: **OSNet, несмотря на 2,19 M параметров против 23,5 M у R50, требует
больше памяти при обучении** — у него много параллельных ветвей на высоком разрешении,
и почти весь расход это активации, а не веса.

### 6.2. Приёмы экономии — с числами

| приём | эффект | цена |
|---|---|---|
| `Adam(foreach=False)` | **−98,8 МБ** | ноль (документация: foreach «uses ~sizeof(params) more peak memory») |
| gradient checkpointing | активации 2 277 → **~850 МБ**, открывает батч 64 | **+25…30 % времени** ([arXiv:1604.06174](https://arxiv.org/abs/1604.06174): «48G → 7G … only 30 percent additional running time»); ловушка — BN обновляется дважды, лечится `momentum 0,1 → 0,05` |
| SGD вместо Adam | −2 состояния × размер модели | обычно нужен другой LR-режим |
| AMP (fp16) | память ~вдвое: 3 134 → ~2 200 МБ | **−17 % скорости** на Maxwell |
| gradient accumulation | **бесполезен** | триплет считается внутри микро-батча, накопление не увеличивает число триплетов |
| `channels_last` | **−** | замер fp32 без Tensor Cores: **×2,4 медленнее** |

**Про fp16 отдельно.** В таблице NVIDIA «Throughput of Native Arithmetic Instructions»
16-битная плавающая арифметика для compute capability **5.0 указана как N/A** — у GM107
нет соответствующих ALU. Замер на Tesla M60 (тот же Maxwell): fp32 79,0 мс → AMP 92,2 мс.
Вывод: **AMP на вашей карте — инструмент экономии памяти ценой 17 % скорости, а не
ускорения.** bf16 и TF32 отсутствуют.

### 6.3. Время: не узкое место

Ваш факт — 245–353 с/эпоху для R50 @208 батч 32. Отсюда:

| конфигурация | с/эпоху (оценка) | 30 эпох |
|---|---:|---|
| R50 @208, батч 32 | 245–353 | **2,0–2,9 ч** |
| R50-IBN-a @208, батч 32 | те же 245–353 | 2,0–2,9 ч |
| R50-IBN-a @208, батч 64 + checkpointing | 320–495 | 2,7–4,1 ч |
| OSNet-AIN @208, батч 24 | 168–241 | 1,4–2,0 ч |
| R50 @256, батч 32 | 361–520 | 3,0–4,3 ч |

**Полный цикл обучения влезает в один трёхчасовой прогон.** Это снимает вашу главную
операционную проблему: не нужно «трёхдневное обучение», которое узел дважды не пережил.
Планируйте прогонами по 2–4 часа, чекпоинт каждую эпоху, запуск через WMI (вы уже
установили, что он переживает разрыв ssh).

Поправка к ожиданиям: **OSNet меньше R50 в 11,7 раза по параметрам, но лишь в 2,8 раза
по FLOPs**, и он memory-bound (арифметическая интенсивность 3,8 MAC/байт против 22,7 у

1. **PR [pytorch#152069](https://github.com/pytorch/pytorch/pull/152069)** вырезал `5.0;6.0`

3. **torch 2.14.0 — последняя версия с sm_50.**
   [RFC #190385](https://github.com/pytorch/pytorch/issues/190385) ✔, заголовок

   Volta)», цитата: «Users on these GPUs should remain on **PyTorch 2.14 (CUDA 12.6) or
   earlier**».
4. Драйвер: **R580 — последняя ветка с поддержкой Maxwell**, обновлять нельзя.

**Практический вывод: ничего не обновлять.** У вас уже есть работающее окружение — это
ценность, которую легко потерять одной командой `pip install -U`. Перед любым прогоном
зафиксируйте `pip freeze` в файл. Если ставить заново — `torch==2.9.1+cu126`

### 6.5. Единственный приём, который покупает метрику, а не мегабайты

Gradient checkpointing открывает батч 64 (P×K = 16×4) вместо нынешних 32 (8×4).
**Bag of Tricks, Табл. 5** ✔:

| P × K | Market R1 / mAP | Duke R1 / mAP |
|---|---:|---:|
| 8 × 4 (ваш нынешний) | 92,9 / **80,0** | 84,7 / **69,4** |
| 8 × 8 | 93,9 / 82,0 | 85,8 / 71,5 |
| **16 × 4** | 93,8 / **83,7** *(+3,7)* | 86,6 / **73,0** *(+3,6)* |

**+3,7 mAP — в 2,8 раза больше вашего σ = 0,0134.** И для нашего сэмплера (§1) большой
батч нужен вдвойне: чтобы в нём одновременно уместились 4 камеры × 4 машины × 4 кадра.

### 7.6. Расписание — трёхступенчатое, с воротами

Основание: **LP-FT, [arXiv:2202.10054](https://arxiv.org/abs/2202.10054), Табл. 1–2** —
полное дообучение даёт in-domain 85,1 / **OOD 59,3**; линейный пробинг 82,9 / **66,2**;
**LP-FT 85,7 / 68,9**. Полное FT меняет признаки в 10–100 раз сильнее. Ваш провал —
буквально «−7 % OOD»: 0,886 на виденных идентичностях против 0,433 на невиданных.

| этап | что | эпох | LR | заморозка | ворота |
|---|---|---:|---|---|---|
| **0** | сборка весов из ONNX, приёмка | — | — | — | **mAP = 0,6566 ± 0,013**, иначе стоп |
| **1** | только BNNeck + классификатор (LP) | 5 | 3,5e-4 (Adam) | весь бэкбон | если mAP < 0,6566 − 0,027 → рецепт неверен, стоп |
| **2** | разморозить верхние блоки | 12–15 | бэкбон **0,1×**, голова 1× | нижние блоки заморожены, BN в них в `.eval()` | CH по камерам (§8, F2) не должен расти; иначе убить прогон |
| **3** | полная разморозка, очень низкий LR | 5–8, **только если этап 2 дал прирост** | 1e-5…3e-5 | нет | честный mAP ↑ **и** разрыв не ↑ |

Числа, стоящие за этим:
- заморозка первых двух слоёв на дообучении: **+1,4 mAP** ([arXiv:2004.10547](https://arxiv.org/abs/2004.10547), §4.4) — единственный re-id-замер по заморозке;
- fast-reid зашивает то же в конфиг: `FREEZE_LAYERS: [backbone]`, `FREEZE_ITERS: 1000`
  (для VeRi — 3000), причём в `hooks.py` замороженные модули переводятся в `.eval()`,
  то есть **BN тоже заморожен**;
- вторая стадия везде короче первой в 2–5 раз: VehicleNet 60 → 12 эпох, DMT 100 → 40;
- LR на второй стадии ×0,1 на бэкбон (DMT, дословно: «Reducing the learning rate is
  also necessary»); VehicleNet держит бэкбон на 0,1×LR, голову на 1×.

**Честное противоречие, которое надо назвать.** Surgical fine-tuning
([arXiv:2210.11466](https://arxiv.org/abs/2210.11466), Табл. 1) утверждает обратное:
при сдвиге на уровне входа (а смена камер — именно такой) тюнить надо **первые** слои,
а не последние; один правильный блок бьёт полное FT «by almost 3 %». Разрешение спора
у вас дешёвое: два прогона по 40 минут — «размораживаем верх» против «размораживаем
низ + `input_IN`». Смягчающее обстоятельство: у OSNet-AIN входной instance-norm уже
обучен именно на подавление стиля, так что нижние слои у вас в лучшем состоянии, чем
у типичной ImageNet-сети. Та же работа, Табл. 4: **постепенная разморозка проиграла**
полному FT (ранг 4,71 против 2,71) — не делайте gradual unfreezing по эпохам, делайте
фиксированные этапы.

## 8. Проверки, которые надо поставить ДО обучения

Все — на **нынешних** готовых весах OSNet, до единой эпохи. Они дают опорные значения,
без которых после обучения не с чем сравнивать. Суммарно ~3 часа.

| # | проверка | как | стоп-сигнал | цена |
|---|---|---|---|---|
| **F0** | знаменатель mAP | усредняется по 832 запросам с парой или по всем 1 110? | расхождение = **25 % относительных**, в 18 раз больше σ — важно зафиксировать до сравнений | 10 мин |
| **F1** | **камерный оракул** | заменить каждый эмбеддинг на **среднее его камеры**, прогнать тот же контур | mAP > **0,05** (пол случайности 0,0103) → протокол сам пропускает камеру | **5 мин** |
| **F2** | **pseudo-F (Calinski–Harabasz) по камерам** | `sklearn.calinski_harabasz_score(embeddings, camera_ids)` на сырых признаках, плюс перестановочный нуль | нулевое матожидание **ровно 1,0**. Значение для OSNet = опора. Рост относительно OSNet после обучения = модель снова учится камере | 10 мин |
| **F3** | **проба на camera_id** | логистическая регрессия по замороженным эмбеддингам, **сплит по идентичностям** | случайный уровень 1/96 = **1,04 %**; top-1 ≥ **5 %** = камера читается | 20 мин |
| **F4** | «только фон» | объект залит средним пикселем, прогон | mAP > **0,10** или top-1 > **15 %**. Ориентир: на людях сеть, обученная только на фоне, даёт top-1 **25,9 %** | 40 мин (нужен сегментатор) |
| **F5** | подмена фона | случайный фон на валидации | падение top-1 > **10 п.п.** Ориентир: обычная модель 87,2 → 64,0, устойчивая теряет **1,4** | 30 мин |
| **F6** | срез «одна сцена / разные сцены» | mAP для кросс-камерных пар в одной сцене против разных | разрыв > **0,10** — работает фон, не машина | 15 мин |
| **F7** | обучение на перемешанных метках | 5–8 эпох с случайными vehicle_id | честная val mAP > **0,05** → в сплите утечка | 30 мин |
| **F8** | near-duplicate train ↔ val | косинус по CLIP-эмбеддингам, τ = 0,98 / 0,95 | hard > 3 %, soft > 7 % | 30 мин |

F1, F2 и F3 — минимальный обязательный набор: они меряют ровно ту болезнь, которая
вас подкосила, и стоят вместе 35 минут.

### 8.1. Дешёвый прокси: убивать плохой прогон на третьей эпохе

MCNL, Рис. 5 — pseudo-F по первым пяти эпохам:

| эпоха | 1 | 2 | 3 | 4 | 5 |
|---|---:|---:|---:|---:|---:|
| **MCNL** (правильный рецепт) | 3,921 | 1,596 | 0,848 | 0,715 | **0,656** |
| **Triplet** (шорткат) | 4,394 | 5,374 | 6,103 | 8,587 | **9,127** |

Расхождение видно уже на **второй эпохе** (3,4×). **Правило: если CH растёт две валидации
подряд — убить прогон.** Хороший паттерн — CH падает ≥2× за три эпохи. Это даёт сигнал
о правильности рецепта за 20–30 минут вместо трёх часов, что на вашем железе решающее.

**mAP на ранних эпохах для этого не годится** — она может расти именно за счёт шортката.

### 8.2. Сколько прогонов нужно, чтобы поверить приросту

Посчитано мной (точный нецентральный t, α = 0,05, мощность 0,8, σ = 0,0134):

| эффект Δ mAP | прогонов **на вариант** | всего |
|---|---:|---:|
| 0,010 | **30** | 60 |
| **0,020** | **9** | 18 |
| 0,030 | 5 | 10 |
| **0,050** | **3** | 6 |
| 0,020 с поправкой Бонферрони на 10 сравнений | 15 | 30 |

Минимально обнаружимый эффект при **одном** прогоне против одного (непарно) —
**0,0371**, а не 0,027. Парное сравнение по per-query AP гораздо мощнее: при ρ = 0,9
σ(Δ) = 0,0060 и MDE = **0,0117**. **Сначала измерьте ρ** между прогонами по per-query AP —
от этого зависит, нужно вам 9 прогонов или 1. У вас уже есть машинерия парного бутстрэпа.

Практический вывод при 2–3 часах на прогон: **широкий перебор невозможен**. Стройте план
вокруг нескольких крупных изменений с ожидаемым Δ ≥ 0,05 (тогда хватит 3 прогонов) и
отсеивайте плохие рецепты прокси-проверкой из §8.1.

### 8.3. Проклятие победителя — почему ваш подбор re-ranking провалился

Симуляция (200 тыс. повторов): выбор **лучшей из 30 эпох** по валидационной mAP завышает
её в среднем на **+0,027**; лучшей из 10 — на +0,021; из 5 — на +0,016. Это **больше
целевого эффекта +0,02**. Ровно этот механизм (плюс загрязнение протокола обученными
идентичностями) объяснил, почему «честно подобранный» оптимум (8, 6, 0,45) оказался на
валидации хуже старого (6, 3, 0,3): 0,4692 против 0,4891.

Лечение: валидировать раз в 5 эпох, а не каждую; брать скользящее среднее или EMA-веса;
**разделить валидацию на `val-dev` (выбор) и `val-lock` (объявление)**; число сравнений
объявлять заранее.

### 8.4. Правило приёмки — пара чисел, а не одно

Ваш диагностический показатель правильный, его надо возвести в формальное правило:

| честный mAP | разрыв (без исключения камеры − честный) | вердикт |
|---|---|---|
| ↑ | ↓ или не изменился | **принять** |
| ↑ | ↑ | **отклонить** — модель снова учится фону, рост временный и на тесте не повторится |
| не изменился | ↓ | принять условно: качество то же, устойчивость выше |
| ↓ | любой | отклонить |

Опорные значения: у готовых весов разрыв **+0,156** по mAP и +0,340 по R1;
у провалившейся модели **+0,265** и **+0,597**. Цель — разрыв ≤ 0,156, то есть не хуже
готовых весов. Рядом держать кросс-камерный Rank-1: 0,631 у OSNet против 0,379 у
провалившейся — этот показатель различает модели резче, чем mAP.

### 8.5. Ещё одно, что стоит поставить: сплит по сценам

Marchwica et al. ([arXiv:1805.06086](https://arxiv.org/abs/1805.06086)) измерили цену
зависимости от сцены напрямую: переход от scene-dependent к scene-independent протоколу
стоит **~30 п.п. Rank-1** (73,6 % → 49,3 %) и **вдвое mAP** (0,45 → 0,23); даже при
84 тыс. кадров разрыв остаётся ~20 п.п. Ваши 60 общих сцен между train и test
(`context-split.md`, §6.4) означают, что честная валидация всё ещё частично
сценозависима. Имеет смысл построить третий, более строгий срез `val-newscene` и
репортить обе цифры — даже если там останется ~150 запросов (σ вырастет до ~0,032).

## 10. Честная оценка: на что можно рассчитывать

### 10.1. Арифметика

Отправная точка: **0,6566** без переранжирования, **0,6937** с ним.

Приросты, на которые есть замеры, с поправкой на то, что они **не складываются**
(ICLR'25 §5.4 прямо предупреждает о перекрытии эффектов камерных приёмов):

| источник | табличный Δ | реалистичная доля у нас |
|---|---:|---|
| правильный старт вместо ImageNet | +11,5…+19,7 | **уже в 0,6566** — это не прибавка, это база |
| сэмплер с внутрикамерным негативом | +9,8…+24,6 (SCT) | +2…+5 (у нас не SCT) |
| P×K 8×4 → 16×4 | +3,7 | +1…+3 |
| BNNeck, если его не было | +4,0 (свой) / +3,4 (чужой) | +0…+4 |
| снятие REA, если он был | +10,7 (cross-domain) | +0…+5 |
| MixStyle после res1+res2 | +4,1…+4,5 (cross-domain) | +1…+3 |
| BIR k=0,2 | +4,96 (VeRi-776) | +1…+3 |
| **итого дообучение** | | **+4…+8 → mAP 0,70–0,74** |
| k-reciprocal (6, 3, 0,3) | у вас +3,7 | +3…+5 |
| камерный штраф VOC-ReID | +3,8 | +0…+4 |
| **итого с пост-обработкой** | | **0,73–0,79** |

### 10.2. Прямой ответ на вопрос «дотянем ли до 0,8»

**Центральная оценка — 0,73–0,77 mAP с переранжированием.** Это на 0,04–0,08 выше
нынешних 0,694, то есть в 3–6 раз больше σ измерения — эффект будет виден надёжно.

**0,80 достижимо, но только при совпадении трёх условий:** (а) камерный штраф VOC-ReID
перенесётся на ваши данные в полную силу (+3,8), (б) в провалившемся конфиге были REA
и/или отсутствовал BNNeck, то есть есть «бесплатные» пункты, (в) дообучение само по себе
даст верхнюю границу коридора. Я оцениваю вероятность всех трёх сразу как **низкую** и
не рекомендую закладывать 0,80 в обязательства.

**Риск, который надо назвать прямо: дообучение может снова оказаться хуже 0,694.**
Литература даёт этому прямое основание — полное дообучение на малой выборке теряет
**−7 % OOD** против линейного пробинга (LP-FT). Именно поэтому в §7.6 стоят ворота после
каждого этапа: план обязан уметь остановиться и оставить готовые веса.

### 10.3. План Б, который может оказаться планом А

Если после этапов 0–1 дообучение не даёт прироста, **правильный ход — не чинить обучение,
а вложить оставшиеся дни в пост-обработку**. Основания:

- камерный штраф VOC-ReID: **+3,8 mAP**, не требует ни одной эпохи обучения основной
  модели, использует ваши `camera_id`, не требует их на инференсе;
- переранжирование у вас недобирает: даёт +0,037, тогда как литературные пары дают
  **+4…+10 mAP** (78,94→88,44 и 80,8→88,0 на VeRi-776; 88,19→92,38 на VERI-Wild). Тут
  есть запас — но подбирать параметры **только на незагрязнённом протоколе**;
- обе меры — постпроцессинг матрицы расстояний, в замер «кроп → эмбеддинг» не попадают.

0,6566 + 0,038 (камерный штраф) + 0,04…0,06 (переранжирование) = **0,73–0,75 вообще без
обучения**. Это почти вся центральная оценка §10.2 — при кратно меньшем риске. Сравните
с тем, что дало обучение в прошлый раз: −0,22.

### 10.4. Что осталось непроверенным

1. **Конфиг провалившегося прогона** — были ли там REA, BNNeck, label smoothing. Два из
   моих трёх «бесплатных» пунктов зависят от ответа. Проверить первым делом.
2. **Величина эффекта MCNL-негатива вне SCT-сеттинга** — прямого замера в литературе нет.
   +24,6 это верхняя граница для случая без кросс-камерных позитивов вообще.
3. **Перенос камерного штрафа VOC-ReID на ваши данные** — их замер на CityFlow, 36 камер
   против ваших 96, и в паре с ориентационным штрафом.
4. **Замера «re-id веса vs ImageNet» на vehicle с явным указанием размера цели** нет;
   кривая «сколько ID → какое качество» существует только для person (LUPerson).
5. **Переноса person → vehicle** не измерял никто (искали пятью формулировками).
6. **Оценки памяти** для OSNet-AIN @208 (3 908 МБ) и R50-IBN (3 134 МБ) — расчёт,
   калиброванный на одной подтверждённой точке. Мерить на месте.
7. **Семантика ваших 96 `camera_id`** (PTZ-точка или сессия) — если часть «разных» камер
   на деле одна физическая точка, и сэмплер, и метрика слегка смещены.
8. **Происхождение чекпойнта OSNet-AIN** в OMZ (на чём обучен — в README не названо).
   Модель под MIT, но для промышленной эксплуатации это стоит выяснить у Intel.

## Приложение: порядок работ на ближайшие дни

| день | работа | выход |
|---|---|---|
| 1 | зафиксировать `pip freeze`; проверки F0–F3, F6 на готовых весах; посмотреть конфиг провалившегося прогона | опорные CH, точность камерной пробы, ответ про REA/BNNeck |
| 1–2 | вынуть веса из ONNX в torch, приёмка (**mAP 0,6566**, косинус ≥ 0,9999) | обучаемая модель-старт |
| 2 | камерный штраф VOC-ReID: обучить `osnet_x0_25` на 96 классах камер, померить на готовых весах | **немедленный прирост без дообучения основной модели** |
| 2–3 | этап 1 (LP, 5 эпох, ~30 мин) + прокси-проверка CH на эпохах 1–3 | ворота: идти дальше или нет |
| 3–5 | этап 2 (12–15 эпох, ~2 ч на прогон), 3 прогона на вариант при Δ ≥ 0,05 | основной результат |
| 5–7 | A/B: IBN да/нет, верх/низ разморозки, BIR k=0,2 | по одному прогону, отсев по CH |
| 7–8 | этап 3 при наличии прироста; переподбор re-ranking **только на незагрязнённом протоколе** | финальные числа |

`Adam(foreach=False)` — минус 98,8 МБ бесплатно. Каждый прогон — 2–4 часа, ни одного
многодневного.
