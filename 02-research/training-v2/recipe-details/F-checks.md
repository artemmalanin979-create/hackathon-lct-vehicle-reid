## F0. Гигиена метрики: знаменатель mAP, junk-маска, шум разрыва

**Что меряем.** Как именно 278 «отказных» запросов (без кросс-камерной пары) входят в
mAP, и совпадает ли реализация исключения камеры с протоколом Market.

**Как считать.**
```
mAP_A = mean(AP_q for q in 832 matched)              # исключаем отказные
mAP_B = (sum(AP_q for q in 832) + 0*278) / 1110      # отказные как AP=0
# mAP_B = mAP_A * 832/1110 = 0.7495 * mAP_A
```
Проверить, какая из двух цифр — наш 0,657. Разница между ними — 25 % относительных,
это в 18 раз больше sd измерения (0,0134) и в 12 раз больше нашего целевого эффекта.
Также: в протоколе Market из галереи выбрасываются (а) те же id с той же камеры, (б)
junk-кадры (id = −1/0). Если у нас нет распределителей, пункт (б) отсутствует — это надо
зафиксировать письменно, иначе сравнение с литературными числами на Market некорректно.

**Отдельно — шум самого диагностического разрыва.** Разрыв Δ = mAP_noexcl − mAP_excl
считается на тех же запросах, значит это *парная* величина. Его sd надо получать из того
же бутстрэпа по per-query AP:
```
for b in 1..4000:
    idx = resample(query_ids)                 # один и тот же idx для обоих прогонов
    gap_b = mean(AP_noexcl[idx]) - mean(AP_excl[idx])
sd_gap = std(gap_b)
```
Без этого нельзя утверждать, что +0,265 достоверно больше +0,156. Ожидаемо sd_gap будет
существенно меньше 0,0134 (парные величины сильно коррелированы), но его надо посчитать,
а не предположить.

**Плохо:** если mAP_noexcl и mAP_excl считаются на разных подмножествах запросов
(например, в non-excl прогоне «отказные» вдруг получают верные ответы со своей камеры и
попадают в знаменатель) — тогда разрыв вообще несравним. Это самый вероятный источник
ложного +0,265.

**Цена:** 10 минут чтения кода + 2 минуты прогона.

**Ссылка:** Zheng et al., *Scalable Person Re-identification: A Benchmark*, ICCV 2015
(протокол Market-1501, junk/good, исключение своей камеры) —
https://openaccess.thecvf.com/content_iccv_2015/papers/Zheng_Scalable_Person_Re-Identification_ICCV_2015_paper.pdf ;
VERI-Wild: «images with the same camera id and same vehicle id as the query are removed
from the gallery» — https://github.com/PKU-IMRE/VERI-Wild

## F1. Камерный оракул: сколько mAP достижимо из ОДНОЙ камеры

Самая дешёвая и самая жёсткая проверка. Ставится за 5 минут на уже имеющихся признаках
OSNet, никакого обучения не требует.

**Что меряем.** Сколько нашей метрики можно набрать, зная ТОЛЬКО камеру кадра и ничего
о машине. Это прямой верхний предел вклада «короткого пути».

**Как считать.**
```python
# 1. извлекли f[i] (D-мерные L2-нормированные эмбеддинги) для query+gallery
# 2. посчитали средний вектор каждой камеры ПО ГАЛЕРЕЕ
m[c] = normalize(mean(f[i] for i in gallery if cam[i]==c))
# 3. подменили КАЖДЫЙ эмбеддинг на средний вектор его камеры
f_cam[i] = m[cam[i]]
# 4. прогнали ровно тот же eval (с исключением камеры запроса)
mAP_camera_oracle = evaluate(f_cam)
```
Варианты того же за минуты: (а) `f_resid[i] = f[i] - m[cam[i]]` — камерное центрирование,
показывает, сколько mAP *прибавится*, если убрать камерное среднее; (б) прогнать
оракул без исключения камеры — получим потолок шортката.

**Что считать плохим.**
- Пол случайных эмбеддингов у нас уже измерен: **0,0103**. Камерный оракул на честном
  протоколе должен лежать рядом с ним.
- **mAP оракула > 0,05 (5× пола)** — протокол пропускает камерную информацию: значит,
  сцены соседних камер похожи, и «исключение своей камеры» не защищает.
- Аналог из литературы: Tian et al. CVPR'18 обучили сеть **только на фоне** (объект залит
  средним пикселем) и получили top-1 **25,9 %** на оригинальном CUHK03 и **37,1 %** на
  фоновом тесте — против случайного угадывания. То есть на person-датасетах «только фон»
  даёт четверть top-1. Если у нас будет что-то похожее, лечить надо сначала протокол.
- Камерное центрирование (вариант «а») — это ровно метод из ICLR'25 «Exploring the Camera
  Bias of Person Re-identification». Там на Market-1501 (unseen domain) центрирование по
  камерам даёт **CC: mAP 22,5 → 30,0 (+7,5), камерный bias NMI 17,1 → 11,2**;
  **TransReID: mAP 43,1 → 52,5 (+9,4), bias 13,6 → 10,9**. Если у нас прирост от
  центрирования такого же порядка (+0,05…+0,09 mAP) — признаки заметно камерно-смещены.
  Замечание: на *seen* домене у супервизных моделей прирост нулевой, их bias уже почти
  равен «bias ground truth» (SOLIDER на Market 7,3 против GT 6,4).

**Цена:** 5 минут (признаки уже есть).

## F2. Pseudo-F (Calinski–Harabasz) камерной разделимости признаков

Это ровно тот количественный детектор нашей болезни, который просили. Разбираю до конца,
включая то, чего в статье нет.

### F2.1. Точное определение

Pseudo-F = **индекс Calinski–Harabasz** (Caliński & Harabasz, 1974), он же variance ratio
criterion. В статье SCT это указано явно: «we use the pseudo F statistics (Caliński and
Harabasz 1974) to evaluate the relations of feature distributions of different cameras
quantitatively» (arXiv:1909.10848, §Visualization).

Для матрицы признаков X ∈ R^{n×d} и разметки на k групп (у нас группы = камеры):

```
    B = Σ_c  n_c · ||μ_c − μ||²          (between-cluster sum of squares, trace)
    W = Σ_c  Σ_{i∈c} ||x_i − μ_c||²      (within-cluster sum of squares, trace)

    CH = [ B / (k − 1) ] / [ W / (n − k) ]
```
μ — глобальное среднее, μ_c — среднее камеры c, n_c — число кадров камеры c.
Реализация: `sklearn.metrics.calinski_harabasz_score(X, camera_labels)` — ровно эта формула.
Без sklearn — 12 строк numpy:
```python
def ch(X, lab):
    n, d = X.shape; ks = np.unique(lab); k = len(ks); mu = X.mean(0)
    B = sum((lab==c).sum() * ((X[lab==c].mean(0)-mu)**2).sum() for c in ks)
    W = sum(((X[lab==c] - X[lab==c].mean(0))**2).sum() for c in ks)
    return (B/(k-1)) / (W/(n-k))
```

**Большое значение CH = признаки кластеризуются по камерам = плохо.** Прямая цитата:
«A larger value of pseudo F indicates more distinct clusters, which means the extracted
features are more related to cameras. In other words, a smaller value of pseudo F implies
that features are better learned.»

### F2.2. Чего в статье нет и что нужно нам: нулевой уровень CH = 1

Это ключ к переносу чисел SCT на наши 96 камер. CH — это F-статистика. Под нулевой
гипотезой (метки камер независимы от признаков) для каждого измерения j работает
ANOVA-разложение: E[SSB_j] = (k−1)σ_j², E[SSW_j] = (n−k)σ_j². Суммируя по d измерениям,
получаем **E[CH_null] = 1 при любых n, d, k**.

Проверено симуляцией (по 60–80 повторов, случайные метки камер):

| n | d | k | среднее CH_null | sd | P95 |
|---|---|---|---|---|---|
| 500 | 2 (t-SNE!) | 8 | 0,976 | 0,478 | 1,79 |
| 500 | 2048 | 8 | 0,999 | 0,014 | 1,02 |
| 1110 | 512 | 96 | 1,000 | 0,006 | 1,01 |
| 7248 | 512 | 96 | 1,000 | 0,007 | 1,01 |
| 750 | 2048 | 96 | 0,999 | 0,003 | 1,00 |

С коррелированными (низкоранговыми) признаками среднее остаётся 1, но разброс растёт:
при эффективном ранге 16 — sd 0,036 / P95 1,061; при ранге 4 — sd 0,076 / P95 1,135;
при ранге 1 — sd 0,173 / P95 1,29. **Вывод: всегда считать эмпирический нулевой уровень
перестановкой меток камер** (200 перемешиваний, секунды), а не полагаться на 1,0.

Второй вывод: **CH на 2D t-SNE (как в статье) шумный (sd 0,48)**. Значения 0,404 и 0,255
у SCT лежат в пределах одного sd нулевого распределения для d=2 — они означают «камерной
структуры не осталось», а не «структура отрицательная». Нам надо считать CH на сырых
L2-нормированных признаках (d=512/2048), где нулевое распределение узкое.

### F2.3. Перевод CH в «долю дисперсии, объясняемую камерой»

Пусть f — истинная доля дисперсии признака, приходящаяся на камеру. Тогда
```
    CH ≈ 1 + n·f / [ (k−1)(1−f) ]        ⇔        f = (CH−1)(k−1) / [ n + (CH−1)(k−1) ]
```
(проверено симуляцией: планируемое f=0,10 при n=1110, k=96 → CH=2,293; формула даёт 2,298).

Пересчёт чисел SCT (Duke, n=500 сэмплов, k=8 камер):

| метод (SCT Fig.3) | CH | f (доля дисперсии на камеру) |
|---|---|---|
| Triplet-other (худший) | 16,683 | 18,0 % |
| **Triplet (аналог нашей провалившейся модели)** | **8,433** | **9,4 %** |
| Triplet-same | 0,404 | ниже нуля (структуры нет) |
| MCNL (исправленный) | 0,255 | ниже нуля (структуры нет) |

**Важно: CH зависит от n.** При одном и том же f=0,05 получается CH=1,62 на n=1110 и
CH=5,00 на n=7248. Поэтому нельзя переносить «8,433» как абсолютный порог на нашу выборку —
переносить надо f или CH, посчитанный на выборке того же размера.

Калибровочная таблица для нашего случая (k=96), симуляция:

| f (доля дисперсии на камеру) | CH при n=1110 (валидация) | CH при n=7248 (train) |
|---|---|---|
| 0,00 | 1,00 | 1,00 |
| 0,02 | 1,23 | 2,55 |
| 0,05 | 1,62 | 5,00 |
| 0,10 | 2,29 | 9,41 |
| 0,20 | 3,90 | 19,8 |

### F2.4. Пороги

Считать CH **на валидации** (1 110 запросов + 750 галереи, метки камер валидации),
на L2-нормированных признаках, с перестановочным нулём:

- **CH ≤ 1,1** (f ≲ 1 %) — камерной структуры нет. Цель.
- **CH 1,1 … 2,0** (f 1–8 %) — терпимо, но следить.
- **CH ≥ 2,0** (f ≥ 8 %) — **стоп-сигнал**: камера объясняет столько же дисперсии, сколько
  у SCT-Triplet, который провалился.
- **CH ≥ 5** — катастрофа, обучение остановить.
- **Динамический критерий важнее статического:** CH готовых весов OSNet замерить ДО
  обучения и считать его референсом. Если после дообучения CH вырос — рецепт вреден,
  независимо от абсолютного значения.

200 перестановок).

## F3. Линейный/логистический пробинг эмбеддингов на camera_id

### F3.1. Что меряем

Насколько камера линейно **декодируема** из замороженного эмбеддинга. Это дополняет F2:
CH ловит «камера = главная ось разброса», пробинг ловит «камера закодирована, пусть и в
малой доле дисперсии» (случай, когда CH мал, а информация всё равно есть).

### F3.2. Как считать — 15 строк

```python
# 1) ЗАМОРОЖЕННЫЕ признаки. Модель не трогаем вообще (Alain & Bengio 2016).
F, cam, pid = extract(model, all_frames)          # F: [N, D], L2-норма
# 2) Сплит ПО ИДЕНТИЧНОСТЯМ, а не по кадрам!  Иначе проба запомнит экземпляры.
ids = unique(pid); tr_ids, te_ids = split(ids, 0.7)
Xtr, ytr = F[isin(pid,tr_ids)], cam[isin(pid,tr_ids)]
Xte, yte = F[isin(pid,te_ids)], cam[isin(pid,te_ids)]
# 3) Мультиномиальная логрегрессия, слабая L2, class_weight='balanced'
clf = LogisticRegression(max_iter=2000, C=1.0, class_weight='balanced',
                         multi_class='multinomial').fit(Xtr, ytr)
acc      = clf.score(Xte, yte)                    # top-1
bal_acc  = balanced_accuracy_score(yte, clf.predict(Xte))
# 4) НУЛЬ — не 1/96, а эмпирический: перемешать cam внутри train и переобучить
null = [LogisticRegression(...).fit(Xtr, shuffle(ytr)).score(Xte, yte) for _ in range(20)]
# 5) Репортить нормированную величину
leak = (bal_acc - mean(null)) / (1 - mean(null))   # 0 = нет утечки, 1 = камера читается идеально
```

Три обязательные детали, без которых число ничего не значит:
1. **Сплит по идентичностям.** Кадры одной машины с одной камеры почти дубликаты; при
   сплите по кадрам проба покажет 90 % на любых признаках.
2. **Эмпирический нуль перестановкой**, а не 1/96 = 1,04 %. При 96 несбалансированных
   камерах majority-class baseline может быть 5–10 %.
3. **Пробу обучать post-hoc, на замороженных признаках.** Если в обучении есть
   состязательная голова — её собственная точность НЕ является измерением. Elazar &
   Goldberg (EMNLP 2018) показали: adversary во время обучения показывает **49,0 %**
   (случайный уровень 50 %), а post-hoc-атакующий на ТЕХ ЖЕ представлениях и с той же
   архитектурой достаёт **56,0 %**; при 5 состязательных головах — **59,7 %**. Вывод
   авторов дословно: «do not rely on adversarial training to achieve invariant
   representation to sensitive features».

### F3.3. Что считать плохим

Абсолютные пороги для 96 камер (n_test ≈ 1 100 кадров валидации):
- Случайный уровень 1/96 = **1,04 %**; 95 %-верхняя граница под нулём при n=1110 — **1,64 %**.
- **top-1 ≥ 5 %** (z ≈ 13 против случайного) — камера уверенно читается. Для нашей задачи
  это **стоп-сигнал**: 5 % = в 5 раз выше случайного.
- **top-1 ≥ 20 %** (z ≈ 62) — камера доминирует, сеть выучила точку съёмки.
- Нормированная утечка `leak ≥ 0,15` — ориентир, эквивалентный ~15 % «восстановимости».
- **Динамика важнее уровня.** Замерить пробу на готовых весах OSNet до обучения; если
  после дообучения top-1 пробы вырос — рецепт вреден. Это прямой аналог диагностики
  «разрыв вырос с +0,156 до +0,265».

Литературные ориентиры величин «плохо/хорошо» (прямых чисел по камерам в re-id мало,
поэтому даю ближайшие количественные аналоги):

| источник | атрибут | «до» | «после дебиасинга» | нуль |
|---|---|---|---|---|
| Elazar & Goldberg, EMNLP'18 | раса по тексту, post-hoc probe | 83,9 % (обучение напрямую) | 56,0 % (после adversarial) | 50 % |
| Elazar & Goldberg, EMNLP'18 | тот же, «показания» самого adversary | — | 49,0 % (ложь) | 50 % |
| ICLR'25, arXiv:2502.10195 | камера, NMI кластеров (Market, unseen) | 17,1 (CC) | 11,2 (после камерной нормализации) | 6,4 (GT) |
| ICLR'25 | камера, NMI (MSMT17-Train, seen) | 34,7 (unsup CC) | 23,2 (супервиз. SOLIDER) | 21,1 (GT) |

Т.е. в литературе «дебиасинг сработал» = превышение над нулём упало примерно **вдвое**
(17,1→11,2 при нуле 6,4: превышение 10,7 → 4,8), а не «упало до нуля».

### F4.2. Как ставить у нас (у нас нет масок!)

Прямая честность: сегментационных масок автомобиля у нас нет. Три варианта по цене:

**(а) Центральный бокс, 0 минут подготовки.** Кропы vehicle re-id почти всегда центрированы
на машине. Залить центральный прямоугольник (0,15 … 0,85 по обеим осям, ~49 % площади)
средним пикселем датасета → «только фон». И обратный вариант: залить всё ВНЕ бокса →
«только объект». Это грубо (часть фона попадёт в бокс), но даёт нижнюю оценку эффекта и
стоит ноль.

**(б) YOLOv8n-seg / любой лёгкий instance-segmenter**, ~7 МБ весов, влезает в 4 ГБ Maxwell.
Прогон по 1 860 кадрам валидации — 2–5 минут. Классы COCO car/truck/bus есть из коробки.

**(в) SAM / SAM2** — качественнее, но на M2000M 4 ГБ тяжело; на CPU ~2–4 с/кадр → 1–2 часа
на валидацию. Оправдано только если (б) даёт плохие маски.

**Протокол теста (важно — модель НЕ переобучаем):**
```
для каждого из 4 вариантов галереи+запросов:
   original        — как есть
   bg_only         — пиксели маски объекта = среднее по датасету
   mean_background — пиксели ВНЕ маски = среднее (объект на сером)
   random_background — пиксели вне маски = случайное фото из набора 100 шт.
прогнать честный eval (с исключением камеры) на каждом → mAP, top-1
```
Ровно эти 4 датасета определены у Tian et al., §2.1.

### F4.3. Что считать плохим

| величина | норма | стоп-сигнал |
|---|---|---|
| mAP на `bg_only` (честный протокол) | ≤ 0,03 (≈3× пола 0,0103) | **> 0,10** |
| top-1 на `bg_only` | сопоставим с 5,3 % Tian | **> 15 %** |
| mAP(original) − mAP(mean_background) | ≤ 0,05 | **> 0,10** |

Обоснование верхней планки: у Tian на person «плохая» модель (DGD) при заливке фона
теряла 10,0 п.п. top-1 (87,2 → 77,2), а фоновый тест давал 5,3 %. У нас фон гораздо
информативнее (96 стационарных камер, 60 общих сцен), так что 5,3 % — оптимистичный
ориентир; всё, что выше 15 %, означает, что фон несёт больше сигнала, чем сама машина
теряет от заливки.

**Отрицательный результат тоже ценен:** если `bg_only` даёт ≈ пол (0,01), а модель всё
равно проваливается кросс-камерно, — проблема не в фоне, а в ракурсе/освещении/масштабе,
и лечить надо другим (аугментации цвета/геометрии, а не erasing фона).

## F5. Подмена фона на валидации

### F5.1. Числа из литературы — проверены построчно

**Tian et al. CVPR'18, Table 2** (модели НЕ переобучались под тест; DGD — обычная модель,
Ours — устойчивая, обученная с random-background аугментацией):

| Тест | DGD top-1 | Ours top-1 |
|---|---|---|
| CUHK03 original | **87,2** | 92,5 |
| CUHK03 mean-background | 77,2 (−10,0) | 91,7 (−0,8) |
| CUHK03 random-background | **64,0 (−23,2)** | 91,1 (**−1,4**) |
| Market-1501 original | 79,1 | 81,2 |
| Market-1501 mean-background | 71,1 (−8,0) | 80,5 (−0,7) |
| Market-1501 random-background | 58,4 (−20,7) | 79,8 (−1,4) |

Числа из ТЗ (87,2 → 64,0; устойчивая теряет 1,4) **подтверждаются точно**, причём −1,4
повторяется и на CUHK03, и на Market — хороший признак, что это реальный уровень
устойчивости, а не случай.

Дополнительно (§2.4): обучение на random-background стоит **2–3 п.п. на оригинальном
тесте** — это цена устойчивости, её надо заранее принять. То есть ожидать, что честная
mAP вырастет от одного только background-augmentation, не следует; вырастет *разница*
между честным и нечестным протоколом в нужную сторону.

### F5.2. Как ставить

```
1. Собрать 100 фоновых изображений, НЕ из нашего датасета (важно: иначе подменяем
   один наш фон на другой наш фон и меряем ноль). Tian брал 100 случайных фото из интернета.
   Для vehicle логично взять дорожные сцены без машин / любые текстуры.
2. Для каждого кадра валидации (запросы И галерея): маска объекта из F4,
   пиксели вне маски ← ресайзнутое случайное фоновое изображение.
   Фиксировать seed: одна и та же подстановка для всех сравниваемых моделей.
3. Честный eval (с исключением камеры).
4. Отдельно — вариант «подмена только в галерее» и «только в запросах»: разводит
   эффект «модель кодирует фон запроса» и «модель кодирует фон галереи».
```
Тонкий момент для нашего протокола: **подмена фона ломает камерный шорткат физически**.
Если mAP на random-background близка к честной mAP — фон не используется; если резко
падает — используется. Это независимая проверка того же, что меряет разрыв +0,156/+0,265,
и она не зависит от корректности исключения камеры.

### F5.3. Что считать плохим

- **Падение top-1 > 10 п.п.** при подмене фона — модель опирается на фон. Референс: DGD
  теряет 23,2 п.п., устойчивая модель — 1,4 п.п.
- **Падение mAP > 0,08** — тот же сигнал в нашей основной метрике.
- Целевой уровень после лечения: **потеря ≤ 3 п.п. top-1** (реалистичная планка; 1,4 п.п.
  у Tian получено с явной сегментационной архитектурой, которой у нас не будет).
- Ещё один полезный производный показатель:
  `robustness = mAP(random_bg) / mAP(original)`. У DGD ≈ 0,73; у устойчивой ≈ 0,985.
  **Стоп-сигнал: robustness < 0,85.**

## F6. Разложение метрики по «сложности» пары

### F6.1. Стандартные срезы, которые есть в литературе

Готовых «стандартных» срезов по числу кросс-камерных верных в re-id **нет** — это придётся
определить самим. Но есть три признанных инструмента, которые надо взять:

1. **q-mAP и g-mAP** (Adversarial Pairwise Reverse Attention, arXiv:2207.01204, §4) —
   единственные опубликованные per-camera метрики для re-id:
   ```
   q-mAP(c) = (1/|Q_c|) Σ_{q∈Q_c} AP(q, G)          # запросы с камеры c, полная галерея
   g-mAP(c) = (1/|Q_c|) Σ_{q∈Q_c} AP(q, G_q)        # в галерее оставлены ТОЛЬКО позитивы
                                                     # с камеры c (плюс все негативы)
   ```
   Авторы репортят пару «Weakest Camera / Average Camera» — именно этот разрыв и есть
   интересующая нас величина. В их таблицах для BagTricks разрыв доходит до
   **Q-mAP 17,4 (слабейшая камера) против 85,4 (средняя)** на разных датасетах — т.е.
   среднее по датасету может полностью скрывать, что часть камер не работает вовсе.

2. **mINP** (Ye et al., TPAMI 2021, arXiv:2001.04193) — mean Inverse Negative Penalty,
   `mINP = (1/N) Σ_i |G_i| / R_i^hard`, где R_i^hard — ранг САМОГО ТРУДНОГО верного.
   Специально придуман, чтобы «avoid the domination of easy matches in the mAP/CMC
   evaluation». Для нас критично: если верных 2–3, mAP почти целиком определяется первым
   найденным, mINP — последним.

3. **Пол/потолок как якоря**: случайные эмбеддинги 0,0103 (у нас есть), one-hot 1,0.
   Все срезы читать относительно них.

### F6.2. Что реально считать у нас

**Срез А — по числу кросс-камерных верных в галерее.** Наши 832 сматченных запроса
разбить на группы n_pos = 1 / 2 / 3+ и посчитать mAP в каждой.

*Математическое предупреждение, без которого срез читается неверно:* AP при n_pos=1 — это
ровно 1/rank первого верного, его распределение сильно отличается от AP при n_pos=3.
Сравнивать группы «в лоб» некорректно. Правильно — **нормировать на случайный уровень внутри
группы**: для галереи размера G и n_pos позитивов случайный AP ≈ n_pos/G · (1 + ln(G/n_pos))
(приблизительно); либо просто нормировать на измеренный пол (случайные эмбеддинги,
посчитанный отдельно по каждой группе). Репортить `lift = mAP_group / mAP_random_group`.

```python
for grp, qs in group_by_npos(matched_queries):
    m_model  = mean(AP[q] for q in qs)
    m_random = mean(AP_random[q] for q in qs)      # тот же прогон случайных эмбеддингов
    print(grp, len(qs), m_model, m_random, m_model/m_random)
```

**Срез Б — матрица по парам камер.** 96×96 = 9 216 клеток на 832 запроса → в среднем
0,09 запроса на клетку. **Полную матрицу считать бессмысленно.** Что реально:
- оставить клетки с **n ≥ 10 запросами**, остальное — в корзину «прочее». При 832 запросах
  таких клеток будет, скорее всего, единицы–десятки;
- вместо матрицы считать **два маргинала**: q-mAP по камере запроса и g-mAP по камере
  галереи (см. выше) — это n ≈ 8–9 запросов на камеру при 96 камерах, всё ещё мало, но
  на порядок лучше;
- главная величина — **не сама матрица, а дисперсия между камерами**: sd(q-mAP по камерам)
  и min(q-mAP). Для доверительного интервала — бутстрэп внутри камеры;
- **сгруппировать камеры в сцены** (у нас известны сцены — 60 общих + остальные). 60 сцен ×
  60 = разреженно, но группировка «своя сцена / чужая сцена» даёт две большие группы,
  и вот это уже статистически осмысленно. **Это самый важный срез для нашей болезни:**
  ```
  mAP(запрос и верный — РАЗНЫЕ камеры, ОДНА сцена)
  mAP(запрос и верный — разные камеры, РАЗНЫЕ сцены)
  ```
  Если первое сильно выше второго — «исключение камеры» не исключает фон, потому что
  соседняя камера той же сцены даёт тот же фон.

**Срез В — внутри/между камер (уже есть).** Rank-1 0,976 внутри своей камеры против 0,379
между — это уже готовый срез, надо только добавить к нему доверительные интервалы
(бутстрэп по запросам) и посмотреть его в разрезе сцен.

### F6.3. Что считать плохим

- **mAP(одна сцена, разные камеры) − mAP(разные сцены) > 0,10** — стоп-сигнал: работает
  фон сцены, а не машина. Это наш аналог разрыва +0,265 и, в отличие от него, не зависит
  от корректности camera-id.
- **min(q-mAP) < 0,3 × mean(q-mAP)** — часть камер не обслуживается вовсе (по аналогии с
  17,4 против 85,4 в arXiv:2207.01204).
- **lift(n_pos=1) < 0,5 × lift(n_pos=3+)** — модель находит «лёгкие» дубли и не находит
  настоящие кросс-камерные пары.
- **mINP < 0,1 × mAP** — все верные, кроме первого, тонут.

### F6.4. Цена

15 минут (всё считается по уже сохранённым per-query AP и ранжировкам; никакого
переобучения). Обязательное условие: **сохранять per-query AP и top-50 ранжировку на диск
для каждого прогона** — без этого любое разложение потом потребует перепрогона.

## F7. Контроли, ловящие утечку и ошибку измерения

Пять контролей, от дешёвого к дорогому. Три первых — за минуты.

### F7.1. Пол и потолок (уже есть)

- случайные эмбеддинги → **0,0103**; one-hot идеальные → **1,0**.
- Держать оба числа в отчёте каждого прогона. Любое значение метрики читать как
  `(mAP − 0,0103)/(1 − 0,0103)`.
- Добавить третий якорь: **эмбеддинг = только камера** (F1). Это пол «шортката».

### F7.2. Перестановочный тест по меткам (permutation test)

**Что меряем.** Достоверно ли наша метрика вообще отличается от случайной, и как выглядит
её нулевое распределение на НАШЕЙ (маленькой) валидации.

**Как считать.**
```
for b in 1..1000:
    pid_perm = shuffle(gallery_pid)        # перемешиваем метки идентичностей галереи
    mAP_b = evaluate(features, pid_perm)   # признаки НЕ трогаем
p = (#{mAP_b >= mAP_obs} + 1) / (1001)
```
Это «первый тест» Ойалы–Гарриги: «assesses whether the classifier has found a real class
structure in the data; the null distribution is estimated by permuting the labels».

**Что считать плохим.** Ожидаемо p < 0,001 для любой разумной модели (иначе катастрофа).
Реальная польза — **не p, а ширина нулевого распределения**: она даёт sd метрики при
полном отсутствии сигнала, что нужно для интерпретации срезов из F6, где групп мало.

**Цена:** 1000 прогонов eval по матрице 1110×750 — это 1000 сортировок матрицы 832×750,
секунды на numpy. **2 минуты.**

### F7.3. Обучение на перемешанных метках

**Что меряем.** Есть ли утечка между train и val, которую метрика не должна была увидеть.

**Как считать.**
```
pid_shuffled = random_permutation(train_pid)   # метки машин случайны, картинки те же
train(model, images, pid_shuffled, epochs=N)   # тот же рецепт, что для боевого прогона
evaluate(model) на честной валидации
```
Zhang et al. (ICLR'17): «when trained on a completely random labeling of the true data,
neural networks achieve **0 training error**» — то есть сеть *обязана* выучить
перемешанные метки на train. Вопрос в том, что останется на валидации.

**Что считать плохим.**
- Честная val mAP после обучения на перемешанных метках должна быть **≈ пола (0,0103)**,
  максимум — на уровне «ImageNet-признаков без обучения».
- **val mAP > 0,05** → **есть утечка**: сеть выучила что-то, что помогает на валидации,
  хотя метки были мусором. Единственный источник — общая структура изображений (сцена/
  камера/время), т.е. именно наша болезнь.
- Обязательно параллельно смотреть train accuracy: если она НЕ дошла до ~1,0, эксперимент
  недообучен и вывод некорректен (аналогия с Zhang et al.).

**Цена:** это полноценный, но короткий прогон. На нашем железе 30 эпох × 7 248 кадров ≈ как
боевой прогон. **Ставить укороченную версию: 5–8 эпох, 30 минут.** Если за 8 эпох train
accuracy не поднялась — увеличить lr, а не число эпох.

### F7.4. «Модель, обученная только на камере»

**Что меряем.** Верхнюю границу mAP, достижимую вообще без знания машины, при нашем
конкретном сплите и правиле исключения камеры.

**Как считать.** Обучить ту же сеть на метках `camera_id` (96 классов) вместо `vehicle_id`,
5 эпох, и прогнать честный eval валидации.

**Что считать плохим.** Прямой аналог у Tian et al. §2.3: модель, обученная **только на
фоне**, даёт top-1 **25,9 %** на нормальном тесте. У нас:
- **mAP > 0,10** (10× пола) — протокол дырявый, честная метрика частично измеряет камеру.
- **mAP ≈ 0,01–0,03** — протокол чист, можно доверять основной метрике.

**Цена:** 20–30 минут (5 эпох).

### F7.5. Рандомизация весов (model parameter randomization)

**Что меряем.** Что наши диагностики (CH, проба, разрыв) действительно чувствительны к
модели, а не считают что-то структурное про датасет.

**Как считать.** Взять случайно инициализированную (необученную) сеть той же архитектуры,
извлечь признаки, посчитать ВСЕ диагностики: CH, пробу camera_id, разрыв, mAP.
Это прямой перенос «model parameter randomization test» из Adebayo et al.

**Что считать плохим.**
- Если у *случайной* сети проба camera_id даёт высокую точность — виновата не модель, а
  сами изображения (яркость/цветовой баланс/размер бокса тривиально выдают камеру). Тогда
  лечение — нормализация входа, а не лосс. **Это надо знать ДО обучения.**
- Известно, что низкоуровневые свойства изображения (яркость, резкость, площадь бокса)
  сами по себе несут камерное смещение: ICLR'25 (arXiv:2502.10195, §4.3) показывает, что
  групповая нормализация по яркости/резкости/площади даёт дополнительный прирост поверх
  камерной нормализации (~**+1,5 mAP** для (area, camera)-специфичной нормализации).
- Ориентир CH у случайной сети: как правило 1,5–4 на 96 камерах — из-за того, что цвет и
  масштаб уже кластеризуют. **Наш «reference CH» — это CH случайной сети и CH OSNet;
  цель — быть не выше их.**

**Цена:** 10 минут.

## F8. Ранняя остановка и выбор чекпоинта

### F8.1. По какой метрике останавливаться

**Не по train-loss.** На нашем размере (7 248 кадров, 1 171 класс, ~6,2 кадра на класс)
train-loss монотонно падает до нуля независимо от того, выучила ли сеть машину или камеру —
это ровно тот режим, в котором Zhang et al. показали посадку на случайные метки.

Останавливаться надо по **композитному критерию**, потому что валидационная mAP одна не
различает наши два режима:
```
score = mAP_честная − λ · max(0, gap − gap_ref)
        где gap = mAP_noexcl − mAP_excl,  gap_ref = 0,156 (уровень OSNet), λ ≈ 1
```
Смысл: чекпоинт, который набрал mAP ценой роста камерного разрыва, штрафуется. При λ=1
модель с mAP 0,70 и gap 0,30 (score 0,556) проигрывает модели с mAP 0,66 и gap 0,16
(score 0,656). Порог λ можно выбрать один раз и не трогать — важно зафиксировать его
ДО экспериментов, иначе λ становится ещё одной ручкой подгонки.

Дополнительно логировать на каждой валидации: CH (F2), top-1 пробы camera_id (F3),
mINP, q-mAP min. Останавливать прогон, если **CH растёт две валидации подряд** — см. F10.

Литературная опора на «останавливаться по валидации, а не по train»: Musgrave et al.
(«Training stops when validation accuracy plateaus», §3.3). Больше того: их центральный
вывод — «The best test set accuracy is reported without a validation set, meaning model
selection and hyperparameter tuning are done with direct feedback from the test set», и это
источник того, что заявленные приросты в deep metric learning за 4 года оказались «marginal
at best» вместо заявленных «>100 % относительно contrastive loss».

### F8.2. Как НЕ переподогнать под валидацию — считаем цену выбора

Это самая недооценённая часть, и здесь есть точный расчёт. При sd одного измерения
σ = 0,0134, если выбирать **лучший из m** кандидатов по валидационной mAP, ожидаемое
завышение (winner's curse) равно σ·E[max_m] (200 000 симуляций):

| m (сколько чекпоинтов/вариантов сравниваем) | E[завышение mAP] | P95 завышения |
|---|---|---|
| 3 | **+0,011** | +0,029 |
| 5 | **+0,016** | +0,031 |
| 10 | **+0,021** | +0,034 |
| 20 | **+0,025** | +0,038 |
| **30 (по чекпоинту на эпоху)** | **+0,027** | **+0,039** |
| 50 | +0,030 | +0,041 |
| 100 | +0,034 | +0,044 |

**Читается так: выбор лучшей из 30 эпох по валидационной mAP в среднем завышает mAP на
+0,027 — ровно столько же, сколько наш «порог значимости» 2σ, и больше, чем целевой эффект
+0,02.** Это количественное объяснение нашего случая с re-ranking: подбор гиперпараметров
на протоколе, где идентичности были в обучении, дал худший результат на честной валидации.

Практические следствия (все — обязательные правила, а не пожелания):
1. **Валидировать не каждую эпоху, а каждые 5** → m=6 вместо 30, завышение падает с
   0,027 до ~0,017.
2. **Не выбирать по максимуму.** Брать усреднение весов последних k чекпоинтов (SWA/EMA)
   или чекпоинт, у которого скользящее среднее по 3 валидациям максимально — это режет
   дисперсию выбора примерно в √3 раз.
3. **Разделить валидацию на две части: `val-dev` (подбор) и `val-lock` (единственное
   финальное измерение).** У нас 832 сматченных запроса — сплит 60/40 по идентичностям даёт
   ~500/330. sd на val-dev вырастет до 0,0134·√(832/500)=0,0173, на val-lock — до 0,0217.
   Это дорого, но иначе нет ни одного числа, которому можно верить в конце. **Правило:
   val-lock смотрится не чаще одного раза на рецепт, максимум 3–4 раза за весь проект.**
4. **Поправка на множественность.** Если сравниваем 10 вариантов с бейзлайном при α=0,05,
   Бонферрони даёт α=0,005: требуемое число прогонов для Δ=0,02 растёт с 9 до **15** на
   вариант (см. F9).
5. Про-отрезвляющая оговорка: Recht et al. построили новый тестовый набор ImageNet и
   получили падение точности на **11–14 %**, но **порядок моделей сохранился почти точно**,
   и вывод был, что падение вызвано не адаптивностью, а сдвигом сложности. То есть
   переподгонка под большой тест-сет — умеренная беда. **Но у нас тест-сет в ~40 раз
   меньше ImageNet-val, и winner's curse из таблицы выше — реальная цифра именно для нашего σ.**

### F8.3. Цена

Ноль дополнительного времени — это правила логирования и выбора. Единственная реальная
цена — сплит валидации на val-dev/val-lock, который увеличивает σ на 29 % / 61 %.

## F9. Сколько прогонов нужно, чтобы отличить +0,02 mAP от шума — РАСЧЁТ

### F9.1. Сначала — два разных шума, их нельзя путать

1. **σ_query = 0,0134** — это то, что даёт наш парный бутстрэп по per-query AP: шум
   *конечной валидационной выборки*. Он НЕ уменьшается от повторных прогонов обучения:
   валидация одна и та же. Он уменьшается только увеличением числа запросов.
   Обратная проверка: если σ = 0,0134 получено на n_q = 832, то sd одного per-query AP
   ≈ 0,0134·√832 = **0,387** — правдоподобно для AP со средним ~0,65. (Если n_q = 1110 →
   sd(AP) = 0,446.) Полезно сверить с реальными данными: это тест корректности бутстрэпа.
2. **σ_seed** — разброс между переобучениями с разными seed. У нас **не измерен**. Его надо
   измерить (3 прогона одного рецепта) прежде, чем делать любые выводы о приросте.
   Литературные ориентиры: Picard (arXiv:2109.08203) на CIFAR-10 — sd по 10⁴ seed-ам
   **0,20–0,23 п.п.**, но разброс min–max **1,82 п.п.** (89,01 … 90,83); на ImageNet с
   предобученными весами sd **0,08–0,11 п.п.**, min–max ~0,44 п.п. Вывод автора: «a 0,5 %
   difference in accuracy could be entirely explained by just a seed change».
   На нашем датасете (в 170 раз меньше CIFAR-10 по кадрам, дообучение с сильным сдвигом
   домена) σ_seed **заведомо больше** этих величин; ожидать 0,01–0,03 mAP.

Bouthillier et al. (MLSys 2021): самый крупный источник дисперсии — **бутстрэп данных**, а
инициализация весов даёт **менее 50 %** дисперсии бутстрэпа, наравне с порядком обхода SGD.
Их рекомендация №1: рандомизировать как можно больше источников (инициализация, сэмплинг
данных, аугментации, порядок батчей) в каждом прогоне, а не только seed инициализации —
это снижает стандартную ошибку среднего сильнее, чем повторы одного и того же.
Рекомендация №3: предпочитать out-of-bootstrap фиксированному held-out.

### F9.2. Расчёт мощности (двусторонний t-тест, α = 0,05, мощность 0,80, σ = 0,0134)

Точный расчёт по нецентральному t-распределению (не нормальная аппроксимация):

| эффект Δ (mAP) | прогонов на вариант, 2 независимые группы | всего прогонов | парный / односэмпльный вариант |
|---|---|---|---|
| 0,010 | **30** | 60 | 17 |
| **0,020** | **9** | **18** | **6** |
| 0,027 (= 2σ) | 6 | 12 | 5 |
| 0,030 | 5 | 10 | 4 |
| **0,050** | **3** | **6** | **3** |
| 0,100 | 2 | 4 | 3 |

С поправкой Бонферрони на 10 сравнений (α = 0,005): Δ=0,02 → **15** на вариант;
Δ=0,05 → **5** на вариант.

Обратная задача — минимальный обнаружимый эффект (MDE) при заданном бюджете:

| прогонов на вариант | MDE (α=0,05, мощность 0,8) |
|---|---|
| 1 vs 1 (t-тест невозможен, z-тест при известном σ=0,0134) | **0,053** |
| 2 (t-тест, df=2 — почти бесполезен) | 0,076 |
| 3 | **0,041** |
| 5 | **0,027** |
| 8 | 0,020 |
| 10 | 0,018 |
| 20 | 0,012 |

**Ответ на вопрос ТЗ: чтобы отличить +0,02 от шума при σ=0,0134 нужно 9 прогонов на
вариант (18 всего); чтобы отличить +0,05 — 3 прогона на вариант (6 всего).**
Одиночный прогон против одиночного прогона надёжно ловит только эффекты **≥ 0,053**.

### F9.3. Как получить то же за меньшие деньги: парный бутстрэп по запросам

Правило «разница меньше 0,027 незначима» — это 2·σ_single, и оно **избыточно строгое для
сравнения двух моделей на одной и той же валидации**. Обе модели оценены на одних запросах,
их per-query AP сильно коррелированы, поэтому считать надо sd *разности*:
```
sd(Δ) = σ_single · sqrt(2(1 − ρ)),  ρ = corr(AP_A, AP_B) по запросам
```

| ρ | sd(Δ) | MDE одного парного прогона |
|---|---|---|
| 0,0 | 0,0190 | 0,053 |
| 0,5 | 0,0134 | 0,038 |
| 0,8 | 0,0085 | 0,024 |
| **0,9** | **0,0060** | **0,017** |
| 0,95 | 0,0042 | 0,012 |

Для двух чекпоинтов одного обучения ρ будет 0,9+; для разных рецептов — 0,7–0,9.
**Практический вывод: сначала измерить ρ, потом решать, сколько нужно прогонов.
Вполне вероятно, что одиночный парный бутстрэп уже даёт MDE ≈ 0,017 < 0,02,
и 9 прогонов не нужны — нужны 2–3 (чтобы покрыть σ_seed).**

Процедура (правильный парный бутстрэп, 20 строк):
```python
d = AP_A - AP_B                               # вектор длины n_q, ОДНИ И ТЕ ЖЕ запросы
boots = [d[np.random.randint(0, n_q, n_q)].mean() for _ in range(10000)]
ci = np.percentile(boots, [2.5, 97.5])        # если 0 внутри CI — разницы нет
# и парный перестановочный тест (точнее бутстрэпа на малых n):
null = [ (d * np.random.choice([-1,1], n_q)).mean() for _ in range(10000) ]
p = (np.sum(np.abs(null) >= abs(d.mean())) + 1) / 10001
```

### F9.4. Итоговый регламент измерения (что прописать в протоколе)

1. σ_seed измерить один раз: 3 прогона базового рецепта с разными seed. **Цена: 3 прогона.**
   Если σ_seed > 0,02 — любые одиночные сравнения бессмысленны, и ничего кроме
   «эффект ≥ 0,05» доказать не получится.
2. Каждый рецепт — **минимум 3 прогона** (Δ=0,05 обнаружим). 9 прогонов ставить только для
   финального сравнения двух лучших.
3. Для каждой пары моделей — парный бутстрэп + парный знаковый перестановочный тест
   по per-query AP, репортить ρ, sd(Δ), 95 % ДИ разности.
4. Рандомизировать всё (init, порядок данных, аугментации), а не только seed init
   (Bouthillier, рекомендация 1).
5. Заранее объявить, сколько сравнений будет, и применить Бонферрони/Холма.

## F10. Дешёвый прокси-эксперимент: сигнал за 20–30 минут

### F10.1. Главная находка: pseudo-F на эпохах 1–5 разделяет хороший и плохой рецепт

Это лучший из найденных прокси, и он взят ровно из нашей референсной статьи.
**arXiv:1909.10848, Figure 5** («Visualization of learned feature distributions at the
**early training stage**») даёт pseudo-F на первых пяти эпохах для плохого и хорошего лосса:

| | Эпоха 1 | Эпоха 2 | Эпоха 3 | Эпоха 4 | Эпоха 5 |
|---|---|---|---|---|---|
| **MCNL (правильный рецепт)** | 3,921 | 1,596 | 0,848 | 0,715 | **0,656** |
| **Triplet (провальный рецепт)** | 4,394 | 5,374 | 6,103 | 8,587 | **9,127** |

Вывод авторов: «at the very beginning of training, Triplet learns more camera-related
features while MCNL quickly discards camera information».

**Это даёт готовый критерий раннего убийства прогона.** На эпохе 2 уже видно расхождение
(1,596 против 5,374 — в 3,4 раза), на эпохе 3 оно 7,2-кратное. Финальные значения
(Fig. 3: Triplet 8,433 → MCNL 0,255) почти совпадают с 5-эпоховыми — **ранняя траектория
предсказывает финал**.

### F10.2. Протокол прокси (20–30 минут на нашем железе)

```
Для каждого рецепта-кандидата:
  подвыборка: 40 % идентичностей train_fit (≈470 ид., ≈2 900 кадров), вход 160×160
  обучить 3 эпохи, сохранять чекпоинт после каждой
  после каждой эпохи на ВАЛИДАЦИИ (1 110 + 750 кадров):
      CH_e       = pseudo-F камерной разделимости  (F2)
      probe_e    = top-1 логистической пробы camera_id  (F3)
      gap_e      = mAP_noexcl − mAP_excl
      mAP_e      = честная mAP
Решение:
  УБИТЬ, если  CH_2 > CH_1  И  CH_3 > CH_2       (камерная структура растёт)
  УБИТЬ, если  gap_3 > gap_0 + 0,05               (разрыв растёт от уровня старта)
  УБИТЬ, если  probe_3 > probe_0 · 1,5            (камера стала читаться в 1,5 раза лучше)
  ПРОДОЛЖИТЬ, если CH падает монотонно И gap не растёт
```
Замер `*_0` (до обучения, на стартовых весах) обязателен как база сравнения.

Оценка времени на Quadro M2000M 4 ГБ: 2 900 кадров × 3 эпохи при ~25 img/s ≈ 6 минут
обучения + 3 × (2 мин извлечение признаков валидации + 1 мин диагностики) ≈ **15 минут
на рецепт**. За час перебираются 4 рецепта — это разумный бюджет для 10-дневного проекта
с падающим узлом.

### F10.3. Опора в литературе на то, что ранняя эпоха предсказывает финал

- Egele, Mohr, Viering, Balaprakash, *The Unreasonable Effectiveness Of Early Discarding
  After One Epoch In Neural Network Hyperparameter Optimization*, arXiv:2404.04111 (2024).
  Два прямых вывода: (1) «dynamically allocating resources as done by successive halving or
  learning curve extrapolation offers minimal (and oftentimes no) utility compared to a
  constant number of training epochs»; (2) «**one can often early discard models after only
  one epoch without losing significant final predictive performance**». Т.е. сложная
  экстраполяция кривых обучения не нужна — достаточно бейзлайна «1-Epoch».
- Wortsman et al., *Small-scale proxies for large-scale Transformer training instabilities*,
  arXiv:2309.14322 (ICLR 2024). Переносимый метод: **LR sensitivity** — прогнать маленькую
  модель на сетке learning rate и измерить, в каком диапазоне lr итоговый лосс остаётся в
  пределах δ от лучшего. Узкий диапазон = рецепт хрупкий и на большом прогоне развалится.
  Дополнительно: «two cases where instabilities can be predicted before they emerge by
  examining the scaling behavior of model activation and gradient norms» — логировать нормы
  активаций и градиентов с первой эпохи.
- Учтите ограничение: 2309.14322 — про трансформеры и нестабильность обучения, не про
  re-id и не про шорткаты. Переносится **методика** (маленький прокси + чувствительность к
  lr + ранние нормы), но не числа.

### F10.4. Что считать плохим

- **CH растёт две валидации подряд** → убить. (Triplet в Fig. 5: 4,394 → 5,374 → 6,103 —
  именно такой паттерн.)
- **CH на эпохе 3 больше CH стартовых весов** → убить.
- **Хороший паттерн:** CH падает минимум в 2 раза за 3 эпохи (у MCNL: 3,921 → 0,848, в 4,6 раза).
- **LR sensitivity:** если сдвиг lr в 2 раза меняет 3-эпоховый CH/mAP сильнее, чем на 2σ —
  рецепт хрупкий, брать более консервативный lr.
- **Осторожно:** mAP на эпохе 3 сама по себе плохой прокси — она может расти именно за
  счёт камерного шортката. Поэтому в критерии стоит CH/gap, а не mAP.

### F10.5. Цена

15–20 минут на рецепт. Обязательное вложение — **логирование диагностик на каждой
валидации**, иначе прокси не построить.

## F11. Утечка фона между train и test

### F11.1. Что у нас известно и что это значит

60 общих сцен между train и test, 1 общий физический кадр. Общий кадр — это **жёсткая
утечка** (hard leakage), её надо просто удалить. 60 общих сцен — **мягкая утечка**: сеть
может выучить «эта сцена = эти машины» на train, и на валидации фон будет помогать, хотя
идентичности не пересекаются.

### F11.2. Методика измерения — есть готовая и свежая

**Data Leakage in Visual Datasets** (arXiv:2508.17416) даёт полностью воспроизводимый
протокол near-duplicate детекции:
```
1. Энкодер: CLIP ViT-B/32 (авторы сравнили resnet152 / DINOv2 ViT-B/14 / CLIP ViT-B/32;
   CLIP лучше держит кроп и геометрические трансформации — а у нас именно кропы).
2. Все изображения train и test → эмбеддинги → FAISS / прямое косинусное сходство.
3. Для каждого test-изображения: max косинусное сходство с train.
4. Пороги:  τ_hard = 0,98  (идентичные),  τ_soft = 0,95  (почти идентичные).
5. H = доля test-изображений с sim ≥ τ_hard;  S = доля с τ_soft ≤ sim < τ_hard.
```
**Ориентиры «нормы» из статьи (на COCO / ImageNet / OpenImages / Flickr30k):**
«Hard leakage rates (i.e. identical images) tend to be **below 3 %**, whereas soft leakage
(i.e. near-identical images) reaches rates of **7 %**. In total, we find **up to 10 %
leakage**.» Примеры: OpenImages-train содержит ~1,5 % жёстко утёкших изображений из
COCO-test/val; ImageNet — ~3 % мягкой утечки; внутридатасетная мягкая утечка COCO-test
1,35–1,38 %.

**Наша адаптация — измерять надо не сходство кадров, а сходство ФОНОВ:**
```
6. Дополнительно: перед энкодером залить объект (маска из F4) средним пикселем.
   Теперь sim меряет похожесть ТОЛЬКО фона.
   S_bg = доля val-кадров, у которых есть train-кадр с фоновым sim ≥ 0,95.
7. И третья, самая прямая величина — доля val-запросов, чья сцена присутствует в train:
   scene_overlap = |{q : scene(q) ∈ scenes(train)}| / |val|
```
У нас scene_overlap известен заранее (60 общих сцен), но надо посчитать его **по кадрам**,
а не по сценам: если 60 общих сцен покрывают 90 % валидационных кадров — это другая
ситуация, чем если 5 %.

### F11.3. Главный тест: mAP с разбиением по перекрытию сцен

Самая информативная проверка — не доля утечки, а её **эффект**:
```
mAP_leaky  = mAP по val-запросам, чья сцена встречается в train
mAP_clean  = mAP по val-запросам, чьей сцены в train нет
```
**Стоп-сигнал: mAP_leaky − mAP_clean > 0,10.** Если разрыв велик, наша честная mAP
завышена относительно того, что будет на новых точках съёмки, ровно в пропорции
доли «протекающих» запросов.

### F11.4. Числа из литературы: сколько стоит перекрытие сцен

Прямое измерение есть в arXiv:1805.06086 (*An Evaluation of Deep CNN Baselines for
Scene-Independent Person Re-Identification*). Их определение: «For scene-independent person
ReID, there must be **no overlap in camera view, environment, or people** between the
training and testing sets». Замеры (MobileNet, 128×64, тест — Market1501Test):

| режим | Rank-1 | mAP |
|---|---|---|
| scene-dependent (train = Market1501Train) | **73,6 %** | **0,45** |
| scene-independent (train = LargeSetTrainSize4, 46 423 кадра) | **49,3 %** | **0,23** |
| scene-independent, крупнейший train (84 080 кадров) | 55,1 % | 0,27 |

Авторы формулируют прямо: «a **staggering ~30 % Rank-1 accuracy difference**» между
сценозависимым и сценонезависимым режимами; даже с 84 тыс. кадров разрыв остаётся ~20 п.п.

**Это самая важная цифра всего раздела для нашего проекта:** переход от «те же сцены» к
«другие сцены» стоит **20–30 п.п. Rank-1 и примерно вдвое mAP** на person re-id. Наши
60 общих сцен означают, что честная валидация всё ещё частично сценозависима, и реальная
цифра на новых точках съёмки будет ниже измеренной.

Практическое следствие: если заказчику важно работать на **новых** камерах, надо построить
третий сплит — `val-newscene` (только те идентичности, чьи сцены не встречаются в train) —
и репортить обе цифры. Даже если запросов там останется 100–200 (σ вырастет до
0,0134·√(832/150) ≈ 0,032), одно число «mAP на новых сценах» ценнее, чем его отсутствие.

косинусные сходства, 10 мин на разбиение метрики по сценам.
