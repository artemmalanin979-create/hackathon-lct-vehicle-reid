# Структура галереи: проверенные надбавки к k-reciprocal

Исследовательская записка, 2026-09-16. Прочитаны `BRIEF.md` и `context-errors.md`; модели и данные проекта не запускались. Таблицы сверены по тексту PDF и визуально. Все разности ниже — **абсолютные процентные пункты**, не относительный процент. Нужный нам результат — улучшение относительно уже работающего k-reciprocal (KR), а не относительно голого эмбеддинга.

**Основной результат:** у graph/diffusion есть недорогие варианты без обучения и `camera_id`, но проверенные надбавки к KR существенно меньше требуемых +10,6 п.п. Ни один из найденных результатов не измеряет наш AP@10. Мой порядок коротких проверок: diffusion → graph propagation → ECN; DBA/αQE — дешёвый контроль с высоким риском ухудшить первые места.

## Вариант GCR без camera_id: полезное уточнение

В работе **Graph Convolution Based Efficient Re-Ranking for Visual Retrieval** стандартная строка `GCR` использует и глобальный, и cross-camera граф. Её нельзя переносить целиком при отсутствии `camera_id`. Есть отдельная абляция **`GCR w/o Cross`**: Market **94,6 mAP**, Duke **89,4**, тогда как полный GCR **94,7 / 89,7** (Table IV, PDF p.8). По сравнению с BoT+KR из Table I (**94,2 / 89,1**) это соответствует **+0,4 / +0,3 п.п.**; это сравнение строк двух таблиц одной статьи, не отдельная прямая строка Table IV. Небольшая внутренняя разница R1 полного GCR между Table I и IV (96,1/96,0 на Market) дополнительно советует не придавать десятым долям чрезмерную точность. [S4]

GCR — резервная реализация пункта 2, если её проще подключить; его `w/o Cross` полезнее нам, чем более красивые числа с камерным графом. При ограниченном дне я бы не делал одновременно GNN и GCR: проверить один, другой оставить резервом.

## Ограничения переноса и единый протокол

- Все приведённые validation-таблицы измеряют **полный mAP**, не AP@10; CityFlow private test — mAP@100. Снижение R1 при росте полного mAP особенно опасно в нашей задаче, хотя само по себе не доказывает снижение AP@10.
- Работать с тем же замороженным набором OSNet-AIN@208. Размер CNN остаётся **8,4 MB**, число извлечений признаков не растёт; добавляется только постобработка. Реальное время extraction и rerank замерить раздельно по правилам исходного benchmark, ничего не переносить между измеряемыми этапами ради оценки.
- Заранее зафиксировать dev/контрольные IDs и число вариантов. Победителя по dev один раз оценить на контрольных IDs; парные интервалы строить по ID, а не по многим зависимым кадрам одной машины. Массовый поиск сотен k/α по одному сплиту легко повторит неудачный перенос diffusion из [S1].
- Если разрешён только отдельный запрос, строить gallery graph и прикреплять запрос, не рассчитывать на другие запросы. Если пакетная transduction разрешена, можно включать весь query+gallery, но одинаково для всех методов. Размер 750 сам по себе не гарантирует хорошо восстановимый граф: важны количество снимков каждой машины и чистота ближайших соседей.
- На наших взаимных двойниках уже известна слабость KR; альтернативная формула соседства не создаёт отсутствующие визуальные признаки. Ожидание большого скачка на этой группе необоснованно. Значения **+0,17…+2,9** выше — результаты чужих задач, **не прогноз нашего прироста**. Для планирования разумнее считать успехом воспроизводимый небольшой плюс; полученными свидетельствами нельзя обосновать **0,694→0,800** только сменой rerank.
- Произвольное транзитивное замыкание connected components не предлагается: одна ложная связь склеит визуальных двойников. Diffusion/GNN сохраняют веса и ограниченную глубину, что позволяет проверить силу распространения; безопасность от ложных связей всё равно не гарантируется.
