## 1. Результат и границы достоверности

Готов офлайн-модуль [reid_metrics.py](reid_metrics.py), работающий на NumPy и стандартной библиотеке Python. Он считает mAP, Rank-1/5, mINP, precision, recall, F1, TNR, трапецеидальную AUC-PR и отдельно ступенчатую площадь PR. Сохранены ручные оракулы, тесты, исходники внешних реализаций и доказательства проверок.

- **37/37 тестов прошли**, включая перебор **247** конфигураций галереи до семи элементов.
- **15/15 намеренно сломанных вариантов обнаружены assertions**; ошибок исполнения при мутационных прогонах — 0.
- **200** матриц сверены с настоящими Python-функциями fast-reid и torchreid; расхождения mAP ≤5.56×10⁻¹⁷, mINP ≤2.78×10⁻¹⁷. Для CMC расхождение ≤2.65×10⁻⁸ связано с float32 у внешних реализаций.
- **600** сверок отказов с отдельным медленным оракулом на прямом подсчёте и рациональной арифметике: ошибка ≤2.23×10⁻¹⁶.
- Случайные scores: **mAP=0.0812604** при аналитическом ожидании **0.0806049**, отклонение 0.69 стандартной ошибки среднего.

Это независимый проверенный расчёт **при явно заданных соглашениях**. Совпадение с эталоном организатора пока проверить невозможно: скрипта и закрытой разметки нет. Исполнение MATLAB и Cython не заявляется. Числа выше характеризуют проверки вычислителя, а не качество обученной модели.

## 2. Протокол: сначала допустимая галерея

Для запроса q известны идентичность yq и камера cq; у элемента g — yg и cg. `scores[q,g]` — близость, больше означает лучше. В режиме расстояния меньше означает лучше. Все формулы ниже используют ранги **с единицы после удаления исключений**, без ограничения top-10.

### 2.1. Две разные маски камеры

**Market-протокол:** исключается `yg == yq AND cg == cq`. Неверные идентичности той же камеры остаются отрицательными кандидатами. Это непосредственно видно в проверенных [fast-reid, `eval_market1501`](https://github.com/JDAI-CV/fast-reid/blob/7ed6240e2cb5e56e5ccd61744a3045f24ea7e62d/fastreid/evaluation/rank.py#L91) и [torchreid, `eval_market1501`](https://github.com/KaiyangZhou/deep-person-reid/blob/6b8fe56638d81c36b7872e8e41efe18232335f2f/torchreid/metrics/rank.py#L86).

**Полностью кросс-камерная галерея:** исключается любое `cg == cq`, включая неверные идентичности. Это отдельное возможное прочтение ТЗ, а не правило Market-1501. Например, same-camera N перед cross-camera P даёт AP=1/2 при первой маске и AP=1 при второй. Поэтому параметр `camera_policy` обязателен: `market` или `all_same_camera`.

Дополнительно исключаются:

- `gallery_junk[g]`: непригодный элемент для всех запросов;
- `exclude_mask[q,g]`: любая известная организатору причина исключения пары;
- при передаче `query_frames` и `gallery_frames` — совпадение **камеры и номера кадра**. Одинаковые номера кадров разных камер не считаются одним кадром. Для глобальных image_id или более сложных правил можно передать готовую маску.

Junk удаляется из рангов и знаменателей precision; он не становится отрицательным примером. Авторская [страница Market-1501](https://zheng-lab-anu.github.io/Project/project_reid.html) описывает good/junk-разметку и нулевое влияние junk на оценку. В доступном [MATLAB `evaluation.m`](https://github.com/zhunzhong07/person-re-ranking/blob/ca27f37dd88b27ee1f9dbc5668a9d0f45989ca71/evaluation/utils/evaluation.m) `-1` исключается явно; в функциях Python выше этой проверки нет. В частности, [загрузчик Market-1501 torchreid](https://github.com/KaiyangZhou/deep-person-reid/blob/master/torchreid/data/datasets/image/market1501.py) отбрасывает `pid == -1` до оценки. Наш универсальный API не приписывает числу −1 специального смысла: нужна явная маска.

Дедупликации по идентичности, усреднения по камерам, объединения кадров в треки и CUHK03 sampling здесь нет. Каждый допустимый снимок — отдельный элемент галереи. При использовании только camera_id невозможно восстановить исключение одинакового кадра среди разных объектов: frame/image IDs или готовая маска необходимы. Маски на основании истинных ID используются **оценщиком**, не являются доступным модели способом отбора кандидатов.

### 2.2. Три класса запросов

Пусть Dq — оставшаяся галерея, Gq={g∈Dq: yg=yq}, Mq=|Gq|.

| Статус | Смысл | Ранжирование | Отказы в нашем временном протоколе |
|---|---|---|---|
| `known` | Mq>0 | Участвует | Положительный запрос |
| `unknown` | Истинный ID отсутствует в исходной галерее, `known_absent=True` | Исключён | Отрицательный запрос для TNR |
| `filtered_positive` | ID был в исходной галерее, но все его верные элементы исключены | Исключён | Исключён, с отдельным счётчиком |

Последний случай включает «верные есть только на своей камере». AP делила бы на ноль, последнего верного ранга для INP нет; превращать это в неудачный поиск неправильно **в протоколе оценки валидных ReID-запросов**. Python-реализации выше пропускают любой запрос без оставшихся положительных. Его исключение также из отказов — наше явное временное соглашение: источники закрытого ReID не определяют для него F1/TNR. Оно не позволяет незаметно повысить TNR, переименовав неудобные известные запросы в неизвестные.

`known_absent` здесь — полная булева разметка отсутствия ID **до фильтрации**, а не confidence модели и не флаг «возможно отсутствует». Противоречие между флагом и ID вызывает `ValueError` в обе стороны. Для неизвестных нужны реальные различные ID; общий служебный ID, совпадающий с галерейным, не создаёт TP.

Фраза ТЗ «mAP по всем запросам» не разрешает однозначно вопрос отрицательных запросов. Основное наше число усредняется по V={q:Mq>0}; количество исключённых обязательно возвращается. Нулевая AP для неизвестных с делением на все Q — возможная **иная** метрика, которую надо согласовать, а не молча подставить.

## 3. Точные определения метрик ранжирования

### 3.1. AP и mAP

После фильтрации и сортировки обозначим relq(r)∈{0,1}; \(C_q(r)=\sum_{\ell=1}^{r}rel_q(\ell)\), то есть число верных до позиции r включительно. Эквивалентно, r₁<…<rM — позиции всех верных снимков. Precision на позиции r равна Cq(r)/r.

Для используемой fast-reid/torchreid ступенчатой AP:

\[
AP_q^{step}=\frac{1}{M_q}\sum_{r=1}^{|D_q|}rel_q(r)\frac{C_q(r)}r
=\frac1{M_q}\sum_{j=1}^{M_q}\frac{j}{r_j},
\qquad mAP=\frac1{|V|}\sum_{q\in V}AP_q.
\]

Единица среднего — **запрос**, не идентичность, не положительная пара, не камера. Формула соответствует [исходнику torchreid](https://github.com/KaiyangZhou/deep-person-reid/blob/6b8fe56638d81c36b7872e8e41efe18232335f2f/torchreid/metrics/rank.py#L126). Наличие нескольких верных снимков влияет на каждое слагаемое; нельзя заменить AP reciprocal rank первого совпадения.

**Классический MATLAB-вариант Market-1501** использует трапеции между precision/recall соседних обработанных позиций. Проверен [авторский `compute_AP.m`](https://github.com/zhunzhong07/person-re-ranking/blob/ca27f37dd88b27ee1f9dbc5668a9d0f45989ca71/evaluation/utils/compute_AP.m), опубликованный в репозитории Zhong/Zheng et al.; файл сохранён локально. Точная эквивалентная формула:

\[
AP_q^{MATLAB}=\frac1{M_q}\sum_{j=1}^{M_q}\frac12
\left[p_j^-+\frac{j}{r_j}\right],\quad
p_j^-=\begin{cases}1,&r_j=1,\\(j-1)/(r_j-1),&r_j>1.\end{cases}
\]

Это не 11-point AP и не интерполяция по огибающей precision. Примеры, выведенные из рангов:

| Допустимый список | AP step | AP MATLAB |
|---|---:|---:|
| P | 1 | 1 |
| N,P | 1/2 | 1/4 |
| N,P,N,P,P | 8/15 | 73/180 |
| P,N,N,N,N,P | 2/3 | 19/30 |

Для одинаковой галереи и валидного запроса **наш вывод из этих формул**:

\[
AP^{step}-AP^{MATLAB}=\frac1{2M}\sum_{j:r_j>1}\frac{r_j-j}{r_j(r_j-1)}\in[0,1/4].
\]

Верхняя граница достигается на одном P на rank 2: разница **25 процентных пунктов**. Нельзя сравнивать две AP-формулы как одно число. В API доступны `ap_method="step"` и `"market_matlab"`.

**Отдельное отличие знаменателя:** сохранённая MATLAB-обёртка [evaluation.m](https://github.com/zhunzhong07/person-re-ranking/blob/ca27f37dd88b27ee1f9dbc5668a9d0f45989ca71/evaluation/utils/evaluation.m) заменяет NaN AP на 0 и делит на число всех запросов. Python пропускает невалидные. На штатном benchmark с положительными у каждого запроса это отличие незаметно. При доле валидных α вариант «остальным 0» даёт α·mAP_valid. **Наш `market_matlab` переключает только интегрирование AP**, сохраняя заявленный пропуск невалидных; это не полная эмуляция MATLAB-обёртки.

### 3.2. CMC Rank-k

\[
CMC_q(k)=\mathbf1\{\min_j r_j\le k\},\qquad
Rank\text{-}k=\frac1{|V|}\sum_{q\in V}CMC_q(k).
\]

Успех — хотя бы одно верное совпадение среди первых k допустимых **снимков**. Несколько совпадений не дают несколько успехов: кумулятивная сумма обрезается сверху единицей. Это реализовано в [fast-reid](https://github.com/JDAI-CV/fast-reid/blob/7ed6240e2cb5e56e5ccd61744a3045f24ea7e62d/fastreid/evaluation/rank.py#L122). На P,N,N,N,N,P Rank-1=Rank-5=1, хотя recall@5=1/2. Это разные величины.

Если |Dq|<k, проверяется вся Dq: любой валидный такой запрос имеет Rank-k=1. При V=∅ результат `None`. Режим CUHK03 в тех же библиотеках случайно выбирает по одному снимку на identity; его CMC нельзя смешивать с приведённым Market-протоколом.

### 3.3. mINP

Первоисточник: Mang Ye, Jianbing Shen, Gaojie Lin, Tao Xiang, Ling Shao, Steven C. H. Hoi, **Deep Learning for Person Re-identification: A Survey and Outlook**, arXiv:2001.04193, §4.1, формулы (6)–(7), опубликовано также в TPAMI, DOI 10.1109/TPAMI.2021.3054775. [Статья с формулами](https://arxiv.org/pdf/2001.04193).

\[
R_q^{hard}=\max_j r_j,\quad NP_q=\frac{R_q^{hard}-M_q}{R_q^{hard}},\quad
INP_q=1-NP_q=\frac{M_q}{R_q^{hard}},\quad
mINP=\frac1{|V|}\sum_{q\in V}INP_q.
\]

Это precision на позиции **последнего** верного: насколько много ложных результатов надо просмотреть, чтобы найти все верные. При фиксированном M ложные элементы после последнего верного не влияют; перед ним уменьшают INP. При M=1 INP=1/r и совпадает с AP step. Если первые M мест верны, INP=1; минимум при последнем верном на конце списка равен M/|Dq|. M=0 означает неопределённость и пропуск, не ноль.

Например, для положительных на ranks 1 и 6: AP step=2/3, INP=1/3. mINP оценивает ранжирование известных запросов; абсолютные scores и неизвестные запросы на него не влияют. Поэтому утверждение ТЗ про «mINP или AUC-PR» не делает mINP проверкой качества отказов.

## 4. Отказы: F1 и TNR

Обозначения: zq=1 у `known`, zq=0 у `unknown`; K=Σzq, U=Σ(1−zq). Для непустой Dq: g*q — первый кандидат, sq=max score. aq(t)=1, если Dq непуста и sq≥t. Пустая Dq всегда даёт отказ, в том числе при t=−∞. Для distance используется min и сравнение ≤t.

Общие формулы:

\[
Precision=\frac{TP}{TP+FP},\quad Recall=\frac{TP}{TP+FN},\quad
F1=\frac{2TP}{2TP+FP+FN}.
\]

Это стандартные определения, включая отличие micro-подсчёта от усреднения отдельных F1: [документация F1 scikit-learn](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.f1_score.html). ТЗ не определяет единицу TP/FP. В модуле обязательный `refusal_mode` выбирает одну из следующих **явных операционализаций**; универсальный стандарт ReID-F1 здесь не выдумывается.

### 4.1. `presence`: обнаружение наличия совпадения

TP=Σza; FP=Σ(1−z)a; TN=Σ(1−z)(1−a); FN=Σz(1−a).

Это обычная бинарная матрица: четыре непересекающихся класса запросов. Принятый запрос с совпадением в галерее считается TP даже при неправильной выданной идентичности. Такой F1 измеряет обнаружение наличия, а не правильность сопоставления. На двух известных запросах с исключительно неверными top1 он может равняться **1**.

### 4.2. `top1`: правильная выданная идентичность

bq=1, если g*q имеет истинный ID запроса. TP=Σza b; FP=Σa−TP; FN=K−TP. Число `tn_unknown`=Σ(1−z)(1−a).

| Запрос / ответ | TP | FP | FN | TN_unknown |
|---|---:|---:|---:|---:|
| Известный, верный принят | 1 | 0 | 0 | 0 |
| Известный, неверный принят | 0 | 1 | 1 | 0 |
| Известный, отказ | 0 | 0 | 1 | 0 |
| Неизвестный, любой принят | 0 | 1 | 0 | 0 |
| Неизвестный, отказ | 0 | 0 | 0 | 1 |

Неправильная идентичность — одновременно ложная выдача и пропуск истинной. Это подсчёт ошибок сопоставления, **не четыре непересекающиеся клетки бинарной матрицы запросов**. `TP+FP+FN+TN_unknown` может превышать число запросов. Разделение пороговой ошибки поиска известного объекта и выдачи кандидатов для неизвестного согласуется с [определениями открытой идентификации NIST](https://pages.nist.gov/frvt/html/frvt1N.html); изложенная F1-агрегация — наш явно выбранный вариант, не приписывается NIST.

### 4.3. `pairwise`: список принятых снимков

Для каждой допустимой пары (q,g): yqg=1[yg=yq], aqg(t)=1[scoreqg≥t].

TP=Σyqg aqg; FP=Σ(1−yqg)aqg; FN=Σyqg(1−aqg). Это micro precision/recall/F1 по **всем допустимым парам**. Вариант соответствует буквальному списку принятых кандидатов, когда каждый снимок оценивается отдельно; общие правила micro-подсчёта описаны в [документации F1](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.f1_score.html).

Здесь принимаются все пары выше порога без top-N. Политика «если максимум выше порога, вернуть N кандидатов, включая лежащих ниже него», дедупликация по ID и усреднение F1 по запросам дадут другие ответы. Такие соглашения ТЗ пока не уточняет.

### 4.4. TNR — всегда по неизвестным запросам

\[
TNR(t)=\frac{\sum_{q:z_q=0}\mathbf1\{ответ_q(t)=\varnothing\}}{U}
=1-FPIR(t).
\]

NIST определяет FPIR как долю поисков без истинного соответствия, которые выдают хотя бы одного кандидата выше порога: [FRTE 1:N](https://pages.nist.gov/frvt/html/frvt1N.html). В наших режимах пустота ответа определяется одним и тем же максимумом допустимых scores. **Парные TN не используются в TNR**: тысячи верно отвергнутых неверных снимков не компенсируют одну ложную непустую выдачу неизвестному запросу.

На ручном H12 при t=.5: presence даёт TP/FP/TN/FN=2/1/1/1 и F1=2/3; top1 даёт TP/FP/FN=1/2/2 и F1=1/3. В обоих случаях TNR=1/2. При отказе всем известным F1=0; отказ всем неизвестным даёт TNR=1. Нужны оба вида запросов.

Нулевой знаменатель возвращает `None`/JSON `null`: нет неизвестных → TNR=None; нет положительных → recall и AUC-PR=None; нет принятых → precision=None; `2TP+FP+FN=0` → F1=None. При наличии положительных и отказе всем F1=0, даже если precision неопределена. Это выбранное соглашение; scikit-learn по умолчанию в некоторых таких случаях возвращает 0 с предупреждением. Неопределённость не скрывается как успешная метрика.

## 5. AUC по precision–recall

Кривая строится по **непорогованным scores**, перебором всех различных порогов. Сохранены конкретные точки, TP/FP и пороги; одинаковые scores принимаются целой группой. Принципы threshold sweep, уникальных порогов и начальной точки P=1,R=0 описаны в [документации precision_recall_curve](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.precision_recall_curve.html).

| Режим | Событие, score, правильность | Знаменатель recall |
|---|---|---|
| presence | Один непустой запрос; max score; истинное наличие ID | K известных запросов |
| top1 | Одна выдаваемая идентичность; max score; правильность top1 | **Все K известных**, включая те, где top1 неверен |
| pairwise | Каждая допустимая пара; score пары; равенство ID | Число всех допустимых положительных пар |

Неизвестные входят как отрицательные события, а не теряются при усреднении AP по известным. В top1 максимальная полнота равна закрытому Rank-1 на тех же известных запросах; она может быть <1. Площадь считается на достижимом диапазоне, остаток до R=1 вносит ноль. **Не нормируем на число только правильных top1**: иначе плохая идентификация получит завышенную полноту. Это обобщённая кривая идентификации, не результат простого `precision_recall_curve(top1_correct, max_score)`.

При обходе порогов от высокого к низкому имеем точки (Ri,Pi), R0=0,P0=1:

\[
AUC\text{-}PR_{trapezoid}=\sum_i(R_i-R_{i-1})\frac{P_i+P_{i-1}}2,
\qquad AP_{PR,step}=\sum_i(R_i-R_{i-1})P_i.
\]

Это разные площади: [average_precision_score](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.average_precision_score.html) прямо отделяет non-interpolated AP от интегрирования трапециями; [auc](https://scikit-learn.org/1.0/modules/generated/sklearn.metrics.auc.html) определяет трапецеидальный интеграл. Мы возвращаем обе: `auc_pr` — явно **trapezoid**, также `auc_pr_trapezoid`; `ap_pr_step` — ступенчатая.

Примеры: P,N,P с разными scores → step=5/6, trapezoid=19/24. Одна группа ничьих P,N → step=1/2, trapezoid=3/4; перестановка внутри группы не меняет PR. Для одной группы с долей положительных π трапеции дают (1+π)/2 вместо step=π: разница может приближаться к **0.5** при редких положительных. Это свойство выбранного интегрирования и начальной точки; высокая такая AUC сама по себе не означает хорошее разделение.

В H12 presence AUC-PR=55/72, step=29/36; top1 обе площади=1/3 и максимальный recall=1/3. mAP по запросам и глобальная PR-площадь по парам также не равны: первая усредняет отдельные ранжирования, вторая зависит от общего масштаба scores между запросами.

## 6. Ничьи, полнота списка, пустые входы

Сортировка стабильна: при равных scores меньший исходный индекс галереи идёт первым. Можно передать уникальные `gallery_keys`; тогда второй ключ — их порядок. Он сохраняет результат при перестановке столбцов вместе с метаданными. Истинная релевантность не используется для разрешения ничьих. Обычный `np.argsort` в рассмотренных внешних исходниках не запрашивает стабильность; [NumPy](https://numpy.org/doc/stable/reference/generated/numpy.argsort.html) документирует различие режимов.

При шести равных scores и единственном P: AP step и INP могут принимать значения от 1/6 до 1, Rank-1 и Rank-5 — 0 или 1. Средняя AP при равномерно случайном месте P равна H₆/6=49/120. Наш модуль не выдаёт это математическое ожидание за фактически выбранный стабильный порядок; если организатор усредняет ничьи, потребуется другой протокол.

Пустая галерея: ранжирование неопределено; неизвестные запросы корректно получают отказ, TNR=1. Пустая выборка: все агрегаты без знаменателя `None`. Валидный единственный запрос считается обычным образом. `NaN`/∞ в scores, несогласованные формы, невалидные ID и противоречивая разметка отвергаются; ±∞ разрешены только как пороги режимов «принять всё/отказать всем».

ТЗ просит `submission.csv` с top-10 и отдельно embeddings. **Полный mAP/mINP из top-10 не восстановить.** Например, единственный P на rank 11 имеет AP step=INP=1/11; top-10 не содержит ни одного P. API требует полную матрицу и вычисляет полный список; нельзя выдавать mAP@10 за полный mAP. Rank-5 также должен считаться после исключений: десяти сырых кандидатов может не хватить, если первые элементы являются junk.

## 7. Реализация и запуск

Проверенное окружение: **Python 3.13.13, NumPy 2.2.6**. Другие зависимости отсутствуют; сеть для метрик, CLI и всех повторных проверок не нужна. [requirements.txt](requirements.txt) описывает зависимость; это не комплект офлайн-wheel, NumPy должен уже быть установлен.

```bash
python -B -m unittest -v test_metrics
python -B verify.py
python -B reid_metrics.py example.npz --threshold 0.5 \
  --camera-policy market --refusal-mode top1 --output example_result.json
```

Из Python:

```python
from reid_metrics import evaluate, scores_from_embeddings

result = evaluate(
    scores, query_ids, gallery_ids, query_cameras, gallery_cameras,
    known_absent, threshold=threshold,
    camera_policy="market", refusal_mode="top1",
    ap_method="step", include_rankings=True,
)
# Альтернатива матрице: cosine или negative_l2, обе возвращают близость.
# scores = scores_from_embeddings(query_embeddings, gallery_embeddings, "cosine")
```

NPZ содержит `scores[Q,G]`, `query_ids[Q]`, `gallery_ids[G]`, `query_cameras[Q]`, `gallery_cameras[G]`, `known_absent[Q]` (bool). Дополнительные ключи: `gallery_keys[G]`, `gallery_junk[G]`, `exclude_mask[Q,G]`, `query_frames[Q]`, `gallery_frames[G]`. ID — целые числа или строки. Для CLI нужны обычные числовые/строковые массивы, не object/pickle. В API поддерживаются массивы и Python-списки.

JSON содержит `protocol`, `counts`, `ranking`, `refusal`, `per_query`. Для каждого запроса доступны статус, число допустимых кандидатов, положительные ранги, AP/INP, лучший индекс и score. В CLI сохраняется также весь допустимый порядок. `None` сериализуется как `null`; бесконечные пороги — строки `+inf`/`-inf`.

[example.npz](example.npz) и [example_result.json](example_result.json) — ручной H12: mAP=mINP=2/3; Rank-1=1/3; Rank-5=1; top1 precision=recall=F1=AUC-PR=1/3; TNR=1/2. **Порог 0.5 здесь иллюстративный**, не подобран для реальной модели. Данных для содержательного выбора командного порога не предоставлено. Его следует обосновать на отдельной размеченной валидации с неизвестными запросами и заморозить перед тестом; `validate_identity_split` помогает проверить непересечение ID, но без train IDs сам evaluator этого проверить не может.

Стоимость: полный вход O(QG); сортировка ранжирования O(QG log G). Для pairwise PR дополнительно хранятся и глобально сортируются допустимые пары, O(E log E) времени и O(E) памяти. Это эталонный расчёт для сверки; потоковый расчёт для миллионной галереи не реализован.

### 8.2. Независимость проверок

1. Ручные точные дроби проверяют сами значения, не внутренние функции.
2. Полный перебор 247 малых конфигураций сравнивает средние с комбинаторным выводом.
3. [verify.py](verify.py) извлекает AST **настоящих** `eval_market1501` из сохранённых исходников, без изменения тела; запускает 200 общих входов. Никакой установки Torch/Cython нет. ### 8.3. Случайный уровень

Для N допустимых кандидатов, M>0 положительных и равномерного случайного порядка, HN=Σᵣ₌₁…N 1/r, самостоятельно выведено:

\[
E[AP^{step}]=\frac{H_N}{N}+\frac{(M-1)(N-H_N)}{N(N-1)}\quad(N>1),
\]
\[
E[Rank\text{-}k]=1-\frac{\binom{N-M}{\min(k,N)}}{\binom N{\min(k,N)}},\qquad
E[INP]=\sum_{r=M}^N\frac Mr\frac{\binom{r-1}{M-1}}{\binom NM}.
\]

Первая формула следует из условного ожидаемого числа положительных до позиции r при положительном на ней: (r−1)(M−1)/(N−1). Это вывод из определения AP, **не цитата по памяти**; детали и особый N=M=1 находятся в `ORACLES.md`.

Monte Carlo: seed=20260915, 5000 запросов, N=100, M=4, независимые uniform[0,1) scores. До прогона выбран допуск 5 стандартных ошибок среднего и грубая граница mAP<0.15.

| Метрика | Теоретическое среднее | Получено | Отклонение в стандартных ошибках |
|---|---:|---:|---:|
| mAP | 0.0806049 | 0.0812604 | +0.69 |
| Rank-1 | 0.0400000 | 0.0408000 | +0.29 |
| Rank-5 | 0.1881249 | 0.1838000 | −0.79 |
| mINP | 0.0525548 | 0.0528925 | +1.25 |

Случайная AP на конечной галерее **не равна просто M/N**; ожидать ровно 0.04 здесь неверно. Сам случайный тест не ловит обратную сортировку: распределение случайной перестановки остаётся равномерным. Поэтому ручные направленные примеры обязательны. Полные числа, допуски и окружение — [verification_results.json](verification_results.json).

## 9. Где наше число может разойтись с чужим расчётом и почему

| Причина | Размер/пример расхождения |
|---|---|
| AP step против MATLAB | До 0.25 при одинаковой валидной галерее; N,P: 0.5 против 0.25 |
| Невалидные запросы включены как нули | mAP_all=α·mAP_valid; один идеальный из трёх: 1/3 против 1 |
| Полная same-camera маска против same-ID AND same-camera | Same-camera N перед cross-camera P: 1 против 1/2 |
| Не удалён same-camera P/junk | Меняются положительные ранги и знаменатели; H06 вместо 1/2 даёт AP=5/6 при снятии маски камеры |
| Разные веса запросов | H07: правильное 17/24 против взвешенного 11/18 |
| Ничьи/порядок галереи/квантизация | Один P среди шести равных: AP от 1/6 до 1 |
| Кадры, дубликаты, tracklets, image-ID вместо vehicle-ID | Меняется само множество положительных; универсальной малой границы нет |
| CMC вместо recall@k или CUHK03 sampling | На P,N,N,N,N,P Rank-5=1, recall@5=1/2 |
| presence F1 против правильной идентификации | Неверные top1 всех известных: F1=1 против 0 |
| Pairwise F1/TNR вместо query-level TNR | Число отрицательных пар может скрыть ложные выдачи; TNR нужен по отказам запросам |
| AP PR против трапеций | P,N с равными scores: 1/2 против 3/4; при редких positives разница приближается к 1/2 |
| PR по запросам против глобальных пар | Меняются единица учёта, доля positives, веса и требования к калибровке scores |
| Порог ≥ против >; distance против similarity | Все совпавшие с порогом переходят в другой класс; обратная сортировка меняет всю выдачу |
| Top-10 вместо полной галереи | P на rank 11: полный AP=INP=1/11; в top-10 положительных нет |
| Float32, float64, CPU/Cython, reranking/ANN | В нашей общей проверке CMC расходилась на 2.65×10⁻⁸; изменение порядка близких scores может дать намного больше |
| Доли против процентов | Наше 0.8 соответствует 80%; перед сравнением нужен единый масштаб |
| Другая доля неизвестных/размер галереи | PR/F1 и распределение максимума отрицательных scores меняются даже без изменения модели |

При появлении эталона сначала совпадают входные ID/порядок/маски и `protocol`, затем сравниваются статусы запросов, ранги всех положительных, AP/INP, счётчики и PR-точки. Совпадение только итоговой mAP недостаточно: ошибки могут компенсироваться.

[compare_results.py](compare_results.py) сравнивает JSON нашей схемы рекурсивно, включая протокол, счётчики и `per_query`, и показывает первые различия. Float допускает абсолютную погрешность 1e−7; целые счётчики сравниваются точно. Код возврата 0 означает совпадение, 1 — расхождение. Выход организатора понадобится привести адаптером к этой схеме; адаптер невозможно написать без его формата.

```bash
python -B compare_results.py example_result.json example_result.json
# После появления и адаптации эталона:
# python -B compare_results.py our_result.json organizer_result.json --atol 1e-7
```

Компаратор отдельно проверен на одинаковых результатах, допустимой float-погрешности, изменённом положительном ранге и несовпадающем протоколе: [comparison_check.json](comparison_check.json).

## 10. Чего мы не знаем и должны спросить у организатора

1. **Какие данные дадут для воспроизведения оценки?** По §5 camera_id участникам не передаётся, тестовый vehicle_id тоже. Нужны размеченная валидация с camera/frame IDs или точные query–gallery маски; иначе кросс-камерную mAP независимо не пересчитать.
2. Что именно означает «исключить одну камеру»: все такие снимки или только same-ID AND same-camera? Как исключаются один кадр, один bbox, near-duplicates, junk и треки?
3. Какая AP: precision@positive ranks, MATLAB trapezoid, интерполированная AP? Можно получить точную версию/commit эталона и фиксированные ожидаемые ответы на H02/H03?
4. Кто входит в среднее «по всем запросам»? Каковы правила для истинно отсутствующих и для запросов, чьи положительные исчезли только после фильтрации? Последние нельзя молча подменять отрицательными.
5. В ТЗ open-set означает также новые относительно обучения ID. Будут ли **неизвестные относительно галереи**? Как строятся gallery/query split, доля неизвестных и флаг отсутствия? Гарантия двух камер на ID сама этого не определяет.
6. TP/FP/FN для F1 считаются по парам снимков, уникальным ID, query presence, верному top1 или успеху в top-N? Неправильный принятый ID известного запроса даёт FP и FN? F1 micro или среднее по запросам?
7. Сервис принимает каждый score≥t или проверяет только максимум и затем возвращает top-N? N фиксировано? Как обрабатываются дубликаты одного автомобиля в списке?
8. AUC-PR строится по каким score/label и с каким знаменателем recall? Какая интерполяция, группировка ничьих, начальная точка и обработка недостижимого recall? Чем обоснована альтернатива mINP, которая неизвестные не оценивает?
9. Будет полная галерея восстановлена из embeddings или оценка ограничена `submission.csv` top-10? Если усечение есть, как определены знаменатели AP@10 и отсутствующий последний позитив для INP?
10. Как разрешаются ничьи и фиксируется порядок галереи? Какая ориентация score, точность вычислений и правило равенства порогу? Какой результат нужен при пустых знаменателях?
