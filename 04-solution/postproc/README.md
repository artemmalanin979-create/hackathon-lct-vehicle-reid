# Постобработка: что берём и чего не берём

GPU не было, поэтому волна качества началась с того, что можно выжать из готовых весов
без обучения. Полный разбор — [`REPORT.md`](REPORT.md).

## Рекомендация

**Берём переранжирование (k-reciprocal, k1=6, k2=3, λ=0,3). Не берём усреднение по
входам и вторую модель.**

| Конфигурация | mAP | Rank-1 | Время извлечения | Веса |
|---|---:|---:|---:|---:|
| база | 0,657 | 0,631 | 43,8 мс/об | 8,4 МБ |
| **+ переранжирование (6,3,0,3)** | **0,694** | **0,663** | **43,8 мс/об** | **8,4 МБ** |
| + переранжирование с параметрами из статьи | 0,667 | 0,632 | 43,8 мс/об | 8,4 МБ |
| усреднение по трём входам + переранжирование | 0,695 | 0,667 | 133,9 мс/об | 8,4 МБ |
| со второй моделью + переранжирование | 0,700 | 0,681 | 294,9 мс/об | 107,5 МБ |

Почему именно так:

**Переранжирование не трогает то, что меряет организатор.** ТЗ (разд. 7) меряет время
формирования признака — «изображение → вектор». Переранжирование работает **после**, на
готовых векторах: те же 43,8 мс на объект, та же модель 8,4 МБ. Вся его цена — 0,55 с на
полный прогон 1110 запросов против 750 объектов галереи.

**Усреднение по входам не окупается.** Поверх переранжирования оно добавляет +0,0016 mAP
и **утраивает** время извлечения — три прохода сети вместо одного. На чужом железе
соотношение сохранится. Плохой размен.

**Вторая модель провалилась на наших данных, и это полезное знание.** `fast-reid`
R50-IBN, обученный на VeRi-776, даёт здесь **mAP 0,238** против 0,657 у OSNet — заявленные
для него 81,9 на VeRi-776 не переносятся вообще. Доменный разрыв между китайским
академическим датасетом и московскими камерами оказался решающим. В ансамбле он даёт
+0,005, но ценой учетверения времени, +99 МБ весов, зависимости от torch и лицензионной
серой зоны (веса обучены на данных «только для исследований»).

## Цена переподгонки — названа числом

Разбор бейзлайна давал 0,7041, но параметры там подбирались на том же сплите, где
измерялись. Здесь подбор и проверка разделены: **все** свободные величины выбирались на
отдельном протоколе, собранном из `train_fit` (295 идентичностей, структура зеркалит
валидацию), и только потом конфигурации один раз прогонялись на нетронутой валидации.

| | mAP |
|---|---:|
| оптимум, подобранный на той же валидации (переподгонка) | 0,6946 |
| параметры, подобранные честно на других идентичностях | **0,6937** |
| «всё вместе», подобранное на валидации | 0,7068 |
| «всё вместе» честно | 0,6952 |

**Цена переподгонки — 0,001–0,012 mAP.** Из заявленного разбором прироста +0,048 честно
переносится **+0,037**. Дополнительный контроль: валидация делилась пополам по
идентичностям, подбор на одной половине и объявление на другой — потери 0,004 и 0,012.

Подбор на чужих идентичностях дал (6, 3, 0,3). В более широкой сетке на валидации
максимум у (4, 4, 0,3): 0,6946 против 0,6937 — разница 0,0009 mAP.
Параметры этих двух оптимумов различаются; источник — `out/grid_val_base.json`
и `out/final_val.json`.

## Что это меняет в решении

1. В пакетный прогон добавляется переранжирование на объединении «запросы + галерея»,
   топ-10 строится по возрастанию переранжированной дистанции.
2. **Порог отказа придётся перекалибровать.** Шкала скоров после переранжирования другая
   (смесь жаккардовой дистанции и нормированного косинуса), и порог 0,5496, подобранный
   на косинусах, к ней неприменим. До перекалибровки переранжирование идёт в
   `submission.csv`, но не в `candidates.csv`.

## Запуск

Команды ниже проверяют входы до ML-импортов: при отсутствии файлов выводят
их пути, предыдущий шаг подготовки и завершаются с кодом **2**.
Частичный прогон требует только выбранные наборы/варианты; закэшированные
варианты, которые извлечение пропускает, не требуют исходных изображений.

Из каталога `04-solution/postproc`, интерпретатор — `.venv/bin/python` проекта.
Шаги 3 и далее читают векторы из `out/`; `*.npy` в git не лежат, поэтому этап
начинается с их получения. Веса — `../service/model/...onnx`
(`sh model/fetch_model.sh` в каталоге сервиса), путь можно переопределить
переменной `REID_MODEL_PATH`, каталог данных — `REID_DATA_DIR`.

```bash
PY=../../.venv/bin/python

# 1. базовые векторы валидации: их считает бейзлайн (см. baseline/README.md, шаг 1),
#    здесь они каноничны — s03 сверяет с ними свой препроцессинг
cp ../baseline/out/val_query.npy ../baseline/out/val_gallery.npy out/
cp ../baseline/out/val_query.ids ../baseline/out/val_gallery.ids out/

# 2. сверка бейзлайна и обоих наборов параметров переранжирования -> out/s01_verify_baseline.json
$PY scripts/s01_verify_baseline.py

# 3. векторы TTA-вариантов. Полный прогон (оба набора, 6 вариантов) — это ~22 тыс.
#    объектов; для шага 6 достаточно трёх вариантов валидации:
$PY scripts/s03_extract.py --sets val --variants 208,208f,256

# 4. файлы выбранных комбинаций TTA/TTA2 (то звено, которого ждёт шаг 6)
$PY scripts/s05b_make_tta_vectors.py --sets val

# 5. финальная таблица восьми конфигураций -> out/final_val.json
$PY scripts/s06_final_val.py
```

Проверено прогоном: все восемь конфигураций `final_val.json` воспроизводятся
по этим командам без расхождений (отличается только поле времени
`rerank_seconds`).

Что этими командами **не** воспроизводится:

- `s05_tta.py`, `s04_grid.py`, `s06_halves.py`, `s09_timing.py` требуют полного
  прогона шага 3 (оба набора и все шесть вариантов) — сам подбор и тайминги
  заново мы не переигрывали;
- `s07_fastreid_extract.py` и `s08_fusion.py` требуют отдельного окружения с
  torch и весов fast-reid (`fastreid_job/`, в репозитории их нет) — сравнение со
  второй моделью из чистого клона не воспроизводится.

## Ограничение, о котором стоит помнить

Переранжирование квадратично по памяти: на 7440 объектах рабочие матрицы занимают
около 1,8 ГБ, практический потолок обычной реализации — порядка 10⁴ объектов. В нашей
задаче это не проблема (тест — 1110 запросов и 750 объектов галереи), но для
демонстрации масштабирования на 10⁶ (тай-брейк из разд. 10 ТЗ) понадобится разреженный
вариант.
