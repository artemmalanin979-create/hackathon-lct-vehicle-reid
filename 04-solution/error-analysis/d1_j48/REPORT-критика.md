# job_87 — независимая проверка разбора ошибок d1_j48

**Вердикт: числовую часть и конкретные примеры можно нести на защиту. Безусловный тезис «наши ошибки мягкие» не одобряю.** Защищаемая формулировка — «на этой валидации сократилось число ошибок первого места, а первая верная пара среди оставшихся ошибок чаще находится ближе к началу списка». Разбиение на единственную главную причину следует представлять как субъективную разметку одного наблюдателя: в независимой проверке совпали **20/32 метки, 62,5%**, κ = **0,4435**. Подтверждения подгонки состава выборки не найдено.

Это **допуск материала с обязательным уточнением интерпретации**, а не опровержение качества модели. Сам исходный REPORT содержит существенные честные оговорки: визуальные гипотезы, пересекающиеся признаки, отсутствие второго человека, повторно используемая валидация, различие presence и правильной идентификации. Их нужно сохранить в выступлении. Отдельный недостаток проверяемости: существующий `verify_numeric.py.txt` пропускает **8 из 13** выполненных мутаций. Это не означает, что текущие восемь чисел неверны: текущие числа пересчитаны и подтверждены.

**Независимая визуальная разметка.**

До чтения индивидуальных авторских меток выбраны **32 из 64**, равновероятно без возвращения, seed **8700923**. Заранее известны агрегаты причин из BRIEF. Собственные листы содержат query, лучшую правильную пару и top-1; авторские категории и числовые ранги скрыты. Для q60 и q252 до сравнения дополнительно просмотрены полные кадры. Определение T было более строгим: почти одинаковая видимая форма/окраска кандидата при отсутствии более сильной видимой помехи. Это отличается от более широкого авторского «модель/класс/цвет/ливрея» и объясняет часть расхождений.

Все 32 решения были записаны до раскрытия авторских меток. **Ограничение моей процедуры:** в B07 вручную ошибочно записан `q933` вместо напечатанного на листе `q833`. Из-за этого проверка набора индексов при создании hash-манифеста упала, а следующее чтение авторских меток уже состоялось. После раскрытия исправлен только индекс B07 по листу; ни одна первичная/вторичная метка и ни одна заметка не переписаны. Исходный TSV сохранён дословно. Следовательно, временная фиксация текстов предшествует раскрытию, а отдельный hash-манифест — **нет**; полностью безупречной слепой процедурой это не называю.

Итого **пойманы 5/13; пропущены 8/13**. Ошибка индексации в BRIEF сформулирована двусмысленно: штатный оценщик уже делает `flatnonzero(...) + 1`, поэтому переход к единичному рангу сам по себе правилен; ошибками являются дополнительное `+1` либо последующее `−1` без смены трактовки. Оба случая выполнены.

Причина выживших мутаций конкретна: проверяльщик сравнивает `positive_ranks`, но **не сравнивает производный `first_positive_rank` с его первым элементом**, и не валидирует `derived_stats.json`/медианы и доли в тексте. В `write_report.py.txt` таблица глубины и медианы вообще внесены литералами. Следовательно, успешная проверка mAP/Rank-1 не гарантирует правильной подписи «медиана 5». На текущих неизменённых данных подпись верна — это установлено отдельным пересчётом данного аудита. [Полные результаты](evidence/mutations.json), [логи](mutations.log).

**В каких постановках «мягкость» не держится.**

1. **Все запросы с парой.** На всех 832 known-query медиана первого положительного ранга — **1 у всех трёх моделей**. По этой метрике сравнительное преимущество исчезает. Средний ранг при этом лучше: 5,558 против 11,725 и 11,376. Для 278 запросов без пары «ранг правильного ответа» не определён: их нельзя молча заменить нулями. Если явно ввести для отсутствия пары `+∞` и считать все 1110, медианы будут 1/2/2 для d1_j48/OSNet/OSNet+KR; это уже другой искусственно расширенный показатель.

2. **AP как цена ошибки.** Средний AP на 224 остаточных ошибках — **0,24715**, медианный AP — **0,2**. Средняя потеря относительно AP=1 составляет **0,75285**. Эти ошибки дают **0,20269 пункта** из общего дефицита mAP до единицы **0,22591**, то есть **89,72%** потерь. Поэтому «верная машина на пятом месте» не значит «почти без потери основной метрики». Есть также **71** запрос с правильным первым местом, но AP<1: анализ только top-1 не охватывает все ошибки ранжирования.

3. **Первые десять кандидатов как конечный продукт.** Даже в списке допустимых кандидатов **49/832** query имеют первую верную пару дальше десяти; среди этих ошибок медиана **23**, а не 5. При реальной семантике `submission.csv`, **сначала raw top-10, затем market-фильтр**, без единой допустимой верной пары остаются **55/832 = 6,61%** query; по крайней мере часть релевантных пар не попала у **89/832**. mAP@10 = **0,7684546**. Шесть дополнительных промахов относительно 49 появляются из-за порядка усечения и фильтрации. Их нельзя исключать как «нет ранга в коротком списке».

4. **Остаток после просмотра 20 кандидатов.** Среди собственных промахов с рангом >20 средний ранг у d1_j48 **102,62** на 29 случаях; у OSNet **88,78** на 89; у OSNet+KR **94,92** на 79. Здесь направление сравнения тяжести остаточных ошибок **обращается**. Их медианы — 48, 48 и 54: преимущество относительно сырой OSNet исчезает. Это условные популяции разного состава, поэтому результат не опровергает общий выигрыш модели; он опровергает универсальность фразы «остаточные ошибки всегда мягче». Уже при промахе top-10 средний ранг final 66,49 против 65,75/63,11.

5. **Надёжность принятой идентификации.** В режиме `top1` 84 принятия с существующей парой, но чужим ID, добавляются к 60 принятиям без пары: **144 ошибочных идентификации из 666 принятий = 21,62%**. Precision **0,7838**, recall **0,6274**, F1 **0,696929**. Близость правильной машины в выдаче не исправляет уже выданный неверный top-1. Это пересчёт при прежнем пороге и market-фильтре, не измерение нефильтрованного HTTP API и не рекомендация нового порога.

6. **Статистически устойчивое преимущество AP именно на финальных остаточных ошибках.** На одних и тех же 224 final-ошибках средний AP final 0,24715, OSNet 0,21742, OSNet+KR 0,22289. Разница положительна, но парный bootstrap по **102 vehicle_id**, 10 000 повторов, даёт 95% интервалы для разницы **[−0,00183; +0,06059]** и **[−0,01654; +0,06179]**. На этой постановке нельзя заявить уверенно положительный прирост AP остаточных ошибок. Это исследовательский анализ выбранной по final модели подгруппы, а не новый holdout.

При этом честные альтернативные сравнения подтверждают **общий** прогресс. На общих ошибках обеих моделей медиана final **5 против 11** у OSNet (203 query) и **5 против 12** у OSNet+KR (202 query). Средний AP там 0,2230 против 0,1469 и 0,2266 против 0,1446. Значит, эффект не объясняется только сравнением разных наборов ошибок. На всех 832 known-query разница mAP **+0,11752 / +0,08043**, а парный bootstrap по 284 vehicle_id даёт положительные 95% интервалы **[+0,09205; +0,14485] / [+0,05464; +0,10769]**. Эти интервалы описывают данную валидацию и не учитывают историю выбора гиперпараметров.

Если усреднить AP по всем 1110 query с явным нулём для отсутствующей пары, получаются **0,58022 / 0,49213 / 0,51993**: преимущество тоже сохраняется. Переопределение знаменателя не делает отсутствующую пару ранжирующей ошибкой по штатному протоколу.
