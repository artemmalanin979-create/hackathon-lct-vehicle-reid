## Первое честное число

Проверочный сплит, 1110 запросов против 750 объектов галереи, совпадения с камеры
запроса исключены — как это делает организатор.

| Прогон | mAP | Rank-1 | Rank-5 | mINP |
|---|---:|---:|---:|---:|
| **OSNet-AIN, честный кросс-камерный** | **0.657** | **0.631** | 0.787 | 0.607 |
| По усечению до 10 кандидатов (как в `submission.csv`) | 0.645 | 0.631 | 0.787 | — |
| Случайные векторы | 0.0099 | 0.0024 | 0.0112 | 0.0071 |
| — аналитическое ожидание для случайных | 0.0103 | 0.0020 | 0.0099 | 0.0081 |
| **Без исключения совпадений с камеры запроса** | 0.812 | **0.971** | 0.988 | 0.637 |

### Знаменатель: 832, а не 1110

**mAP 0,657 — это среднее по 832 запросам**, у которых в галерее есть кросс-камерная
пара. Остальные 278 запросов сплита — те, у которых пары нет вовсе (материал для режима
отказа), и в среднее ранжирования они не входят.

При другом соглашении того же контура — усреднять по **всем** 1110 запросам, считая
AP = 0 там, где верного ответа нет, — число будет **0,492**.

Мы берём первое: штрафовать нулём запрос, правильный ответ на который «никого», в
задаче ранжирования бессмысленно, и это стандартное соглашение Re-ID. Но обе ветки
называем: разница 0,164 больше любой нашей абляции, и число без знаменателя непроверяемо.

Что из них имеет в виду организатор — вопрос A3, ответа пока нет.

### Две строки таблицы, которые важнее самого числа

**Случайные векторы легли на аналитическое ожидание** (0,0099 против 0,0103). Значит ни
сплит, ни контур не подыгрывают: когда мерить нечего, метрика это показывает.

**Запоминание точки съёмки даёт +34 пункта Rank-1** (0,631 → 0,971) и +15,6 пункта mAP.
То, что предсказал разбор данных, подтвердилось числом.

### Это число занижено

Независимый разбор показал: **теми же весами, без обучения** доступно
**mAP 0,704 и Rank-1 0,682** — переранжирование плюс усреднение по нескольким входам.
Вариант с параметрами прямо из статьи даёт +0,010 без переизвлечения векторов.

## Модель

OSNet-AIN x1.0 из Open Model Zoo, лицензия MIT, **8,4 МБ**, вход 208×208, выход — вектор
512. sha256 `4aaad3e5db648618b0df3d2ff21c61323985ff9e50194c3d2edd4fb87c92d91f`.

Препроцессинг выяснен по источникам, а не угадан: карточка модели, `model.yml`,
`accuracy-check.yml` и инспекция самого графа. Первый узел сети —
`InstanceNormalization`, то есть модель сама нормирует вход, и внешняя нормализация на
результат не влияет — проверено: косинус между вектором при входе 0..255 и при 0..1
равен единице. А вот порядок каналов влияет (0,83–0,96), поэтому RGB зафиксирован.

## Скорость на CPU

| Показатель | Значение |
|---|---|
| Полный конвейер, батч 1 | **39–64 мс** на объект (разброс трёх прогонов: 54,2 / 56,7 / 64,1) |
| — из них декодирование кадра 1920×1080 | 13,4 мс |
| — из них сеть | 19,2 мс |
| Сеть при батче 32 | 20,3 мс на объект |

Первая версия отчёта называла 64,4 мс. Это **верхняя точка разброса**, то есть
характеристика загрузки машины, а не решения — на ней в тот момент работали соседние
процессы. Финальные замеры организатор делает сам на своём железе.

Что здесь действительно важно: **батч не быстрее одиночных объектов** (19,2 против
20,3 мс на чистой сети) — onnxruntime и так занимает все ядра, а треть времени уходит на
декодирование кадра. Оптимизировать надо ввод, а не сеть.

## Проверка порядка строк в `embeddings.npy`

Ошибка в порядке строк тихо обесценивает всю сдачу, поэтому проверялось скриптом, а не
глазами: для 24 контрольных позиций (включая границы блоков 0/1109/1110/1859) вектор
пересчитан **заново, свежей сессией модели**, и сравнён со строкой файла. Во всех
случаях косинус в своей позиции равен единице, и ближайшая ко всему файлу строка — сама
эта позиция.

## Абляция по номерной пластине — и почему она ничего не доказала

Первая версия закрывала нижние 30 % кропа, давала −0,108 mAP, и мы сделали вывод, что
решение не держится на пластине. **Вывод был неправомерным.** Независимый разбор закрыл
полосы той же площади в других местах:

| Что закрыто (30 % площади) | mAP | Δ |
|---|---:|---:|
| ничего | 0.657 | — |
| низ — там пластина | 0.549 | −0.108 |
| **верх** — крыша и стёкла, пластины там нет | 0.576 | −0.081 |
| **середина** — пластины там нет | 0.505 | **−0.151** |

Полоса посередине, где пластины нет ни у одного кропа, стоит **дороже** низа. Значит
−0,108 — это цена потери 30 % пикселей, а не цена пластины. С контролем равной площади
вклад пластины выходит около **−0,027**.

Вдобавок на 24 просмотренных кропах у четырёх пластина оказалась **выше** линии среза:
городские камеры снимают сверху и сбоку, и нижние 30 % кропа — это часто бампер и
асфальт, а не номер.

Честная абляция требует контроля равной площади и маски, которая действительно накрывает
пластину. Это задача следующей волны, и она обязательная: на ней держится наш
единственный довод против обвинения в использовании признаков государственного знака.

## Режим отказа — черновой порог, уже заменённый

Порог 0,349 выбран как максимум F1 на валидации. Результат честно неудачный: **TNR
0,144**, а на выданном тесте он отсекает **3 запроса из 1110**.

Независимый разбор добавил к этому две вещи. Во-первых, порог не переносится: на
валидации он отказывает в 3,7 % случаев, на тесте — в 0,27 %, в 13,7 раза реже. Отсюда
оценка, что доля запросов без пары в тесте около **1 %**, а не 25 %, заложенных в наш
сплит. Во-вторых, `precision 0,775` относится к решению «у запроса есть пара» по одному
top-1, а точность самих строк `candidates.csv` — **0,089** (0,052 после камерного
фильтра организатора).

Порог с тех пор перекалиброван — см. [`../refusal/`](../refusal/): TNR поднят до 0,698
ценой 0,134 F1, по правилу, зафиксированному до просмотра результатов. Оценку «около 1 %»
там ещё предстоит учесть.

## Запуск

Только через `.venv/bin/python` проекта. Векторы (`*.npy`) в репозиторий не кладём —
воспроизводятся прогоном; каталог данных берётся из `REID_DATA_DIR` (по умолчанию
`data/` репозитория), путь к весам задаётся аргументом `--model`.

Шаг 0 — веса, если их ещё нет в рабочем дереве (`*.onnx` исключён `.gitignore`):

```bash
(cd 04-solution/service && sh model/fetch_model.sh)
```

Дальше — из каталога `04-solution/baseline`. У `extract_embeddings.py` все четыре
аргумента обязательны (`--csv`, `--images-dir`, `--model`, `--out`), а `run_eval.py`
ждёт восемь файлов `out/*.npy`: базовый вариант и три абляционных для query и gallery.

```bash
PY=../../.venv/bin/python
M=../service/model/osnet_ain_x1_0_vehicle_reid.onnx
IMG=../../data/images

# 1. векторы валидации: база (+ .ids) и три абляции
for part in query gallery; do
  $PY scripts/extract_embeddings.py --csv ../split/files/val_$part.csv --images-dir $IMG \
      --model $M --out out/val_$part.npy --ids-out out/val_$part.ids
  $PY scripts/extract_embeddings.py --csv ../split/files/val_$part.csv --images-dir $IMG \
      --model $M --mask-bottom 0.30 --out out/val_${part}_mask30.npy
  $PY scripts/extract_embeddings.py --csv ../split/files/val_$part.csv --images-dir $IMG \
      --model $M --grayscale --out out/val_${part}_gray.npy
  $PY scripts/extract_embeddings.py --csv ../split/files/val_$part.csv --images-dir $IMG \
      --model $M --mask-bottom 0.30 --grayscale --out out/val_${part}_mask30gray.npy
done

# 2. все прогоны таблицы через общий измерительный контур -> out/metrics_summary.json
$PY scripts/run_eval.py

# 3. векторы выданного теста -> сдаваемые артефакты -> проверка порядка строк
for part in query gallery; do
  $PY scripts/extract_embeddings.py --csv ../../data/test_$part.csv --images-dir $IMG \
      --model $M --out out/test_$part.npy --ids-out out/test_$part.ids
done
$PY scripts/make_submission.py --threshold 0.34921352213815304
$PY scripts/check_embeddings_order.py
```

Порог в шаге 3 — полное значение из `out/metrics_summary.json`
(`_threshold_selection.t_star`); округление до 0.349214 даёт другой
`candidates.csv`, поэтому в команде стоит всё число целиком.
