## 1. Абляция «низ на 30 %» не измеряет вклад номерного знака (тяжёлая)

Заявлено: `mask30 → mAP 0.5486 (−0.108)`, и это названо «верхней оценкой» вклада пластины
с обоснованием «полоса в 30 % много шире пластины». На этом числе держится единственный
довод, что решение не нарушает запрет ТЗ/README на использование признаков ГРЗ.

**Вход.** Те же кропы, та же серая заливка (127) полосы в 30 % высоты кропа до resize, всё
остальное идентично `subject/scripts/extract_embeddings.py`. Меняется только положение
полосы. Извлечение — `work/extract_bands.py`, метрики — `work/eval_bands.py`.
Контроль: мой вариант «низ» побайтово воспроизводит их `val_*_mask30.npy`
(`max|diff| = 0.0`), то есть сравниваю ровно с их абляцией.

**Полученное:**

| Что закрыто (30 % площади кропа) | mAP | Δ к 0.6566 | Rank-1 |
|---|---:|---:|---:|
| ничего | 0.6566 | — | 0.6310 |
| **низ** (их абляция, там пластина) | 0.5486 | **−0.1080** | 0.5024 |
| **верх** (крыша/стёкла, пластины там нет никогда) | 0.5760 | **−0.0805** | 0.5517 |
| **середина** (пластины там нет никогда) | 0.5054 | **−0.1512** | 0.4639 |

**Верное.** −0.108 — это в основном цена потери 30 % пикселей и сдвига статистик
`InstanceNormalization` на входе, а не цена пластины. Полоса в середине, где пластины нет
ни у одного кропа, стоит **дороже** (−0.151), чем полоса внизу. Всё, что эти данные дают
как оценку вклада пластины, — разность с контролем равной площади, то есть
−0.108 − (−0.081) ≈ **−0.027** против верхней полосы, и **отрицательная** величина против
средней. Тезис «ни один вариант не падает к случайному уровню, значит решение не держится
на пластине» из −0.108 не следует: он одинаково следует из −0.081 при закрытии крыши.

Вторая часть: **полоса часто не накрывает пластину вообще.** Картинки —
`work/pics/crops24_band.png` (24 случайных кропа, красным обведены закрашиваемые нижние
30 %) и `work/pics/crops208_mask30.png` (кроп после `--mask-bottom 0.3`). В выборке из 24
у **4** (#9, #10, #15, #21) размытая пластина целиком выше линии и абляцией не тронута,
ещё примерно у 6 задета частично — ракурсы сверху/сбоку, типичные для городских камер,
уводят передок и корму вверх кадра. То есть для заметной доли объектов эксперимент
«закрыли низ» пластину не трогает и про неё ничего не говорит.

**Почему.** Чтобы читать падение метрики как вклад признака, нужно, чтобы вмешательство
(а) действительно удаляло признак и (б) не удаляло больше ничего сопоставимого по цене.
Здесь не выполнено ни (а) — у части кропов пластина остаётся, ни (б) — контроль равной
площади без пластины стоит столько же или дороже. Нужен либо детектор пластины, либо
хотя бы сравнение с контрольной полосой — второе сделано выше и вердикт снимает.

Воспроизведение:
```
python work/extract_bands.py   # ~3.5 мин, пишет work/emb/val_{query,gallery}_{btm30,top30,mid30}.npy
python work/eval_bands.py
```

## 2. Заявленные 0.6566 / 0.6310 занижают то, что дают эти же веса без обучения (тяжёлая)

Прямой ответ на вопрос задания. Да, способ есть, и он не в препроцессинге.

**Вход.** Те же веса, обучения нет. Две независимые добавки: (а) TTA — усреднение
L2-нормированных векторов четырёх входов (208, 256, 288, горизонтальное отражение 208);
(б) k-reciprocal re-ranking (Zhong et al., 2017) поверх готовых векторов, чистая
пост-обработка. Метрики — их же контуром, `camera_policy=market`, полная галерея.

**Полученное:**

| Прогон | mAP | Rank-1 | mAP@10 |
|---|---:|---:|---:|
| Заявленное (их вектора) | 0.6566 | 0.6310 | 0.6451 |
| только re-ranking, параметры из статьи (k1=20, k2=6, λ=0.3), **на их же файлах `.npy`** | 0.6666 | 0.6322 | 0.6549 |
| только re-ranking, k1=6, k2=3, λ=0.3, на их же файлах | 0.6937 | 0.6635 | 0.6834 |
| только TTA (208+256+288+flip) | 0.6678 | 0.6442 | 0.6568 |
| **TTA + re-ranking (k1=6, k2=3, λ=0.3)** | **0.7041** | **0.6815** | **0.6934** |
| для сравнения: DBA по галерее, k=2 | 0.6778 | 0.6550 | 0.6669 |

**Верное.** Тот же контур, тот же сплит, те же веса, ноль обучения: **mAP 0.7041
(+0.0476), Rank-1 0.6815 (+0.0505), mAP@10 0.6934 (+0.0483)**. Для масштаба: это примерно
половина того, что в отчёте стоит обесцвечивание кропа (−0.087), и в десять раз больше
зазора между `market` и `all_same_camera` (0.0046) — величина не косметическая.

Честная оговорка: k1/k2/λ подобраны на том же val, на котором меряю, поэтому 0.7041 —
оптимистичная граница. Но плато широкое (k1 6..8, k2 2..4, λ=0.3 дают 0.688…0.704), а
неподобранный вариант с параметрами прямо из статьи даёт +0.010 без всякой настройки и
вообще без переизвлечения векторов — достаточно `subject/out/val_*.npy`.

Воспроизведение:
```
python work/postproc.py      # re-ranking/AQE/DBA на их векторах, ~15 с
python work/best_number.py   # сетка TTA+re-ranking, ~3 мин
```

## 3. mAP 0.6566 усреднён по 832 запросам, а не по 1110, и знаменатель не назван (существенная)

**Вход.** `subject/out/evalrun/base_market.json`, поле
`ranking_full_gallery.mAP_by_query_average`.

**Полученное.** Тот же самый прогон контура возвращает рядом обе ветки:

```
"mAP_by_query_average": { "valid_queries": 0.6565692724907637,
                          "all_queries_zero": 0.4921312024435274 },
"mAP_denominator": 832
```

В `out/metrics_summary.json` попадает только первая; в README/REPORT решения вторая не
упоминается ни разу. При этом заголовок таблицы в README — «Проверочный сплит, **1110
запросов** против 750 объектов галереи», а ТЗ (`context-tz.txt`, раздел «Критерии
оценки») формулирует основную метрику как «mAP по **всем запросам**».

**Верное.** 0.6566 — среднее AP по 832 запросам, у которых в галерее есть кросс-камерная
пара; 278 отказных запросов (25 % выборки, доля задана параметром сплита) из среднего
исключены. При другом соглашении того же контура число — 0.4921. Разница 0.164, то есть
больше любой абляции в отчёте.

**Почему.** Соглашение `valid_queries` само по себе стандартно для ReID и защитимо
(штрафовать нулём запрос, у которого правильный ответ — «никого», странно). Неверна
подача: отчёт специально настаивает, что по ветке усечения до топ-10 «обе ветки
приведены и их нельзя путать», а по ветке усреднения — молча берёт выгодную, не называя
знаменатель, под подписью «1110 запросов». Число без знаменателя не проверяемо, а
знаменатель здесь меняет его на четверть.

Воспроизведение:
```
python -c "import json;print(json.load(open('subject/out/evalrun/base_market.json'))['ranking_full_gallery'])"
```

## 4. Порог 0.349214 и TNR 0.144 не описывают сдаваемый `candidates.csv` (существенная)

Само число проверено и верно: мой независимый argmax F1 по событиям presence даёт
t = 0.34921352213815315 (тот же ивент, расхождение 1 ulp), F1 = 0.8671254632080466,
TNR = 0.14388489208633093 — совпадает до последнего знака (`work/verify_metrics.py`,
`work/threshold_check.py`). Неверно то, что из него следует.

**Вход.** `subject/artifacts/embeddings.npy`, `subject/out/val_*.npy`, тот же порог.
Скрипт `work/threshold_tradeoff.py`.

**Полученное.**

1. Перенос на тест не состоялся: тем же правилом «нет кандидата с cos ≥ t → отказ» на val
   отказ получают **41 запрос из 1110 (3.69 %)**, а на выданном тесте — **3 из 1110
   (0.27 %)**, в 13.7 раза реже. Из уравнения `0.1439·p + 0.0012·(1−p) = 0.0027` доля
   запросов без пары в тесте выходит ≈ **1 %** против заложенных в сплит **25 %**
   (оговорка: это верно, если отказные запросы теста распределены по скорам как
   сконструированные отказные val). Значит F1 = 0.8671, TNR = 0.1439, precision = 0.7748,
   recall = 0.9844, AUC-PR = 0.8876 посчитаны при априори 75/25, который выданный тест не
   подтверждает, и на закрытом тесте будут другими — в отчёте это не сказано.

2. Содержимое сдаваемого файла к заявленной точности отношения не имеет. `precision
   0.7748` — это точность решения «у запроса есть пара» по одному top-1. Точность самих
   принятых пар, то есть строк `candidates.csv`, на val при том же пороге:

   | что считаем | принято пар | верных | точность |
   |---|---:|---:|---:|
   | все пары ≥ t, как пишет `make_submission.py` | 20 685 | 1 845 | **0.089** |
   | то же после камерного фильтра организатора | 19 873 | 1 033 | **0.052** |

   На тесте файл содержит 22 393 строки на 1110 запросов — медиана 13 кандидатов на
   непустой запрос, максимум 118.

**Верное.** Порог, выбранный по argmax F1, ставит систему ровно в то положение, против
которого ТЗ вводит TNR («предотвращает ситуацию, когда решение всегда возвращает топ-1
кандидата»): принимается 95.2 % запросов. Компромисс на тех же векторах доступен и дёшев:

| порог | F1 | TNR | precision | recall | доля принятых |
|---:|---:|---:|---:|---:|---:|
| 0.3492 (их) | 0.8671 | 0.1439 | 0.7748 | 0.9844 | 0.9523 |
| 0.4500 | 0.8448 | 0.4317 | 0.8209 | 0.8702 | 0.7946 |
| 0.4803 | 0.8237 | **0.5000** | 0.8303 | 0.8173 | 0.7378 |
| 0.6000 | 0.6575 | **0.8201** | 0.8963 | 0.5192 | 0.4342 |

TNR 0.144 → 0.500 стоит 0.043 F1. Отчёт объясняет низкую TNR тем, что «максимум F1 тянет
порог к полноте», и откладывает калибровку в следующую волну; число выше показывает, что
выбор был между двумя точками одной кривой и цена смены точки известна.

# Что проверено и проблем не найдено

Перечень входов и того, что с ними сделано.

1. **Препроцессинг против первоисточника.** `model.yml` и `accuracy-check.yml` модели
   `vehicle-reid-0001` получены с raw.githubusercontent (WebFetch): вход `[1,3,208,208]`
   NCHW; аргументы конвертера — только `--reverse_input_channels`, без `mean_values` и
   `scale_values`; препроцессинг эталона — `resize 208×208, use_pillow: True,
   interpolation: BILINEAR`, aspect_ratio не задан, нормализации нет. Размер файла
   8 836 743 Б совпадает с манифестом. Код делает ровно это. `--reverse_input_channels`
   означает, что **исходный ONNX ждёт RGB** — выбор RGB верен.
2. **Порядок каналов и разрешение проверены метрикой, а не только косинусом**
   (`work/extract_variants.py`, `work/eval_variants.py`): BGR 0.5874, letterbox с
   сохранением пропорций 0.5521, 256 → 0.6497, 288 → 0.6292 против 0.6566 у базы. Все
   альтернативы хуже — выбор автора подтверждён.
3. **Соответствие векторов и строк — проверено полностью, а не выборочно.** Все 1860
   векторов теста переизвлечены моим кодом с кропом numpy-срезом `arr[y:y+h, x:x+w]`
   (не `PIL.crop`) и сверены с `artifacts/embeddings.npy` построчно: min cos =
   1.000000000, max|diff| = 7.8e-09, строк с cos < 0.9999 — ноль; у 200 случайных позиций
   ближайшая строка всего файла — своя (`work/recheck_test_vectors.py`). Аналогично
   переизвлечены оба val-сплита: `max|diff| = 0.0` с `subject/out/val_query.npy` и
   `val_gallery.npy`. Файлы `.ids` во всех четырёх случаях совпадают с порядком строк CSV.
4. **Кроп по bbox — глазами.** `work/pics/frames_bbox.png` (bbox нарисован на кадре) и
   `work/pics/crops208.png` (кроп как его видит сеть): `x, y, w, h` трактуются как
   левый-верхний угол + ширина/высота, оси не перепутаны, вырезается именно машина из
   аннотации. Все 11 416 кадров — 1920×1080, EXIF Orientation = 1 у всех (авто-поворота,
   который PIL не применяет, нет), ни одного bbox вне границ кадра и ни одного
   вырожденного — граничное поведение `PIL.crop` не задействовано.
5. **Метрики пересчитаны своей реализацией с нуля** (`work/verify_metrics.py`): market-
   фильтр, AP как среднее precision в позициях попаданий, mAP по запросам с ≥1 допущенным
   позитивом, top-10 по сырым скорам всей галереи с последующим фильтром. Получено
   0.6565692724907637 / 0.6310096153846154 / 0.6451091746794871, без исключения камеры
   0.8122072020105592 / 0.9711538461538461, случайные 0.009922260378380145, F1
   0.8671254632080466, TNR 0.14388489208633093 — совпадает с заявленным до последнего
   знака. Максимальное расхождение моего косинуса с контурным 6.7e-16.
6. **Контур применён детерминированно.** `run_eval.py` перезапущен на их же векторах:
   `metrics_summary.json` и все девять `evalrun/*.json` совпадают с приложенными
   **побайтово**.
7. **Честность применения сплита** (`work/check_split_use.py`): строки `val_query`,
   `val_gallery`, `train_fit` совпадают с `train.csv` по `x,y,w,h,vehicle_id,camera_id` —

8. **Политика исключения камеры применена как заявлено.** Прогон «без исключения» сделан

9. **Сдаваемые файлы против схемы `dataset-readme.md`** (`work/check_artifacts.py`):
   `embeddings.npy` — `(1860, 512)`, `float32`, конечные, L2-нормы с отклонением 6e-08,

   `query_id,gallery_id_1…gallery_id_10`, 1110 строк, порядок `query_id` как в CSV, 11
   колонок в каждой строке, ни одного `gallery_id` вне `test_gallery`, ни одного повтора
   внутри строки; `candidates.csv` — заголовок `query_id,gallery_id,confidence`, 22 393
   строки, 1107 запросов с кандидатами и 3 отказа. **Оба файла пересобраны из
   `embeddings.npy` — расхождений ноль**: те же топ-10, тот же порядок убывания, те же
   списки принятых, `confidence` совпадает с косинусом, ниже порога ничего не принято.
   Формально к схеме претензий нет; из мелочей — файлы записаны с CRLF (умолчание
   `csv.writer`), и «пустой ответ» реализован как отсутствие строк, что README допускает,
   но явно не фиксирует.
10. **Случайные векторы** воспроизведены (три seed, 0.0102 / 0.0097 / 0.0098, среднее
    0.00992) — вырожденный прогон действительно падает к нулю, сплит и контур не
    подыгрывают.
11. **Абляции сопоставимы по всему, кроме входа**: один и тот же вызов контура, один и тот
    же порог (на ранговые метрики он не влияет), меняются только `.npy`. Здесь претензий
    нет — претензия в п. 1 к интерпретации, а не к постановке.

Замечание вне предмета проверки: README сплита указывает 369 идентичностей в `val_query` и
294 в `val_gallery`; фактически в файлах 358 и 295. На числа baseline это не влияет
(валидные запросы 832 и `filtered_queries = 0` подтверждаются), но расхождение есть.
