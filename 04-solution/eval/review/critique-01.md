# Отчёт независимой проверки `subject/reid_metrics.py`

Дата: 2026-09-15. Проверялись: `subject/reid_metrics.py`, его тесты
`subject/test_metrics.py`, проверочный скрипт `subject/verify.py` (с
`subject/sources/*` и `subject/example.npz`), на соответствие ТЗ (разделы 8–9)
и критериям приёмки из задания.

Инструменты проверки лежат в `work/`:

| файл | что делает |
|---|---|
| `work/oracle.py` | независимый оракул на `Fraction`, написан с нуля по определениям (AP step, MATLAB-AP по `sources/compute_AP.m`, INP, CMC, PR-кривая с группировкой ничьих) |
| `work/fuzz.py` | дифференциальный фаззер: 6000 малых конфигураций, сравнение **всего** выхода `evaluate` с оракулом |
| `work/mutants.py` | мутационная проверка авторских тестов; выжившие мутанты пишутся в `work/mutant_*.py` |
| `work/demos.py` | воспроизводимые входы с неверными числами для каждого выжившего мутанта |
| `work/tz_checks.py` | проверки соответствия ТЗ §8–9 и критерию «случайного уровня» |
| `work/run/` | копия subject, в которой запускались авторские тесты и verify.py |

Запуск: `cd work && python3 -B fuzz.py && python3 -B mutants.py && python3 -B demos.py && python3 -B tz_checks.py`.

## Резюме

1. **Арифметических ошибок в самой реализации не найдено.** Независимый оракул
   на точных дробях, сравнение всего выходного словаря (включая `per_query`,
   `counts`, `refusal.pr_curve`), 6000 конфигураций с ничьими, junk,
   exclude_mask, frames, gallery_keys, режимом distance, порогами ровно равными
   оценкам, пустыми галереями — 0 расхождений.
2. **Главная находка — в другом: проверки автора слепы к целым классам поломок.**
   Утверждение автора «намеренно ломал реализацию — все поломки были пойманы»
   опровергнуто предъявлением: **8 поломок проходят весь `verify.py` целиком**
   (все 37 тестов, оба дифференциала, random-level, матрица из 15 авторских
   мутантов, CLI), ещё 2 проходят все 37 тестов. Среди них есть поломки,
   искажающие главную метрику ТЗ (mAP/Rank-1) и TNR. Код поломок и входы с
   неверными числами приложены (раздел «Поломки…» ниже).
3. **Несоответствие прикладному формату ТЗ §8:** метрика ранжирования считается
   только по полной галерее; посчитать метрику по сдаваемому артефакту
   (submission.csv = топ-10 кандидатов) код не умеет в принципе, а числа этих
   двух постановок расходятся (пример ниже: 0.0833 против 0).

## Находки (по убыванию тяжести)

### Н1. Тесты и verify.py автора не замечают поломок, искажающих mAP, Rank-1, TNR и выдаваемые пользователю поля

Это главная находка; полный разбор с кодом и входами — в разделе
«Поломки, которые тесты автора не ловят». Кратко: авторская система проверок
устроена так, что

- дифференциал ранжирования гоняется только на **непрерывных** случайных оценках
  (ничьих не бывает), similarity, market, без junk/keys/frames, CMC сверяется
  только в рангах 1 и 5;
- дифференциал режима отказа сравнивает **только скалярные поля** `refusal`
  (см. `slow_refusal` → `reference.items()`), т.е. `pr_curve`, `per_query` и
  `counts` не сверяются ни с чем и нигде;
- режим `score_kind="distance"` нигде, кроме одного unit-теста с двумя
  элементами, не проверяется, и этот тест сравнивает лишь избранные ключи;
- `gallery_keys` проверяются только на галереях из **двух** элементов и только
  **без** какой-либо фильтрации;
- мутационная матрица — это 15 заранее выбранных мутантов, и вывод «всё
  ловится» не переносится ни на один класс поломок вне этого списка.

Следствие: реализацию можно сломать так, что она будет отдавать неверные
главные метрики, а весь `verify.py` завершится с «PASS: 37 tests; 15 / 15
mutants detected».

### Н2. ТЗ §8: код не умеет считать метрику сдаваемого артефакта (топ-10), а числа расходятся

**Вход** (`work/tz_checks.py`, T1): 1 запрос, галерея из 12; единственное
верное совпадение имеет наименьшую оценку и стоит на ранге 12.

**Код выдаёт:** mAP = 0.083333, mINP = 0.083333 (по полной галерее,
`protocol.ranking_scope = "full_gallery"`; параметра усечения списка нет).

**Что требуется по ТЗ:** §8 определяет сдаваемый артефакт «submission.csv: …
первые 10 кандидатов по убыванию близости», и проверка организаторами идёт по
сданным артефактам эталонным скриптом. В сданном топ-10 этого запроса верного
совпадения **нет вообще**: AP по сданному списку = 0, mINP по усечённому списку
не определён (последнее совпадение не попало в список).

**Почему это находка:** число, которое печатает этот код, невозможно получить
из артефакта, который команда реально сдаёт, и наоборот. Для запросов, у
которых совпадения глубже 10-й позиции, самооценка по этому коду систематически
**завышена** относительно любой оценки по submission.csv (0.0833 против 0 в
примере). Режим «метрика по первым 10 кандидатам» в коде отсутствует как
функциональность, т.е. проверить соответствие собственного submission.csv
требованиям §8–9 этим инструментом нельзя. (Если эталонный скрипт организаторов
считает по эмбеддингам и полной галерее — расхождения нет; но ТЗ этого не
обещает, а сдаётся именно усечённый список.)

### Н3. Интерпретационные расхождения с §9 (документированы кодом, но решают другую задачу)

Не арифметические ошибки — выбор протокола задокументирован в `protocol` и
докстроке, — но при сдаче по ТЗ эти числа могут не совпасть с эталонными:

- **«mAP … по всем запросам» (§9).** Код усредняет AP только по valid-запросам
  (known с хотя бы одним допустимым совпадением). Вход (`tz_checks.py`, T5):
  2 запроса, один known с AP=1, один unknown. Код: mAP = 1.0
  (`num_valid_queries = 1`). Буквальное прочтение «по всем запросам» дало бы
  0.5. Выбор кода — стандарт Market-1501 (AP для запроса без позитивов не
  определён), нулями отброшенные запросы **не** подменяются, знаменатель
  честно публикуется — но эталонный скрипт организаторов может читать §9
  буквально.
- **Судьба «known-запроса, у которого все позитивы отфильтрованы»** (например,
  все совпадения сняты той же камерой): код выбрасывает его и из ранжирования,
  и из режима отказа (`filtered_positive_policy="drop"`), т.е. он не входит и в
  знаменатель TNR. По смыслу §9 («TNR — доля корректных отказов на запросах,
  для которых в галерее нет совпадения») такой запрос после кросс-камерного
  исключения фактически не имеет допустимого совпадения, и эталон может
  требовать от системы отказа на нём (т.е. включать его в знаменатель TNR).
  Число: вход `[[1.0]]`, qid=1, gid=1, камеры равны → код: TNR = None
  (unknown-запросов нет), запрос исчезает из refusal; альтернативное прочтение:
  знаменатель TNR = 1.
- **Применимость к данным ТЗ.** Обязательные входы `query_cameras`,
  `gallery_cameras`, `known_absent` в выдаваемых данных отсутствуют (§5:
  идентификатор камеры участникам не передаётся; в test.csv нет vehicle_id).
  Кросс-камерное исключение §9 участнику воспроизвести не из чего; инструмент
  применим только к собственной разметке своего сплита train с самодельными
  метками камер.

## Поломки, которые тесты автора не ловят

Методика: текстовые мутации `reid_metrics.py` (`work/mutants.py`), запуск
неизменённых авторских тестов против каждого мутанта, затем запуск **полного**
`verify.py` с подменённым модулем. Демонстрации неверных чисел —
`work/demos.py` (каждый вход умещается в одну строку). Код каждой поломки —
`work/mutant_<имя>.py`.

Статусы: **[ПОЛНЫЙ PASS]** = все 37 тестов И весь verify.py прошли;
**[37 ТЕСТОВ PASS]** = все 37 тестов прошли, verify.py см. оговорку.

### П1. [ПОЛНЫЙ PASS] `M1b_keys_inverse_perm` — обратная перестановка `gallery_keys` ломает ранжирование, mAP 1.0 → 0.5

Мутация: `tie_order = np.asarray(sorted(range(ng), key=...))` →
`np.argsort(...)` от того же выражения (классическая ошибка «перестановка
вместо обратной перестановки»).

Вход: 1 запрос (id 7), галерея `[8, 8, 7]`, все оценки равны 1.0,
`gallery_keys=["b","c","a"]`. Верно: ничья разрешается по возрастанию ключей →
порядок `[2, 0, 1]`, совпадение первое, **mAP = 1.0, Rank-1 = 1.0**. Мутант:
порядок `[1, 2, 0]`, **mAP = 0.5, Rank-1 = 0.0**.

Почему не ловится: оба теста на `gallery_keys` используют галерею из **двух**
элементов, а любая перестановка двух элементов совпадает со своей обратной
(демо печатает этот контрпример). В verify.py `gallery_keys` не встречаются ни
разу. Поломка искажает главную метрику ТЗ при полностью зелёном verify.py.

### П2. [37 ТЕСТОВ PASS; все поведенческие проверки verify.py PASS] `M1_keys_filter_mask` — при `gallery_keys` + фильтрации ранжируется не то множество объектов

Мутация: `candidates = tie_order[eligible[tie_order]]` →
`tie_order[eligible]` (маска допуска применена к переставленному массиву
позиционно — правдоподобный слип).

Вход: 1 запрос (id 7), галерея `[8, 7, 7]`, оценки `[5, 9, 1]`,
`gallery_junk=[False, True, False]`, `gallery_keys=["c","a","b"]`. Верно:
junk-объект 1 исключён, порядок `[0, 2]`, совпадение на ранге 2 → **mAP = 0.5,
Rank-1 = 0.0**. Мутант: ранжирует `[1, 0]` — **включает junk-объект** (и
объявляет его top-совпадением, `top_gallery_index=1`), **теряет допустимый
объект 2** → **mAP = 1.0, Rank-1 = 1.0** (лестно), нарушен сам принцип
исключений (критерий приёмки 2: исключённые объекты участвуют в расчёте).

Почему не ловится: keys-тесты автора — без фильтрации, тесты фильтрации — без
keys; при любом из «чистых» случаев мутант совпадает с оригиналом. В verify.py
это сочетание не встречается. Оговорка честности: полный verify.py на этом
мутанте падает, но только в `mutation_check` с `AssertionError: mutation
ties_reverse: source pattern changed` — это **сверка текста исходника с
шаблоном**, а не поведенческая проверка; все численные стадии
(37 тестов, differential_ranking, differential_refusal, random_level) проходят.

### П3. [ПОЛНЫЙ PASS] `M8_float32` — квантование оценок/порога во float32: mAP 0.5 → 1.0, TNR 1 → 0

Мутация: `utility, cutoff = raw * sign, threshold * sign` → то же с приведением
через `np.float32` (реалистичный вариант: считать полезности в float32 «для
скорости», ТЗ §4 сам предлагает float32-эмбеддинги, у которых косинусы
близких изображений различаются на ~1e-8).

Вход А: запрос id 1, галерея `[1, 2]`, оценки `[0.6, 0.6+2e-8]` — дистрактор
строго выше. Верно: **Rank-1 = 0.0, mAP = 0.5**. Мутант: во float32 оценки
схлопываются в ничью, побеждает порядок столбцов → **Rank-1 = 1.0, mAP = 1.0**
(лестно). Вход Б: unknown-запрос с оценкой 0.5 при пороге `0.5 + 6e-9`.
Верно: отказ, **TNR = 1, fp_unknown = 0**. Мутант: порог округлился к 0.5,
кандидат принят → **TNR = 0, fp_unknown = 1**.

Почему не ловится: все константы в тестах либо точны во float32 (0.5, целые),
либо не имеют соседей ближе 1e-3; дифференциалы verify.py используют целые
оценки (refusal) или непрерывные с зазорами ~1e-2 (ranking), где float32 не
меняет порядок. Проверен запуск полного verify.py: PASS целиком.

### П4. [ПОЛНЫЙ PASS] `M2_pr_thresholds_sign` — пороги PR-кривой при `score_kind="distance"` в чужой шкале

Мутация: убрано обратное преобразование `t * sign` списка
`refusal.pr_curve.thresholds`.

Вход: расстояния `[[1.0, 3.0]]`, id совпадает, `score_kind="distance"`,
порог 2.0. Верно: `thresholds = [None, 1.0]` (расстояние). Мутант:
`[None, -1.0]` — «порог-расстояние −1.0», значение вне области определения
меры. Именно по этой кривой по ТЗ §9 команда выбирает и защищает рабочий
порог; знак здесь — это выбор другого порога.

Почему не ловится: единственный тест на thresholds (`test_H14`) — similarity,
где `sign = 1`; дифференциал refusal сверяет только скаляры; в verify.py режим
distance не появляется вовсе. verify.py: PASS целиком.

### П5. [ПОЛНЫЙ PASS] `M3_top_score_sign` — `top_score` при distance отдаёт −расстояние

Мутация: `top_score=float(raw[i, best])` → `float(utility[i, best])`.

Вход: тот же, что П4. Верно: `top_score = 1.0` (исходное расстояние до лучшего
кандидата — это «числовая оценка уверенности» для candidates.csv из §8).
Мутант: `top_score = -1.0`.

Почему не ловится: ни один тест не смотрит на значение `top_score`; в
similarity-режиме мутант неотличим от оригинала, а distance в verify.py нет.
verify.py: PASS целиком.

### П6. [ПОЛНЫЙ PASS] Четыре поломки отчётных полей: `M4_eligible_count`, `M5_relevant_pairs`, `M6_positive_ranks_0based`, `M7_num_relevant`

| поломка | вход | верно | мутант |
|---|---|---|---|
| `eligible_count` = размер галереи, фильтрация игнорируется | q id 1, галерея `[1,1]`, камеры `[0,1]`, qcam 0, market | 1 | 2 |
| `counts.relevant_pairs` = число известных запросов | 1 запрос, 2 позитива из 3 объектов | 2 | 1 |
| `positive_ranks` с нуля | галерея `[2,1,3,1]`, оценки убывают | `[2, 4]` | `[1, 3]` (ранг «1» у второго объекта; ранга 0/«1-го» дважды по определению не бывает) |
| `num_relevant` = ранг последнего совпадения | тот же | 2 | 4 |

Почему не ловится: ни одно из этих полей не проверяется ни одним тестом и не
входит в сверяемые дифференциалом скаляры; CLI-проверка сверяет только то, что
`compare` **замечает изменение** `positive_ranks`, но не само значение. Все
четыре поломки прошли verify.py целиком. Это поля аудита и отладки
(§8: по ним команда собирает candidates.csv и объясняет метрики при защите) —
неверные значения уводят вниз по течению.

### П7. [37 ТЕСТОВ PASS; ловится только дифференциалом] `M9_accepted_strict` — строгий порог в `accepted`/TNR при нестрогом в tp/fp

Мутация: `>=` → `>` только в вычислении `accepted` (tp/fp остаются на `>=`).
Вход: unknown-запрос с оценкой ровно 0.5 при пороге 0.5. Верно: принят,
**TNR = 0, fp_unknown = 1**; мутант: **TNR = 1, fp_unknown = 0**, и fp=1 при
fp_unknown=0 — внутренне противоречивый отчёт. Все 37 тестов проходят
(`test_threshold_inclusive` проверяет только tp); ловит это **только**
`differential_refusal` в verify.py (целые оценки против порога 1.0). Т.е. кейс
«оценка unknown-запроса ровно на пороге» юнит-тестами не покрыт.

## Качество проверок автора (что заявлено vs что ловится)

Воспроизведено запуском: `verify.py` целиком PASS на оригинале — 37/37 тестов;
200 трайлов `differential_ranking` (макс. |Δ mAP| ~1e-16 к fastreid/torchreid);
600 сравнений `differential_refusal` с точным дробным оракулом; random-level;
15/15 авторских мутантов пойманы; 4 краевых кейса внешних реализаций; CLI.

В своей заявленной области дифференциалы честны и работают. Но область узка, и
формулировка «все поломки были пойманы» не выдерживает проверки: предъявлено
**8 поломок с полным PASS всего verify.py** (П1, П3–П6) и ещё 2 с PASS всех
37 тестов (П2, П7). Систематические слепые зоны: ничьи против внешних эталонов
(дифференциал ранжирования специально сгенерирован без ничьих), режим
distance, `gallery_keys` (в verify.py отсутствуют), сочетания
keys×фильтрация, поля `per_query`/`counts`/`pr_curve` (не сверяются ни с чем),
значения `top_score`/`accepted` на границе порога у unknown-запросов.

## Что проверено и проблем НЕ найдено

Всё ниже — на неизменённом `reid_metrics.py`; входы генерирует `work/fuzz.py`
(6000 конфигураций, сравнение всего выходного словаря с независимым оракулом на
точных дробях, атол 1e-9) и `work/tz_checks.py`.

- **Формулы:** AP(step) и AP(market_matlab) — сверены с определением и с
  `sources/compute_AP.m` (полуcумма precision до/в момент попадания);
  INP = R/rank_last — сверен с fastreid; CMC rank-1/rank-5 — «первое верное
  совпадение в топ-k». Ручные значения тестов H01–H15 пересчитаны дробями и
  верны (в т.ч. 73/180, 29/36, 55/72, 19/24).
- **Ничьи:** одинаковые оценки, в т.ч. все равные; разрешение по порядку
  столбцов и по `gallery_keys` (строковые и целые ключи), устойчивость
  сортировки; группировка ничьих в PR-кривой (одна точка на группу). 0 расхождений
  с оракулом. Вырожденная модель (все оценки равны) на мультиидентичной галерее
  НЕ даёт лестной метрики: mAP 0.089 (галерея, сгруппированная по id) против
  0.073 (перемешанная) при случайном уровне того же порядка — критерий 5
  соблюдён; детерминированная зависимость от порядка при ничьих остаётся в
  рамках критерия 4 и задокументирована (`tie_policy`).
- **Границы:** пустая галерея; галерея из одного объекта; пустой список
  запросов; запрос, у которого все верные совпадения сняты той же камерой
  (filtered_positive: выбрасывается с подсчётом, нулями не подменяется);
  запрос без верных совпадений вовсе (unknown: только режим отказа); порог
  ровно равный оценке (включительно, `>=`/`<=` согласованы между tp/fp,
  accepted и TNR); пороги ±inf; знак меры (distance ↔ similarity дают
  идентичные ранжирования и refusal при отражённых порогах, включая
  `pr_curve.thresholds` — сверено оракулом, а не только избранные ключи).
- **Кто входит в усреднение:** знаменатели mAP/Rank/mINP = valid-запросы
  (публикуется `num_valid_queries`), TNR = unknown-запросы, FN не раздувается
  отфильтрованными запросами; молчаливой подмены нулями нет нигде.
- **Численность:** входные float32-матрицы (после честного приведения к
  float64) — 0 расхождений; накопление через `math.fsum`; NaN/inf во входе
  отвергаются; contradictory `known_absent` отвергается.
- **Случайный уровень:** подтверждён независимо (свой seed 424242, позитивы
  намеренно в конце галереи против позиционного смещения): mAP 0.1068 при
  ожидании 0.1093, Rank-1 0.0460 при ожидании 0.05 — в пределах шума.
- **CLI:** npz со всеми опциональными массивами (keys/junk/mask/frames)
  проходит и совпадает с прямым вызовом `evaluate`; JSON-сериализация inf.
- **Воспроизводимость:** RNG в вычислении отсутствует, сортировки стабильные,
  повторные запуски бит-в-бит идентичны.
- **`compare_results.py`:** различия целых — точно, float — atol, пути к
