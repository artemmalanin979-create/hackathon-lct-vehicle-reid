# Разбор измерительного контура независимой стороной

Это исторический разбор первой версии контура. Найденные пробелы уже закрыты
в [доработке](rework-01.md); ниже сохранены результаты исходной проверки.

Проверяющему дали код, тесты автора и требования заказчика — и **не дали** наших
выводов о том, что считается правильным. Задача была одна: найти, где код даёт неверный
ответ.

## Итог

**Арифметика верна.** Независимый оракул на точных дробях, 6000 конфигураций,
сравнение всего выходного словаря — ноль расхождений.

**Проверки автора оказались слепы.** Заявление «намеренно ломал реализацию, все поломки
пойманы» не выдержало проверки: предъявлено **8 поломок, проходящих `verify.py`
целиком** (37 тестов, оба дифференциала, случайный уровень, матрица из 15 авторских
мутантов, CLI) и ещё 2, проходящих все 37 тестов. Среди них поломки, искажающие
mAP, Rank-1 и TNR в **лестную** сторону.

Код выживших поломок — [`mutants-surviving/`](mutants-surviving/), каждый с
воспроизводимым входом.

| Поломка | Что искажает |
|---|---|
| Обратная перестановка при разрешении ничьих | mAP 1.0 → 0.5 |
| Маска допуска применена к переставленному массиву | mAP 0.5 → **1.0**, в расчёт попадает исключённый объект |
| Оценки квантованы во float32 | mAP 0.5 → **1.0**; TNR 1 → 0 |
| Знак порогов PR-кривой при мере-расстоянии | выбор другого рабочего порога |
| `top_score` при мере-расстоянии | оценка уверенности в `candidates.csv` с обратным знаком |
| Четыре поля аудита (`eligible_count`, `relevant_pairs`, `positive_ranks`, `num_relevant`) | не проверяются ничем |
| Строгое сравнение с порогом в одном месте из двух | TNR 0 → 1 при оценке ровно на пороге |

Почему они выжили: ничьи не сверялись с внешними эталонами (дифференциал специально
генерировал входы без ничьих); мера-расстояние не проверялась нигде, кроме одного
теста; `gallery_keys` проверялись только на галерее из **двух** элементов — а любая
перестановка двух элементов совпадает со своей обратной; поля `per_query`, `counts`
и `pr_curve` не сверялись ни с чем.

**Вывод, который стоит запомнить:** «15 из 15 мутантов пойманы» не значит ничего, если
мутанты выбирал тот же, кто писал код. Покрытие меряется чужими поломками.

## Находка, влияющая на саму задачу

Контур считает метрику **по полной галерее**, а сдаём мы `submission.csv` с **первыми
десятью** кандидатами. Для запроса, чьё верное совпадение стоит на 12-й позиции, код
показывает mAP 0.083, а по сданному файлу это ноль. То есть наша самооценка
**систематически выше** того, что получится по сдаваемому артефакту.

Режим усечения в контуре отсутствует как функциональность. Это первая правка.

## Развилки трактовки — не ошибки, но числа зависят от них

Зависят от ответа организатора, поэтому записаны как открытые, а не как решённые:

1. **«mAP по всем запросам»** — усреднять по запросам, у которых есть допустимое
   совпадение (стандарт Market-1501), или по всем подряд. На двух запросах разница
   между 1.0 и 0.5.
2. **Запрос, у которого все совпадения отфильтрованы по камере** — выбрасывается из
   расчёта или попадает в знаменатель TNR как «совпадения нет».

Вопросы отправлены постановщику — см. [`../../../03-plan/questions.md`](../../../03-plan/questions.md),
пункты A3 и C2.

## Инструменты проверяющего

`oracle.py` — независимый оракул на точных дробях, используемый и текущими тестами.
`fuzz.py`, `mutants.py`, `demos.py`, `tz_checks.py` — исходные инструменты разбора:
они рассчитаны на прежний каталог `run/` с первой версией контура, которого в
клоне нет. Это архив проверки, а не команды для актуального API.

Актуальная проверка из **корня репозитория**, Python с NumPy
(зависимости — `04-solution/eval/requirements.txt`):

```bash
cd 04-solution/eval && python3 -B verify.py
```

`verify.py` запускает текущие тесты, сверку всех прежних полей с неизменённым
дробным оракулом, проверки top-K и исходные/актуальные версии мутантов.
Результаты пишет в `verification_results.json`, `mutation_results.json` и `evidence/`.

Полный отчёт — [`critique-01.md`](critique-01.md).
