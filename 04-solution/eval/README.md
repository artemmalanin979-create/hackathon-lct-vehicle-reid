# Измерительный контур

Независимая реализация метрик протокола повторной идентификации. Написана **до** любой
модели и **отдельно** от кода обучения — по правилу из
[`../../02-research/evaluation.md`](../../02-research/evaluation.md): тот, кто учит
модель, не должен единолично контролировать, чем её меряют.

## Зачем это, если организатор обещал свой скрипт

Эталонный скрипт организатора на 15.09 не опубликован. Но главное — даже когда он
появится, нам нужно, с чем его сверить: расхождения между распространёнными
реализациями mAP в re-id доходят **до нескольких десятых на одних и тех же данных**
(разбор — в [`../../02-research/metrics-protocol.md`](../../02-research/metrics-protocol.md),
раздел 9). Совпадения одной итоговой цифры мало: ошибки компенсируют друг друга, поэтому
`compare_results.py` сверяет протокол, статусы запросов, ранги всех верных совпадений,
AP/INP и счётчики.

## Что считает

Ранжирование: mAP, Rank-1, Rank-5, mINP.
Режим отказа при заданном пороге: precision, recall, F1, TNR, AUC-PR.
Исключение совпадений с камеры запроса — обе распространённые трактовки, переключателем.

## Как проверено

| Проверка | Результат |
|---|---|
| Модульные тесты, включая аналитически просчитанные вручную случаи | 37 тестов, все проходят |
| Исчерпывающий перебор мелких конфигураций (N ≤ 7) | 247 конфигураций |
| Намеренно сломанные варианты реализации | **15 из 15 обнаружены** тестами |
| Случайные близости против аналитически ожидаемого случайного уровня | mAP 0.0813 при ожидаемом 0.0806 (z = 0.69) |

Последняя строка — ответ на вопрос «как это выглядит, когда сломано»: на случайном входе
метрика обязана показывать случайный уровень, а не что-нибудь лестное.

Таблица «какая поломка каким тестом поймана» — [`mutation_matrix.md`](mutation_matrix.md),
аналитические оракулы — [`ORACLES.md`](ORACLES.md).

## Запуск

```bash
python -B -m unittest -v test_metrics   # тесты
python -B verify.py                     # полная проверка, включая мутации
```

Зависимости — только numpy. Сети не требует.
