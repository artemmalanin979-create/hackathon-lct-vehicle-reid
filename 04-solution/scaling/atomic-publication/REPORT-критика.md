# job_83 — независимая критика переноса атомарной публикации

**Вердикт: оставлять перенос в main как есть нельзя.** Численный результат сохранён,
проверка памяти не перенесена, а аварии публикации не дали частичного комплекта.
Однако штатная команда из документации перестала работать; ошибка уборки после
успешной публикации превращает успешный batch в неуспешный; **6 из 23 собственных
мутаций проходят все 78 существующих тестов**, включая полное отключение атомарности
в `app.batch`.

Проверен коммит **`baca15bc38e142d4886f5f29de537b7f60ecaeba`**, baseline —
**`7800f222094df0da26387399e23e9bf6f3c60dd4`**. Все эксперименты выполнены в
изолированных копиях внутри job_83. Код репозитория, его документы и тесты не правились;
коммитов и push от этого задания нет. Во время аудита другой процесс добавил
`b8903b6` с отчётом `audit/threshold-stability/`; проверенные сервис, модели, тесты,
split/eval/reproduce и обсуждаемые команды документации остались прежними.
При заключительной проверке появился также чужой untracked-каталог
`05-presentation/защита/`; он не изучался и не изменялся этим заданием.
[Финальная проверка](evidence/final-verification.json), [журнал](journal.md).

## Что обязательно поправить

### F1 · P1 · Сломан опубликованный способ запуска batch

`service/README.md:132–139`, `SOLUTION.md:231–236`, пример в `service/Dockerfile:85–86`
и docstring `app/batch.py` предлагают mount `/out` и `--out-dir /out`.
Новая публикация пытается обменять **сам корень mount** через
`batch_safety.py:39`. Я воспроизвёл это настоящими малыми CLI-прогонами, с исходными
изображениями и обеими ONNX-моделями:

| Версия | Тот же out-dir — корень настоящего bind mount | Результат |
| --- | --- | --- |
| `7800f22` | `python -m app.batch … --out-dir <bind-root>` | rc=0, четыре файла |
| `baca15b` | такая же команда | rc=1, **EBUSY / errno 16**, итоговый каталог пуст |

Отказ main происходит **после инференса и записи всех четырёх файлов**. Cleanup
удаляет новый комплект. Это регресс пользовательского пути запуска, хотя сам EBUSY
автор уже перечислял среди ограничений. Рабочая команда в отдельном отчёте о переносе
не исправляет команду в документации сервиса.

**Обязательно:** согласовать публичный контракт и все точки входа. При сохранении
нынешней схемы монтировать родителя и публиковать вложенный `/out/result`, обновить
основные инструкции, docstring и пример Dockerfile, добавить проверку настоящего
bind mount. Неподдерживаемый выходной путь следует отвергать до дорогого инференса.
Команды `reproduce/run.py --out-dir /out` не следует механически переписывать: reproducer
сам публикует вложенные `val/` и `test/`.

Доказательства: [результаты CLI](evidence/cli-mount.json),
[stderr main](logs/cli-bound-after.stderr), [скрипт опыта](scripts/cli_probes.py).

### F2 · P2 · Ошибка cleanup скрывает уже состоявшуюся публикацию

`batch_safety.py:70–73` безусловно удаляет staging. После exchange там находится старый
каталог, и его удаление может быть запрещено. `batch.py:120` печатает успешный ответ
только после завершения этого cleanup.

Реальный CLI-пример без мутаций: прежний output имеет mode `0555`, четыре существующих
файла доступны владельцу для записи, родитель доступен для записи. Новый комплект
успешно меняется местами со старым; удаление старых файлов получает **EACCES**.
Получено **rc=1, пустой stdout, traceback PermissionError**, хотя в final уже находятся
все новые файлы. Три сдаваемых файла побайтно совпали с независимым новым контрольным
прогоном; `run_info.json` содержит новые счётчики 1 query / 2 gallery. Старый полный
комплект остался в `.out.incomplete-*`.

**Обязательно:** различать завершившуюся публикацию и неудачную последующую уборку;
вернуть вызывающему коду однозначный статус уже опубликованного результата и
добавить тест ошибки cleanup **после** exchange. Сейчас такой тест отсутствует.
Автор упоминал это ограничение; здесь оно независимо доведено до наблюдаемого
неуспешного завершения настоящего `app.batch`.

[Результат со всеми хеш-сверками](evidence/cli-cleanup.json),
[воспроизводящий скрипт](scripts/cli_cleanup.py), [лог](logs/cli-cleanup.txt).

### F3 · P2 · Тесты не защищают связь batch с перенесённым helper

Шесть выживших мутаций проверены ещё и всеми остальными тестами проекта:
**78/78 зелёные для каждой**. Набор не замечает:

- M17: настоящий `renameat2` вернул ошибку, но код сообщил успех и удалил новый staging;
- M19: вместо старого `embeddings.npy` находится каталог с пользовательским документом,
  который ошибочная реализация удаляет;
- M20: из batch исчез импорт `atomic_output`, обычный запуск падает с `NameError`;
- M21: embeddings пишутся в final, старый комплект повреждается до отказа о неполноте staging;
- M22: batch вообще обходит `atomic_output`, исключение оставляет смешанный комплект;
- M23: `run_info.json` вынесен за контекст публикации, обычный запуск не может завершиться.

**Обязательно:** добавить проверки именно `batch.main`/CLI на успешный полный комплект,
сохранность старого результата при сбое между записями и отсутствие final до публикации.
Отдельно проверять ошибочный возврат libc внутри `_publish`, типы старых записей и
сбой уборки. Подмена всего `_publish` исключением не проверяет его собственную
обработку errno. Точный список мутаций и ловящих тестов приведён ниже.

## Проверки памяти в переносе нет

Проверены **все Python-файлы app и tests**, а не только новый модуль. В них нет
функций, вызовов и импортов `estimate_memory`, `available_memory`, `check_memory`,

rerank / cosine. Исторические отчёты про memory guard в `scaling/` остались на месте;
они не являются исполняемым остатком проверки.

## Аварии и условия файловой системы

Все SIGKILL отправлены только собственным дочерним процессам. Mounts создавались
в отдельных user/mount namespaces; файловые системы и процессы пользователя не менялись.

| Сценарий | Как проверено | Измеренный результат |
| --- | --- | --- |
| SIGKILL при незавершённом rename нового каталога | Настоящий `_publish`; FUSE удерживает ответ на syscall до либо после операции backing FS | 2 опыта: final отсутствует либо содержит все четыре новых файла; rc=-9 |
| SIGKILL при незавершённом renameat2(EXCHANGE) | Та же схема, существующий старый комплект | 2 опыта: все четыре old либо все четыре new; rc=-9 |
| Диск заполнен во время записи **последнего** файла | tmpfs 1 MiB, настоящий write в run_info.json до ENOSPC; с прежним output и без него | errno 28; old сохранён / final отсутствует; staging удалён |

| Два полных batch в существующий output | Оба готовы к публикации; затем A и B | Оба rc=0; итоговый комплект целиком B |

### Что означает опыт «во время rename»

Это не прежняя остановка Python до `_publish` или после его возврата. Для каждого
из четырёх процессов непосредственно перед SIGKILL прочитаны `/proc/<pid>/syscall`
и `wchan`: процесс находился в **syscall 82 (rename) либо 316 (renameat2, flags=2)**,
`wchan=request_wait_answer`. Минимальный FUSE-сервер удерживал ответ файловой системы.
В одном режиме backing-операция ещё не совершена, в другом — уже совершена, а syscall
в приложении ещё не вернулся. После SIGKILL ожидание разрешалось; процесс завершался -9.

Это измерение поведения настоящего незавершённого syscall на контролируемой FUSE.
Остановка внутри внутренней транзакции native Btrfs и потеря питания **не проверялись**.
Production также прямо исключает fsync/power-loss durability из своего контракта.
[Записи syscall/wchan](evidence/rename-inflight.json),
[полностью самостоятельная обвязка](scripts/rename_inflight.py).

## Насколько честны новые тесты

Независимый `EXPECTED_FILES` в тестах действительно отличается от использования
production-константы как собственного эталона. Новые проверки повторного destination,
symlink внутри старого результата и обязательного candidates работают: M09, M10,
M07 убиты. Проверка SIGKILL обнаруживает удаление старого каталога перед rename: M13 убита.

Их доказательная область ограничена:

1. **Все 13 тестов импортируют только `batch_safety`.** Они могут оставаться зелёными,
   когда настоящий batch больше его не вызывает или вообще не запускается. Это главный
   незакрытый риск именно переноса; M20–M23 доказывают его напрямую.
2. `test_failed_rename_preserves_previous_complete_result` подменяет весь `_publish`.
   Поэтому M12 он ловит, а M17 внутри `_publish` — нет.
3. В тесте SIGKILL Python audit hook видит `Path.rename`, но прямой libc-вызов через
   ctypes не даёт события `os.rename`. Ветка exchange останавливается после возврата
   helper. Этот тест полезен против конкретной неатомарной замены, но сам по себе
   не является тестом прерывания исполняющегося renameat2.
4. Fixtures состоят из четырёх файлов с текстом old/new. Это корректный unit-эталон
   поколения, но он не проверяет соединение с настоящими serializers, типы NumPy/CSV/JSON
   и системные ошибки на границе libc. Мои полные и малые CLI-прогоны проверяют эти
   связи отдельно; в репозиторных тестах таких проверок по-прежнему нет.

У исходного helper есть ещё одна узкая граница: staging проверяется только по именам
(`batch_safety.py:60`). Четыре имени с каталогом либо symlink вместо run_info.json
успешно публикуются; это измерено на исходном коде. Штатные serializers такие объекты
не создают, поэтому этот опыт не доказывает порчу обычного запуска. Он показывает,
что полнота по именам слабее обещания «четыре обычных файла».
[Опыт с типами staging](evidence/edge-contracts.json).

Отдельно хеши содержимого не покрывают права доступа: новый final получает **0700**
от mkdtemp, baseline при той же umask дал **0755**. Это измерено на полных прогонах.
Публикуется новый inode; прежние directory mode/ACL/владелец явно не копируются.
Mode проверен непосредственно, ACL и смена владельца отдельно не измерялись. Для чтения результата другим UID
потребуется согласованная политика прав или подходящий UID запуска контейнера.

При конкурентных писателях доказана целостность конечного поколения в описанных
сценариях, но нет гарантии успеха обоих запусков или сохранения результата каждого:
новый output даёт гонку ENOTEMPTY, существующий работает как «последний победил».
Однописательский контракт автора остаётся существенным ограничением.

## Воспроизведение и завершённость

Все scripts, evidence, logs, мутации, оба полных комплекта и контрольные результаты
сохранены рядом с отчётом. Скрипты намеренно создают новые каталоги с `exist_ok=False`:
повторять нужно в свежей копии задания, чтобы не перезаписывать доказательства.

- Подготовка снимков и manifest: `python3 -B scripts/prepare.py`.
- Два полных прогона: `scripts/full_runs.py`, запускать интерпретатором проектной `.venv`
  через systemd-run с CPUQuota=200%, MemoryMax=4G, MemorySwapMax=0, Nice=10.
- Мутации: `python3 -B scripts/mutations.py`; все тесты: `python3 -B scripts/all_tests.py`.
- Файловые аварии: `unshare -Urnm python3 -B scripts/faults.py`.
- Незавершённый syscall: `unshare -Urnm python3 -B scripts/rename_inflight.py`.
- CLI-контрпримеры: `scripts/cli_probes.py normal`, затем в private mount namespace
  `scripts/cli_probes.py mount`; использовать проектный Python.
- Конкуренция и cleanup: `scripts/cli_concurrency.py`, `scripts/cli_cleanup.py` тем же Python.

Итоговые проверки: **исходный main 78/78**, каждая из шести выживших мутаций **78/78**;
оба полных прогона успешны; 296 файлов снимков и 1860 изображений повторно сверены;
проверенные пути сервиса/split/eval/reproduce в рабочем дереве не изменены.
Собственных активных процессов и mount namespaces
после опытов не осталось. Публикация и исправления оставлены координатору.
