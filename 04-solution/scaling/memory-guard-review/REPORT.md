# job_80 — независимый критический аудит guard/memory

**Вердикт: вливать в main как есть нельзя.** На разрешённом входе guard пропускает реальный OOM; на выполнимых входах отказывает. Стандартные способы запуска с private cgroup namespace и выходом в корень bind mount перестают работать. Численный результат штатного прогона сохранён, и сам rename выдержал проверенные аварии. Это не закрывает ошибки определения допустимого прогона и пробелы тестов.

Проверены неизменённые снимки `guard/memory` **de1c68cf97b23ad9732f6da06dcf693495618676** и его baseline **0b2e2f0c52d9220e14aeacb6182a1b6f8dd72033**. В исходных деревьях ничего не исправлено, коммитов/push/переключения веток нет. Снимки и SHA-256 исходников — [source-manifest.json](evidence/source-manifest.json), ход работы — [journal.md](journal.md). Итоговая проверка неизменности — [final-source-integrity.json](evidence/final-source-integrity.json).

Тяжёлые измерения: worker-vm, образ `localhost/job72-jury:6179b69` (`f04d50ee90c8`), Python 3.13.15, NumPy 2.5.3, ONNX Runtime 1.30.0. Каждый опыт в отдельном контейнере; по одному CPU, два полных прогона на CPU 0/1, короткие опыты последовательно на CPU 2. Лимиты/swap и точные команды записаны в `evidence/worker/*.controller.json`. Поддерживающий процесс сохранял `memory.events` после гибели дочернего Python. Нет глобального изменения лимитов, сброса кэшей или тяжёлой нагрузки на основную машину.

## 3. Ложные срабатывания и обнаружение бюджета

**P1: неизменяемый минимум 2 GiB под модели плюс 256 MiB резерва отсекает маленькие рабочие прогоны.** `max(32, ...)` в строке 33 не уменьшает резерв даже для Q=G=batch=1. Baseline действительно выполнил этот набор при 512 MiB: RSS **146.2 MiB**, пик cgroup **118.0 MiB**. Guard отказал с требованием около 2304 MiB. [лог](logs/worker/j80-small-baseline.log), [cgroup](evidence/worker/j80-small-baseline.watch.json); [лог](logs/worker/j80-small-guard.log), [cgroup](evidence/worker/j80-small-guard.watch.json).

**P1: стандартный private cgroup namespace запрещён целиком.** Контейнер с 4 GiB и тем же крошечным набором заканчивается `родительские cgroup скрыты` ещё до создания Embedder. Это намеренный fail-closed, а не ошибка парсинга; но новые обязательные `--cgroupns=host` и mount полной иерархии не внесены в штатные команды запуска. Нельзя называть ветку совместимой с прежним container entrypoint. [лог](logs/worker/j80-private.log), [cgroup](evidence/worker/j80-private.watch.json).

**Reclaimable cache вычитается как невозвратная память.** При 4 GiB в собственной cgroup записан и fsync-нут файл **3500 MiB**. Guard отказал Q=32/G=1/batch=32: available **547.5 MiB**, required **2305.1 MiB**. После намеренного обхода только check_memory тот же настоящий ONNX-прогон завершился в той же cgroup. Kernel вытеснил **77312 страниц**, пик cgroup **4096.0 MiB**, OOM=0. Кэши хоста не сбрасывались. Причина — строки 97–101, не отличающие освобождаемый file cache от рабочего набора. [лог](logs/worker/j80-cache-reclaim.log), [cgroup](evidence/worker/j80-cache-reclaim.watch.json).

**Swap не учитывается даже там, где позволяет закончить прогон.** Q=32/G=1/batch=32: baseline при **768 MiB RAM + 1024 MiB swap** завершился, реальный пик swap **120.0 MiB**. Guard отказал. Контроль baseline с теми же 768 MiB и swap=0 получил OOM-kill. Следовательно, дело не только в консервативном запасе при фактически неиспользуемом swap. [лог](logs/worker/j80-swap-active-baseline.log), [cgroup](evidence/worker/j80-swap-active-baseline.watch.json); [лог](logs/worker/j80-swap-active-guard.log), [cgroup](evidence/worker/j80-swap-active-guard.watch.json); [лог](logs/worker/j80-noswap-control.log), [cgroup](evidence/worker/j80-noswap-control.watch.json).

**memory.high трактуется как hard admission limit.** При `memory.max=max`, `memory.high=192 MiB` baseline Q=G=batch=1 проходит, guard отказывает. Это ещё один измеренный ложный отказ относительно критерия «набор помещается». Однако игнорировать high безусловно тоже нельзя: отдельный контроль high=96 MiB достиг пика **114.4 MiB**, OOM=0, high-events=2271, но не завершился за 90 секунд и был остановлен `timeout` (124). Он доказывает throttling, а не успешное завершение выше high. [лог](logs/worker/j80-high-baseline.log), [cgroup](evidence/worker/j80-high-baseline.watch.json); [лог](logs/worker/j80-high-guard.log), [cgroup](evidence/worker/j80-high-guard.watch.json); [лог](logs/worker/j80-high-crossed.log), [cgroup](evidence/worker/j80-high-crossed.watch.json).

Семантика сверена с [документацией ядра cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html): `memory.high` ограничивает через reclaim/throttling, сам его выход за границу не вызывает OOM; `memory.current` включает anonymous memory и page cache; swap учитывается отдельно. Политику допустимого замедления нужно отделить от утверждения о неизбежном OOM.

## 4. Атомарность по сценариям

Лёгкие сценарии выполнялись на исходном `batch_safety.py`, SIGKILL посылался только собственным дочерним процессам. ENOSPC, bind mount и EXDEV проверены настоящими системными вызовами в отдельном mount namespace; никакие внешние mounts не менялись.

| Сценарий | Измеренный результат |
| --- | --- |
| SIGKILL в середине записи первого файла, с прежним результатом и без | Старый комплект цел либо final отсутствует; половина файла только в `.incomplete-*` |
| SIGKILL после первого закрытого файла, оба варианта | То же; полукомплекта в final нет |
| SIGKILL между завершением всех записей и публикацией, оба варианта | Старый final/отсутствие final; новый полный набор остаётся только в staging |
| SIGKILL сразу после rename/exchange, до cleanup, оба варианта | Final целиком новый; при замене старый комплект остаётся в staging |
| Новый output, пустой существующий output, полный старый output | Успех, четыре новых файла, staging убран |
| Исключение/неполный набор | Отказ публикации; прежний результат не повреждён |
| Настоящий ENOSPC на tmpfs 2 MiB, оба варианта | Errno 28; final сохранён/отсутствует; staging очищен |
| Symlink самого output | Ранний SystemExit; цель ссылки сохранена |
| Symlink файла внутри старого комплекта | Ранний SystemExit; цель сохранена |
| Посторонний notes.txt до входа | Ранний SystemExit, файл сохранён |
| Нет прав записи в parent | Ранний PermissionError, final сохранён; ошибка без дружелюбной обёртки |
| Старый output read-only 0555, parent writable | Новый final уже опубликован, затем finally/rmtree бросает PermissionError; снаружи отказ при изменившемся final |
| Существующий output 0755 | После успешного exchange становится 0700 — права от mkdtemp не нормализуются |
| TMPDIR на другой FS | Stage всё равно sibling output, операция успешна; TMPDIR не влияет |
| Temp принудительно создан на другой FS | Реальный EXDEV=18, понятный отказ, старый комплект сохранён, stage удалён; подменено только место mkdtemp |
| Output — реальный bind mount, parent writable | EBUSY=16, старый комплект сохранён. Обычный пакетный запуск с таким output перестаёт работать |
| Четыре каталога вместо четырёх обычных файлов в staging | Публикация успешно проходит: проверяется только набор имён |
| Посторонний файл добавлен между последней проверкой и EXCHANGE | Файл удалён при cleanup старого каталога; второй проверки недостаточно для защиты от конкурентных изменений |

Доказательства: [atomic.json](evidence/atomic.json), [filesystem.json](evidence/filesystem.json), скрипты [atomic_probe.py](scripts/atomic_probe.py) и [filesystem_probe.py](scripts/filesystem_probe.py).

**P1 — совместимость bind mount проверена и сквозным batch.** `j80-bind-root-baseline`, root container, `--out-dir /bound-out`: успех. Guard с теми же правами/данными: инференс и запись stage проходят, затем EBUSY, пустой итоговый каталог. При UID 1000 отказ ещё раньше: нет прав создать sibling непосредственно в `/`. В README сервиса и SOLUTION.md используется `--out-dir /out` с примонтированным `/out`. Нужен согласованный контракт: монтировать родительский каталог и публиковать вложенный результат либо другая схема публикации. Несовместимость следует проверять до дорогого инференса. [Baseline](logs/worker/j80-bind-root-baseline.log), [guard root](logs/worker/j80-bind-root-guard.log), [guard UID 1000](logs/worker/j80-bind-output.log).

**P2 — гонка и состояние после ошибки cleanup.** Для TOCTOU подменена только функция проверки: непосредственно после её второго успешного возврата создаётся notes.txt. Это детерминированное воспроизведение окна, эквивалентного конкурентной записи; не утверждение, что файл самопроизвольно пропадает без конкурента. `rmtree(staging)` после обмена удаляет его. Для read-only старого каталога вмешательства в код нет: обычные права 0555 достаточны, чтобы новый результат был виден при исключении из context manager. Требуются явный контракт владения каталогом/конкурентных писателей и корректный статус после публикации.

Частичные staging после SIGKILL действительно остаются **на диске**. Гарантия выполнена для **итогового пути**, не для отсутствия любых временных полукомплектов и не для автоматической уборки сирот. Устойчивость к отключению питания не проверялась и кодом прямо не обещана (нет fsync-протокола).

## 6. Честность тестов и конкретные дыры

Тесты не «проходят при любой ошибке»: 9 мутаций действительно пойманы, проверки предков, вычитания charge и раннего symlink работают. Но следующие зелёные состояния недопустимы:

1. **Guard, отказывающий всегда, проходит всё.** Проверяется отказ при недостатке, нет позитивного `check_memory` при достаточном бюджете и проверки равенства на границе.
2. **Набор файлов берётся из проверяемой реализации.** `fill` и `assert_complete` используют `safety.OUTPUT_FILES`; удаление обязательного candidates.csv меняет и production-ожидание, и oracle теста. Реальный batch после такой мутации вообще не сможет опубликовать свои четыре файла.
3. **Не наблюдается сама публикация.** «Один exchange» тестируется только состояниями до/после context manager. `os._exit(137)` в исходном тесте происходит до публикации и не является посланным процессу SIGKILL. M18 с удалением старого результата и несколькими rename остаётся зелёной.
4. **Формула проверяется широкими неравенствами на нескольких заранее известных точках.** Уменьшение коэффициента 64→48, памяти моделей 2→1.5 GiB, полное удаление линейных буферов или резерва остаётся зелёным. Нет измерений декодирования/crop, допустимых размеров и разных профилей batch.
5. **Среда подменена файлами.** Это полезно для арифметики, но не обнаруживает regression обычного private namespace, bind mount output, реальные ENOSPC/EXDEV, swap/reclaim или фактический смысл high.
6. **Нет честного end-to-end контракта.** Тестовый файл вообще не запускает `app.batch`; зелёные проверки helper не доказывают вызов guard до Embedder, отказ без побочных эффектов и успешный штатный контейнерный запуск.
7. **Нет ошибок после успешного exchange, режима доступа, file symlink внутри результата и гонки между проверкой/rename.** M14 и M15 проходят; четыре каталога с нужными именами тоже считаются полным комплектом.

## 7. Что обязательно поправить перед main

1. Ограничить и проверить размеры декодируемых кадров/bbox **до тяжёлой аллокации** либо включить реальные пиковые копии препроцессинга в оценку. Контрпример с 13300² должен превращаться в ранний понятный отказ или успешно проходить с достаточным бюджетом, а не получать OOM после `guard_passed`.
2. Устранить безусловный минимум для маленьких реальных прогонов и зафиксировать проверенные диапазоны формулы. Не подменять измерения RSS предположением о всех будущих размерах и batch.
3. Согласовать политику RAM, reclaimable cache, swap и memory.high. Не считать весь charge невозвратным и не вычитать весь file cache без разбора. Если swap/high используются как ограничения времени или принята намеренная консервативность, сделать это явным контрактом, а не сообщением о неизбежной нехватке памяти.
4. Исправить штатные команды/контейнерный контракт для cgroup namespace и output volume. Проверить обычный запуск из README, root и non-root; mountpoint/output permissions проверять до инференса. Сохранить доступность результата для предполагаемого потребителя вместо неоговорённого перехода 0755→0700.
5. Обработать cleanup после уже успешной публикации отдельно от неудачной публикации. Определить, допускаются ли конкурентные изменения output; при обещании сохранности чужих файлов закрыть воспроизведённое окно удаления.
6. Добавить независимые acceptance/rejection-тесты, фиксированный внешний список четырёх файлов, наблюдение/аварию внутри публикации, реальные container/filesystem проверки и память на различных формах входа. Как минимум M19, M18, M16 и новые воспроизведённые дефекты должны перестать проходить незамеченными.
