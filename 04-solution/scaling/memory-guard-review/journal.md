## Файловая система и старт тяжёлых прогонов

- В отдельном private mount namespace реальный tmpfs 2 MiB дал ENOSPC=28; при обоих вариантах старого выхода staging убран, прежний комплект сохранён. Реальный bind mount дал EBUSY=16, искусственно направленный tempfile на другую FS дал настоящий EXDEV=18; старые файлы сохранены. Внешние mount namespace и файловые системы не изменялись.
- 13 искусственных /proc/cgroup сценариев: нет v2, legacy v1, max, вложенные лимиты/charge, memory.high при отсутствии memory.max, большая/маленькая память хоста, swap, глобальный/приватный корень. Все результаты записаны отдельно от реальных измерений.
- Полные независимые validation baseline/guard запущены на worker с реальными часами, 1110×750, по 1 CPU и 4 GiB RAM без swap. Метрики будут пересчитаны из самостоятельно полученных embeddings после неизменённого batch.main.
- Подготовлена последовательная worker-suite: малые реальные данные, private namespace, memory.high без hard limit, bind output, reclaimable cache, swap, увеличенное разрешение кадров, шесть точек синтетических векторов и прогретые ONNX.

## Подтверждённые ложные отказы

- j80-small-baseline (Q=G=1, batch=1) завершился при 512 MiB, maxRSS 153292800 байт; j80-small-guard на тех же данных отказал (минимальная оценка около 2.25 GiB).
- При memory.max=max, memory.high=192 MiB baseline также завершился, guard отказал.
- j80-cache: реальный файловый кэш 2560 MiB, guard отказал; намеренный обход только guard в измерительном wrapper дал успешный настоящий ONNX batch. Это тест возможного reclaim, не отключение защиты в исходниках.
- j80-swap-baseline: 1408 MiB RAM + 1024 MiB swap, успех; guard на тех же параметрах отказал. Точные charge/swap/peak сохраняются supervisor-ом.
- Дополнена мутация M19: безусловный отказ. Все 30 тестов проходят. Исправлен предварительный арифметический подсчёт: теперь всего 19 мутаций, 9 убиты, 10 выжили.

## Уточнение экспериментальных гипотез

- Первый опыт j80-large-oom НЕ вызвал OOM: кадр 12000² при bbox 208² прошёл (RSS ≈2000 MiB). Название опыта — исходная гипотеза, результат успех, скрывать его нельзя. Следующий контроль использует bbox целого допустимого кадра: это добавляет копию большого кропа.
- При cache=2560 MiB kernel reclaim не понадобился (пик ≈3457 MiB), а при RAM=1408 MiB фактическое использование swap было нулевым. Эти успехи доказывают консервативный ложный отказ, но сами по себе НЕ доказывают reclaim или пользу swap. Назначены отдельные контроли cache=3500 MiB и RAM=768 MiB ± swap.
- Выживший M18 отдельно убит SIGKILL между первым и вторым файловым rename: старый комплект потерян целиком, финальный out содержит только run_info.json. Доказательство в evidence/mutant-crash.json; 30 исходных тестов этого не заметили.

- j80-fullcrop-oom: Q=33, G=1, batch=32, кадр 13300×13300 RGB PNG, bbox на весь кадр, до него 32 малых кадра. Никакая проверка guard не отключена.

- Контроль того же набора при 4 GiB (j80-fullcrop-13300) завершился: maxRSS=3070701568, memcg peak=3047927808 байт. Значит оценка недостаточна и без конкурирующего внезапного потребителя.
- Дополнительные полные кропы: 6000² — RSS 1380352000 / memcg 1353351168; 12000² — RSS 2673090560 / memcg 2649657344. Оценка для всех трёх одинаковая: она не учитывает размер декодирования, RGB-конвертацию и большую копию crop.

## Полные прогоны завершены; исправление измерительного harness

- Оба неизменённых batch.main успешно завершили ONNX + ranking + четыре выходных файла: baseline total_elapsed_s=1088.927; guard=1083.614. После их завершения отдельная проверка метрик в моём wrapper упала: в сокращённый git archive не был включён scope_metrics.py (evaluate импортирует его лениво). Поэтому общий код обоих wrapper — 1, а не 0; это ошибка моего harness, не batch/guard.
- Добавляется точный scope_metrics.py из тех же commit в измерительные снимки. Метрики будут пересчитаны из уже независимо полученных файлов, без повторения инференса и без изменения выходов. Исходные traceback/logs остаются в evidence. RSS из supervisor относится к полному дочернему процессу, не буду выдавать его за отдельный сохранённый замер batch.
- Оба исходных git дерева всё ещё чистые, guard HEAD по-прежнему de1c68c.
