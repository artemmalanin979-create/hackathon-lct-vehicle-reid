# Где мы упрёмся в память и чего стоит защита

Сплошной аудит ТЗ назвал главным незакрытым техническим риском память: пакетное
переранжирование квадратично, автоматического ограничения нет, а размер теста у жюри нам
неизвестен. За производительность отвечает 20 % оценки, за отказ — ещё 10 %. Здесь этот
риск измерен: 39 принятых прогонов, 29 успешных, 9 подтверждённых OOM-kill, 1 MemoryError.

Всё считалось на узле, в отдельной cgroup на каждый прогон, со swap = 0 и одним
закреплённым ядром. Исполнялся **неизменённый `app.batch.main`** целиком — от чтения CSV
до записи `submission.csv`; подменялся только поставщик векторов (нормированные гауссовы
512-мерные). Полный прогон на настоящих 1110 × 750 воспроизвёл
**0,7740915539438481 / 0,7307692307692307** точно.

## Границы

| Лимит памяти | Проходит | Падает |
|---|---|---|
| 4 ГиБ | 5550 × 3750 | 5735 × 3875 |
| 16 ГиБ | — | 17760 × 12000 |

Наш штатный размер 1110 × 750 и его удвоение проходят с запасом; 4440 × 3000 при 4 ГиБ
даёт пик 2,73 ГиБ и 38 секунд на переранжирование.

**Падение жёсткое.** Не понятная ошибка, а OOM-kill: код 137, процесс исчезает за
десятки секунд. Хуже того, на диске остаётся **неполный комплект** — например, один
`embeddings.npy` без остальных файлов, что снаружи выглядит как частичный успех.

Попутно нашлась ненадёжность мониторинга: при настоящем OOM Podman записал
`OOMKilled=false`, и классифицировать пришлось по совокупности признаков ядра
(`CONSTRAINT_MEMCG`, `memory.events oom_kill=1`, код 137), а не по одному флагу.

## Чего стоит защита

Ограничить переранжирование кандидатами приближённого поиска можно, но это не бесплатно:

| Режим | mAP | Rank-1 | цена по mAP |
|---|---:|---:|---:|
| полное переранжирование | 0,774092 | 0,730769 | — |
| top-500 | 0,757105 | 0,712740 | −1,70 п.п. |
| top-200 | 0,752152 | 0,709135 | −2,19 п.п. |
| **top-100** | 0,749217 | 0,707933 | **−2,49 п.п.** |
| top-50 | 0,744022 | 0,703125 | −2,97 п.п. |
| потоковый косинус | 0,731609 | 0,685096 | −4,25 п.п. |

**Важнее цены по метрике: у ограниченного режима другая шкала уверенности.** При старом
пороге TNR падает с 0,784 до 0,55–0,57, то есть режим отказа ломается. Каждому профилю
нужна своя калибровка: для top-100 диагностический порог 0,7181023670882151 даёт
F1 / TNR 0,798122 / 0,769784. Включить ограничение «на всякий случай», не трогая порог,
нельзя.

## Что предлагается сделать

Рекомендация исполнителя, полностью — в `REPORT.md`:

1. Проверка бюджета памяти **до** инференса, по всей иерархии cgroup, а не по одному
   листовому лимиту — эксперимент предъявил контрпример, где чтение только листа вводит
   в заблуждение.
2. Разделить извлечение признаков и поиск по времени жизни памяти: `batch = 32`
   ограничивает тензоры инференса, но не матрицы переранжирования.
3. При превышении бюджета — ограниченный режим на каждый запрос, без сборки полной
   матрицы; исходный компромисс K = 100.
4. Запасной вариант — потоковый точный косинус со своим порогом.
5. **Публиковать комплект атомарно**: во временный каталог и затем переименованием, чтобы
   убитый прогон не выглядел как успешный.

## Границы самого измерения

Большие наборы синтетические: измерена работа алгоритма с памятью, а не качество на
миллионе разных машин. Качество и отказ для top-K измерены на настоящих 1110 × 750. По
одному прогону на точку, без повторов. Замеры относятся к пакетному режиму: API и Qdrant
одновременно не поднимались, суммарная память развёрнутого сервиса здесь не описана.
Прежняя миллионная цифра из `scaling/` — про отдельный индекс приближённого поиска, а не
про текущий пакетный путь целиком.
