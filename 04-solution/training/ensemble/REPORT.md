(= паспорт сервиса), ain_v2+rr 0,6908, concat w=1+rr 0,7146, **среднее+rr 0,7227**.

Оговорка о выборе: «лучший» выбран из 4 запрошенных (+2 дополнительных) конфигураций на той же валидации — это даёт
оптимизм порядка одного сравнения из шести; при p < 0,0005 (0 из 4000) и Δ > 2σ такой поправкой результат не снимается.

**Разрыв по камере** (Таблица B): у ансамбля-среднего разрыв **меньше**, чем у базы (косинус +0,1442 против +0,1556;
переранж. +0,1292 против +0,1417). Ансамбль не вносит камерного шортката — наоборот, кросс-камерный Rank-1 у него выше
(0,6863 против 0,6635), а внутрикамерный (без исключения) практически тот же (0,9748 против 0,9760).

## 7. Вердикт

**В решение сегодня идёт то, что там есть: базовая OSNet-AIN + переранжирование (0,6937 / 0,6635, отказ 0,806 / 0,777).**

**ain_v2 сама по себе — нет.** +0,0064 mAP меньше σ, p = 0,52, Rank-1 хуже; отказ такой же (0,803 / 0,773). Стоп-правило
сработало правильно, полная таблица это только подтверждает.

**Ансамбль «среднее L2(база) + L2(ain_v2)» + переранжирование — единственный кандидат, у которого прирост больше σ, и он
рекомендуется к внедрению при выполнении условий ниже.** mAP 0,7310 (+0,0374, ДИ [+0,0248; +0,0505], 0 из 4000 ресэмплов
против; 2,8 σ), Rank-1 0,6863 (+0,0228, p = 0,011), mAP@10 0,7227 против 0,6834, без исключения камеры 0,8602 против 0,8354
(+0,025 — прирост сохраняется и в протоколе без камер, каким, вероятно, будет жюри). Отказ при перекалиброванном пороге
0,5521: F1 0,812 / TNR 0,788 — не хуже. Разрыв по камере меньше базового (+0,129 против +0,142): камерного шортката ансамбль
не вносит. Пер-запросно: AP вырос у 258 запросов, упал у 80; провальных (AP < 0,1) стало 69 вместо 132.

Условия, без которых ансамбль в решение **не идёт**:

1. **Абляция зоны номера для ain_v2 и для ансамбля** — на машине с кадрами (`04-solution/plate-ablation/`: `extract_variants.py`
   с `REID_MODEL_PATH=ain_v2_s2.onnx` → 13 вариантов × 1860, ≈ 21 мин; векторы базы по тем же вариантам уже воспроизводятся,
   ансамбль = среднее L2-векторов двух моделей по каждому варианту; `eval_variants.py`). Критерий тот же, что у базы: контраст
   «пластина − контроль равной площади» не значимо положителен, верхняя граница ДИ на уровне базовых +0,004…+0,016.
   Пока это не сделано, требование ТЗ (дисквалификация за признаки ГРЗ) для ain_v2 **не проверено**, а дообучение шло на тех
   же кадрах с пикселизованными пластинами — риск реальный, а не формальный.
2. **Цена по времени принята осознанно:** две сети вместо одной — «изображение → вектор» при батче 1 ≈ ×2 (≈ 88 мс вместо
   44 мс на машине postproc); ТЗ даёт 20 % за производительность, 45 % за mAP. Формат сдачи не меняется: 512-мерный вектор
   (среднее, не конкатенация), переранжирование то же, веса 8,4 + 8,7 МБ.
3. **Перекалибровать порог** (0,4994 → 0,5521 на шкале переранжирования) и заново получить все три артефакта одним прогоном.

Если п. 1 не проходит или не успевается — остаётся база + переранжирование, и тогда ничего менять не нужно.

Почему именно среднее, а не concat: на val среднее лучше при каждом весе (Таблица A/C), оно не меняет размерность вектора
(512, формат сдачи и сервис как есть), а честный подбор веса на dev-срезе (раздел 6-bis) ставит w = 1 на плато оптимума.

Что этот прирост **не** доказывает: он измерен на нашем сплите (25 % отказных, есть camera_id); на закрытом тесте состав другой.
Выбор «лучшего» из шести конфигураций на той же валидации даёт небольшой оптимизм (порядка 0,005 по опыту postproc), но не
съедает 2,8 σ. Веса ансамбля не подбирались (сетка брифа), переранжирование не переподбиралось.
