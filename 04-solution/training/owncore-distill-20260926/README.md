# Дообучение самостоятельного CrossViewCore

После появления официального оценщика отдельно пересчитан [mAP@10 по независимым
запросам](REPORT.md#дополнение-2909-официальный-протокол-сдачи): 0,297972 у combined
CrossViewCore против 0,741103 у сдаваемой `d1_j48` на повторно использованной val.
Числа KR ниже относятся к прежнему общему пакетному исследованию.

Предыдущий `CrossViewCore` действительно получает изображение и выдаёт один 512D
дескриптор, но после 14 эпох на собственных данных достиг KR mAP 0.311518
против 0.774092 у сдаваемой `d1_j48`. Его CPU p95 2.190 мс против 71.642 мс
измерен на границе готовый RGB208 тензор → дескриптор. Простое продление
исходного режима не обещает закрыть разрыв: за последние шесть эпох dev cosine
mAP вырос лишь на 0.017.

Следующий заранее ограниченный опыт продолжает **тот же image encoder** с
checkpoint SHA-256 `22fc2fdd92519ae21f08eb6feef3812dc92bb5dd0191b2f6c7f1bbdc6a966e1a`.
Учитель — две существующие ONNX-ветви, но только **во время обучения**.
Их геометрия приводится whitening, обученным на 6639 fit-кадрах; 609 dev-кадров
не входят в target и градиент. Исторически teacher `combined_v1` и исходный
checkpoint уже выбирались с использованием dev100: dev не является новым
нетронутым holdout. Val 1110×750 также неоднократно использовалась ранее.

До нового обучения зафиксированы [own-only протокол](protocol-own.json) и
[combined-продолжение](protocol-combined.json). Первый: одна попытка 1+11 эпох
по 600 P8K4 batch на 6639 fit-кадрах. Второй разрешён только по ресурсному
правилу **до просмотра val первого**: проверенные 19 967 fit-кадров, отдельный
teacher target и smoke; 8 дополнительных эпох. Число seeds и сетка fusion
не меняются после результатов. Checkpoint выбирается по dev cosine mAP,
пороги отказа — по dev отдельно для cosine/KR. Финальная val — только после
заморозки кандидатов. При двух попытках статистическое семейство состоит из
8 сравнений, [агрегатор](aggregate.py) пересчитывает Holm для всех восьми.

Исследовательская цель Артёма — догнать KR mAP 0.774092. Это не обещание и
не критерий автоматической смены релиза: последний требует прежних границ
качества, отказа, скорости и доверительного интервала. Fusion 1024D, даже
если окажется лучше, требует отдельной версии API и перестройки индекса.
До этого релиз остаётся `d1_j48`, а экспериментальные checkpoint/ONNX и
разрешённые данные хранятся локально вне Git.

Статус: оба заранее объявленных продолжения обучены и проверены. Отдельная
сеть после второго продолжения достигла KR mAP **0.327450** на многократно
использованной val, против **0.774092** у релизной `d1_j48`. Её CPU batch-1
p95 на границе тензор → дескриптор составил **1.727 мс** против **43.861 мс**
у релиза в парном прогоне, но качества и отказа для смены релиза недостаточно.
Проверка комбинации с релизом тоже не прошла заранее заданный критерий.
Релиз остаётся `d1_j48`; таблицы, SHA, команды, ограничения и отрицательный
результат — в [отчёте](REPORT.md). Checkpoint и ONNX остаются в локальном
`outputs/`, не входят в сдаваемый сервис и не подменяют эталонные метрики.

Дополнительная [внешняя проверка на KPNEUMA](external-kpneuma/README.md)
охватила все 318 query/gallery-пар и парно сравнила ядро с релизом. На этом
другом домене превосходство ядра также не подтвердилось; числа не являются
оценкой закрытого теста ЛЦТ.
