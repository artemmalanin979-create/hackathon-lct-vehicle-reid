# Третья и четвёртая ветви — подтверждённого прироста нет

Проверяли: сдаваемая сборка **d1_j48** состоит из двух ветвей на входе 208 (OMZ OSNet-AIN
без дообучения + наша `combined_v1`). Даст ли прирост добавление третьей и четвёртой ветви
из уже обученных моделей? Модели с разным входом ошибаются на разных кадрах, и усреднение
иногда даёт то, чего не даёт ни одна.

Обучать ничего не требовалось — все веса были, считался только инференс и сборка.

Обозначения: **A** = OSNet@208, **B** = combined_v1@208 (это и есть d1_j48 = AB),
**C** = combined_256@256 (из job_68), **D** = OSNet@256, **E** = combined_v1@256.
Проверены все шесть расширений базы: ABC, ABD, ABE, ABCD, ABCE, ABDE.

Лучшее по точечной оценке — **ABD: +0,003782 mAP (0,28σ)**. Парный бутстрэп 4000:
CI95 [−0,003303; +0,010959], p = 0,309, **p после поправки Холма = 1,000**. Семейный
интервал Бонферрони [−0,005819; +0,013439] тоже включает ноль. При кластеризации по
vehicle_id — то же самое.

Ни одно из шести сочетаний не прошло заранее объявленный критерий (Δ > 0 **и** p_Holm < 0,05
**и** семейный интервал выше нуля). Порядок, число гипотез и критерий записаны в журнал
**до** просмотра результатов — иначе «победитель» находится всегда.

Цена при этом реальная: третья ветвь — это ещё один прогон сети на каждый кадр,
+77,7 % времени у ABD и до 2,8× у четырёхветочных.

## Что всё-таки видно

Rank-1 подрос у всех трёх сочетаний с ветвью на 256 (0,7368–0,7392 против 0,7308), а mAP —
нет. Это согласуется с тем, что вторая модель помогает поставить правильный ответ на первое
место, но не улучшает порядок всей выдачи. Прирост Rank-1 отдельно не проверялся как
гипотеза: критерий был заявлен по mAP, и менять его после просмотра чисел нельзя.

Пограничный случай: **ABCD на косинусе** дал семейный интервал [+0,000121; +0,017507] —
формально выше нуля, но p_Holm = 0,0510 > 0,05, а при кластеризации по vehicle_id интервал
уже включает ноль. Не засчитано. Косинус — не сдаваемый режим.

## Честность замера

Контрольная точка воспроизведена **побитово** до всех остальных расчётов: mAP
0,7740915539438481, Rank-1 0,7307692307692307, максимальная разница per-query AP с исходным
замером = **0,0**. Это единственная защита от того, что взяты не те векторы — и она
сработала: выяснилось, что `postproc/whitening/final/README.md` описывает прежний ансамбль
с `ain_v2`, и взять оттуда вторую ветвь было бы ошибкой.

Whitening для каждого сочетания обучен заново на own train_fit (7248 кропов, 1171 ID,
13 485 межкамерных пар), не на валидации. Веса ветвей равные, подбора не было.

Для ветви E пришлось извлечь недостающие train_fit-векторы — это инференс замороженной
модели, не дообучение; протокол в `features/extraction_info.json` на узле.

## Ограничение, которое надо помнить

Поправка на множественность здесь покрывает только эти шесть гипотез. Она **не исправляет**
того, что одна и та же валидация использовалась во множестве прошлых заданий. Накопленная
подгонка под этот сплит существует, и её величина не измерена — независимого закрытого теста
у нас нет.

## Вывод

Конфигурация не меняется: **d1_j48 @ 208, mAP 0,774092 / Rank-1 0,730769**.
