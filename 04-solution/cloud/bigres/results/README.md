# Больший вход без дообучения: хуже, и чем больше — тем хуже

21.09.2026, узел worker-vm, полная валидация (1110 запросов / 750 галереи), метрики
контуром `04-solution/eval/`, переранжирование (6, 3, 0,3).

| Вход | OSNet | combined_v1 | **d1_j48 (сдаваемая)** |
|---|---|---|---|
| **208** (наш) | 0,6937 | 0,7423 | **0,7741** |
| 256 | 0,6912 | 0,7242 | 0,7577 |
| 320 | 0,6400 | 0,6553 | 0,6865 |
| 384 | 0,5655 | 0,5731 | 0,6027 |

Деградация монотонная у всех трёх вариантов: на 384 сдаваемая конфигурация теряет
**0,171 mAP**. Одинаковость падения по всем моделям означает, что дело не в конкретных
весах, а в рассогласовании с масштабом, на котором модели обучались.

**Вывод.** Просто подать больший вход бесполезно. Если больший вход и может помочь
различать двойников (а измеренный резерв внутри первой десятки — +0,120), то только
через **дообучение на этом входе**. Потеря на 256 минимальна (−0,016), поэтому именно
256 — разумный размер для дообучения: рассогласование мало, и есть шанс отыграть его
с плюсом. 320 и 384 в 4 ГБ видеопамяти не помещаются без урезания батча.

Полные метрики (mAP, Rank-1, Rank-5, mINP на косинусе и переранжировании) —
`metrics-summary.json`. Скорость по входам — `benchmark.log` уровнем выше.
