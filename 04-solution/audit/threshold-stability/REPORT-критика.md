## 2. Методика: что корректно и где границы

**Разбиение корректное.** 832 known-запроса от 284 ID и 278 unknown-запросов от 74 ID; по 142 known-ID + 37 unknown-ID в половине. Все 200 разбиений воспроизведены из seed, полный охват и отсутствие пересечения ID проверены. Метрики взвешивают запросы, а группировка при разбиении — машины: это разные, здесь корректно разделённые операции. Ошибочная разбивка по запросам оставляет в среднем 245.78 общих ID между A/B и меняет знак результата.

**Симметризация корректная.** Автор вычисляет `0.5 * [(J_A(t_A)-J_B(t_A)) + (J_B(t_B)-J_A(t_B))]`, затем усредняет 200 значений. Перестановка A/B инвариантна. Нулевой результат для фиксированного порога — алгебраическое следствие формулы, не отдельное доказательство отсутствия переобучения. По критерию, который максимизировали, этот оптимизм также неотрицателен по построению: это полусумма двух потерь относительно собственных оптимумов.

**0.0353 — не граница статистически значимого улучшения.** В [README автора](evidence/author/README.md) меньшие улучшения объявлены шумом, а эффект сопоставлен с 0.0069 от выбора модели. Это не следует из расчёта: J40 и mAP — разные функционалы; средний selection optimism не является ни стандартной ошибкой, ни доверительным интервалом парной разности правил. Подбор на половине данных не даёт точную поправку к порогу, выбранному на всех данных. Более осторожные оговорки есть в полном [REPORT автора](evidence/author/REPORT.md), но они не спасают категоричность README.

**200 разбиений — не 200 независимых тестов.** Они повторно используют те же 358 ID. Все интервалы далее — квантили разбиений, не доверительные интервалы эффекта на скрытом тесте; биномиальные p-value по счёту побед не применялись. Исторический подбор модели/whitening на этой валидации данным аудитом не устранён.

**Критерий не выведен из ТЗ.** При чистом сдвиге долей `F1_p = 2(1-p)r / ((1-p)(1+r)+p*u)`, где r — recall, u — FPR. Он не возрастает по p: J40 = min(TNR,F1_0.40), J60 = min(TNR,F1_0.60). Точки 0.10 и 0.25 избыточны в max-min. При p=0 TNR потока не определена; используется её условное продолжение по исходным unknown-запросам. Сдвиг долей пересчитывает условные частоты, а не симулирует новую галерею или новый трансдуктивный граф. Веса F1/TNR в баллах жюри неизвестны; проверять правило по J60, выбранное по J40, допустимо как явно заданный стресс-тест, но нельзя выдавать его за единственную официальную оптимальность.

**Воспроизводимая находка: выбор по меткам проверочной половины не обнаруживается.** В отдельном комплекте вместо t_A подставлен t_B, затем честно пересчитаны и fit, и test при этом пороге. Эквивалентная однострочная мутация: [diff](evidence/mutation_select_test.diff). Неизменённый авторский `verify.py` завершился `passed` за 115.6 с: [результат](out/original_verifier_mutant.json), [код исходной проверки](evidence/author/verify.py), [воспроизведение](run_verifier_mutant.py). В том же комплекте намеренно неверная итоговая сводка тоже осталась незамеченной: verify.py её не читает.

Затем отдельно повторены те же 560 прямых fit/test вызовов оценщика с проверкой F1/TNR/recall: все прошли, max error = 0.0. [Native-проверки мутанта](out/mutant_native_generation_checks.json). Причина: оба слоя проверяют правильность метрик **при уже переданном пороге**, но не восстанавливают argmax только по A. Верификатор даже вычисляет переменную `fit`, не используя её для проверки выбора. Мой дополнительный guard восстанавливает источник выбора и отвергает 2800 из 2800 RR-строк мутанта. [Свидетели защит](out/mutation_guard_probes.json).

Старый SHA256SUMS, конечно, обнаруживает изменение байтов старого комплекта; здесь проверяется защита нового расчёта от логической ошибки, а не подделка неизменённого архива.

Это не обвинение исходного расчёта в утечке: его выборы независимо воспроизведены и корректны. Это доказанный пробел защиты, позволяющий получить противоположный вывод с зелёными проверками.

**Pooling — отдельная методическая чувствительность.** Усреднение J60 половин и расчёт J60 после объединения проверочных счётчиков не коммутируют. Второе даёт +0.006864 и 168 побед, сохраняя обучение на другой половине. Оно оценивает смесь двух обученных порогов по объединённым запросам; исходное — среднее качества двух половин. Ни один функционал нельзя молча подменять другим. Знак −0.0059 относится именно к исходному порядку операций, а не к любому честному сравнению.

## 6. Общий граф и проверка без общего query-контекста

В исходном расчёте переранжирование выполнено один раз на Q∪G; только затем score-строки разделены. В [rerank.py](inputs/04-solution/service/app/core/rerank.py) B влияет на A через нормировку расстояний, соседства и query expansion, и наоборот. **Прямого использования меток B в графе нет.** Для пакетного трансдуктивного inference это допустимый условный протокол. ## 7. Малые пакеты: фиксированное число и заново выбранное правило

**Именно численный t_rr не переносится на малые пакеты.** Простая повторная калибровка текущего правила на соответствующем режиме полезнее небольших отличий семейств правил. Другого правила, доминирующего во всех размерах, порядках и обеих метриках, измерениями не установлено; таблицы показывают, где wide60/blend дают честный локальный выигрыш. Это не повод выбирать единый новый t_rr по всей этой же валидации. Автор уже признавал пакетную проблему в полном REPORT; новое здесь — проверочный подбор по ID внутри каждого режима и сравнение правил, а не сам факт трансдуктивности.

Cosine-контроль: максимальный сдвиг score при chunking 1.33e-15, максимум смен решений 0. Перестановка всего RR-пакета без изменения состава: max score delta 4.44e-16, смен решений 0. Таким образом, основной эффект связан с составом контекста, а не просто с порядком строк. [Контроли](out/controls.json).

Малые RR-пакеты требуют своей проверенной калибровки либо уже предусмотренного cosine-пути; новый универсальный порог данным аудитом не утверждается.
