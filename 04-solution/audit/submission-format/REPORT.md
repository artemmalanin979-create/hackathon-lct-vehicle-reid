**Посимвольные оговорки.** В иллюстрациях README после запятых стоят пробелы, а в файлах их нет. ## Отказы и согласованность трёх файлов

Отказ кодируется **отсутствием всех строк данного query_id в candidates.csv**. Нет пустого `gallery_id`, `-1`, `null` или отдельной строки-маркера. Это соответствует документации batch (`service/README.md:149–150`, `core/submission.py:40–58`). ТЗ допускает «пустой ответ», но не уточняет его CSV-сериализацию; формат принятой реализации надо читать вместе с полным списком query.

В текущем комплекте **34 отказа из 1110 = 3,0631%**. [Список всех 34 query_id с индексом строки и максимальным score](evidence/refusals.csv). Наибольший максимум среди отказов — `0.528055264555317`, меньше порога `0.5282812306342437`; минимальный максимум принятого запроса — `0.5286152185894328`. Самая маленькая сохранённая уверенность принятого кандидата — `0.528464`. Противоречий с порогом в этом комплекте нет; правильность идентичностей/TNR по скрытой разметке здесь не утверждается.

|---|---:|---:|---:|---:|---:|---:|
| Запросов | 34 | 346 | 545 | 134 | 45 | 6 |

Проверка не ограничилась равенством размеров:

1. Порядок всех 1110 строк submission сравнили с `test_query.csv`, каждый из 11 100 gallery_id — с исходной галереей и своим пересчитанным рангом.
2. Из сохранённых 1860 векторов заново вычислили полную матрицу KR-score. Независимой стабильной сортировкой Python и явным сравнением `score >= threshold` построили ожидаемые строки, не вызывая production writer. **Все 1110 строк submission и все 2048 строк candidates совпали**, включая шесть десятичных знаков и порядок. Численная формула KR при этом взята из проверяемой реализации; это проверка целостности комплекта, а не независимое доказательство корректности алгоритма KR.
3. Каждый список candidates совпал с началом submission для того же query. У отказных запросов строка submission остаётся: усечение/фильтрация не потеряли query целиком. Группы candidates следуют порядку query с пропуском только 34 отказов; внутри группы порядок невозрастающий.
4. NPY не содержит image_id. Связь «строка массива → объект» проверена повторным извлечением из настоящих изображений с входным порядком query → gallery. [Построчная ведомость](results/full/row-by-row.csv) содержит для каждой позиции ID, bbox, SHA вектора выпуска и обоих новых прогонов, точное равенство и максимальную разницу.

В submission представлены все 750 ID галереи; в candidates — 718 из 750, поскольку остальные ни для одного query не проходят порог. Это ожидаемое отличие подмножества после фильтрации. [Счётчики ID](evidence/id-coverage.json).

Разные числа строк — 1860, 1110 и 2048 — следуют из трёх разных схем и сами по себе не являются расхождением. В UI-экспорте README:78–81 описывает отказ отдельной строкой без кандидата; это **другой экспорт API**, не сдаваемый `candidates.csv`. Противоречия с документацией batch здесь нет; подменять один файл другим нельзя.

Дополнительные проверки, вызванные наблюдавшимися результатами:

- **Идентичные singleton-пары:** `frame01`, `frame02`, `frame04` дают один `NaN` в score, предупреждение `invalid value encountered in divide`, `rc=0`, пустой candidates и счётчик «отказ». [Доказательство F1](results/extra/same_frame_01/r1/audit.json), [stderr](results/extra/same_frame_01/r1/stderr.log).
  Для всех пяти кадров query/gallery-векторы побайтно равны. У трёх проблемных кадров знаменатель нормировки ровно 0; у двух остальных он `4.44e-16` / `2.22e-16`, и деление округлительной погрешности на себя даёт дистанцию 1 и итоговую уверенность 0.7. [Численная диагностика](results/supplemental/degenerate-distance.json).
- **Ровно порог:** для `frame02 → frame14` сырой score и threshold `0.8729842587930721` совпадают, кандидат принят (`>=` корректно). В CSV записано `0.872984`, что **меньше указанного порога** примерно на `2.59e-7`. При следующем представимом float-пороге `0.8729842587930722` эта пара отвергается. Это проверка двух настоящих batch, а не ручной вызов writer. [Два прогона и параметры](results/supplemental/threshold-boundary.json).
- **Больше десяти:** на 15 галерейных кадрах при явно заданном конечном `--threshold 0` получены 30 строк candidates: **по 15 на каждый из двух запросов**; submission сохраняет обе строки, ровно по 10 ID. Порядок обоих файлов соответствует score. [Аудит](results/extra/more_than_ten_threshold_zero/r1/audit.json). При штатном пороге исходный fixture дал только три принятых кандидата, поэтому этого контроля без низкого порога было бы недостаточно.
- **Повтор в уже заполненный out-dir:** empty_gallery, corrupt_query и corrupt_gallery завершились с `rc=1`, а все четыре старых файла остались **побайтно прежними**. Это не успешная новая сдача. Для каждого случая сохранён отдельный каталог `existing_output/`; исходные `artifacts-final/` в опыте не участвовали.
- **Нулевой bbox:** zero_width, zero_height, zero_both и bbox полностью за границей дают одинаковый полностью нулевой тензор `(3,208,208)` и один и тот же ненулевой эмбеддинг; это подтверждено хешами. [Измерения тензоров](results/supplemental/crop-tensors.json). В этих конкретных опытах все отказы корректны относительно полученного score, но score вычислен по чёрной подложке, а не по ТС.

Каталоги [results/cases](results/cases/), [results/extra](results/extra/) и [results/supplemental](results/supplemental/) содержат команды, коды возврата, stdout/stderr, все созданные файлы и построчные проверки. Fixtures сохранены в [fixtures](fixtures/).

**Выпуск против нового окружения.** В обоих полных новых прогонах параметры и версии зафиксированы. Относительно исторического выпуска submission совпадает, а в candidates меняется только confidence в строке **185** (заголовок — строка 1): `68f05d38644e4af6a8b6cb1bef20c57a → f6061b71031b4ddb9384f86c103690a4`, `0.924793 → 0.924792`. Сырой KR-score этой пары: `0.9247925000183744 → 0.9247924988438161`; он пересёк границу округления до шести знаков. Все ID, пары, ранги и решения об отказе сохранены. [Точное отличие CSV](evidence/r1-candidates-vs-release.json).

Контроль причины выполнен ещё **двумя настоящими batch** на первых 32 query полного набора (тот же полный батч), с ONNX threads=2 и изменённым окружением потоков NumPy/OMP/MKL. При значении 1 все **32/32 эмбеддинга совпали с выпуском побайтно**; при исходном значении 2 и при снятых переменных окружения — 0/32 точных совпадений с выпуском. Максимальное отличие в этих пробах — `8.195638656616211e-08`. Это экспериментально подтверждает влияние потокового численного окружения без изменения модели, входов и исходников. [Сравнение двух проб](results/float-drift/comparison.json). Исторические настройки BLAS в run_info не записаны; эти пробы показывают воспроизводимый механизм различий, но не восстанавливают неизвестный полный набор настроек старого запуска. Дополнительного полного пересчёта всех 1860 кадров при однопоточном BLAS не было. Разница выпуска и нового окружения не выдана за случайный дрейф между двумя одинаковыми запусками.

`run_info.json` — служебный файл, к сдаче не требуется. Поля времени намеренно измеряются заново (`batch.py:109–111`), поэтому его побайтовое различие при одинаковых результатах не означает недетерминированность модели. Провалившиеся сценарии воспроизводят код ошибки; отсутствие выходов не названо побайтовым успехом.

## Что обязательно исправить перед заявлением о поддержке всех проверенных входов

1. Закрыть F1: вырожденное переранжирование, проверка конечности score, воспроизводимый self-match без ложного отказа.
2. Закрыть F2/F3: определить и реализовать согласованный формат для G<10, пустой галереи и пустого query; сейчас схема/комплект не выдерживаются.
3. Закрыть F4/F5: определить идентичность строки при нескольких bbox, проверять входную геометрию и изображения; ошибки ввода отличать от реального отказа модели.
4. Закрыть F6/F8: сделать видимый confidence согласованным с порогом и отклонять неконечный threshold.
5. Для повторного использования out-dir закрыть F9 либо обеспечить в запускающем процессе обязательную проверку успешного rc и свежести комплекта. Для F7 и оформления CSV закрепить договорённость: отсутствие лимита candidates и отсутствие пробелов в именах сейчас соответствуют собственной документации, но не формулировке «нигде больше десяти» из BRIEF.
6. Для заявлений о точном воспроизведении выпуска сохранять полный профиль вычислений (F10); допустимое численное расхождение и побайтовую идентичность не смешивать.

Это список необходимых изменений, **не выполненные исправления**. Текущие файлы нельзя объявлять повреждёнными только из-за дефектов на других входах; исправления должны сопровождаться отдельным выпуском и повторной проверкой.

## Условия и воспроизведение аудита

`worker-vm` был доступен по SSH; ошибка «Network is unreachable» из BRIEF в этом запуске **не воспроизвелась**. Никакой альтернативный узел/маршрут или суррогат вместо него не использован. Тяжёлые вычисления выполнены только на worker, в rootless Podman, лимиты **2 CPU / 4 GiB**, batch=32, ONNX threads=2, NumPy/OMP/MKL threads=2. Источники и исходные изображения смонтированы read-only, сеть контейнера отключена. Использован сохранённый runtime-образ с текущими неизменёнными исходниками и весами из snapshot; новая Docker-сборка не требовалась и не проверялась.

Исключение из настройки потоков — два явно отмеченных диагностических прогона `float-drift/`; их окружение сохранено отдельно. Локально выполнялись только чтение, хеширование, извлечение PDF, сравнение готовых небольших массивов и подготовка отчёта; инференса на основной машине не было.

[Preflight](results/preflight.json): совпали все 38 файлов snapshot и все 1860 настоящих тестовых JPEG с локальными SHA-256; версии Python 3.13.15, NumPy 2.5.3, Pillow 12.3.0, ONNX Runtime 1.30.0. Запуски не используют сохранённые эмбеддинги для инференса. Стандартная проверяемая команда:

```bash
python -B -m app.batch \
  --images-dir /data/images \
  --query /work/snapshot/data/test_query.csv \
  --gallery /work/snapshot/data/test_gallery.csv \
  --out-dir /work/results/full/r1/out \
  --batch 32 --threads 2
```

Точные команды каждого процесса находятся в `execution.json`, полный ход — [journal.md](journal.md) и [runner.log](evidence/runner.log).
