### 2.2. Протокол метрик и перенос порога

На неизменных validation-эмбеддингах и `t_rr = 0.5282812306342437` заново получено:

| Фильтр и смысл F1 | mAP по 832 допустимым query | F1 | TNR |
|---|---:|---:|---:|
| market; наличие пары (`presence`) | 0.7740915539438481 | 0.8090787716955942 | 0.7841726618705036 |
| market; правильность top-1 | 0.7740915539438481 | 0.6969292389853138 | 0.7841726618705036 |
| market; классификация всех пар | 0.7740915539438481 | 0.6411439114391144 | 0.7841726618705036 |
| Исключить всю ту же камеру; `presence` | 0.7823532718527061 | 0.8 | 0.7877697841726619 |
| Исключить всю ту же камеру; top-1 | 0.7823532718527061 | 0.703030303030303 | 0.7877697841726619 |
| Исключить всю ту же камеру; все пары | 0.7823532718527061 | 0.6474149976711691 | 0.7877697841726619 |

Доказательство — [свежий расчёт][Fresh]; определения — [Eval]:28–92 и функции расчёта refusal, [Scope]:18–31. `market` убирает только сочетание того же vehicle_id и той же camera_id. Более буквальная трактовка «совпадения в пределах одной ... камеры ... исключаются» убирает всю камеру, в том числе чужие ID. До эталонного скрипта нельзя объявлять одну трактовку официальной.

При включении всех **1110** запросов в знаменатель, с нулевым AP для 278 query без пары, market-mAP = **0.5802199755687222**. Значение **0.7740915539438481** относится к 832 query с релевантной галереей и полному ранжированию; это не mAP@10 из короткого submission. Фраза ТЗ «по всем запросам» делает выбор знаменателя существенным. Код умеет обе ветви, но наличие поддержки не подтверждает выбор организатора.

Для основной `presence`-ветви TP/FP/FN/TN = **606/60/226/218**. Положительный ответ здесь означает, что у query вообще есть пара в допустимой галерее; выбор чужого top-1 для известного query не превращает такое принятие в FP. Поэтому F1 0,809 нельзя подписывать как точность всех принятых ID или всех строк candidates.csv. В сыром Docker batch на validation **878** непустых ответов и 232 отказа; после камерной фильтрации metric-контур принимает **666 = 606 + 60**. Разница объясняется отсутствием скрытых ID/камерной фильтрации в сервисе, а не побайтовым расхождением артефактов. Первичные файлы: [DockerProof] и [validation run_info](evidence/docker-job75/val-batch/run_info.json).

Порог имеет явное обоснование: максимизация `min(TNR, F1_0.10, F1_0.25, F1_0.40)`, где `F1_p = 2(1−p)r / ((1−p)(1+r)+pf)`. Это следует из определения F1; доли 0.10/0.25/0.40 выбрала команда, они не заданы ТЗ. Точный порог API/cosine — **0.5141976914190476**; порог batch KR — **0.5282812306342437**. Обе шкалы и правило равенства описаны в [Doc]:313–347. Независимого holdout для выбора и оценки порога нет.

Проверен конкретный перенос между составами query. У validation query №0 с `vehicle_id=397` нет пары среди неизменных 750 gallery:

| Режим | Максимальный score | Ответ при соответствующем рабочем пороге |
|---|---:|---|
| Cosine | 0.466739518167381 | Отказ |
| KR со всеми 1110 query | 0.3039154832040669 | Отказ |
| KR только с этим query и той же gallery | 0.863915483204067 | Ложное принятие |

Это воспроизводимый контрпример переносимости KR-порога, а не оценка частоты ошибки на новом тесте. KR использует весь набор query/gallery. HTTP API работает на cosine и не наследует этот конкретный скачок; при запуске batch на другой группе query требуется отдельная проверка. Автоматического защитного переключения KR на cosine в коде нет. [Свежий протокол][Fresh], [RR]:13–34, [Rank]:24–54.

### 2.3. Контракт входов, выхода и ошибок

Имеющийся `data/README.md` задаёт `test_query.csv` и `test_gallery.csv`, а также порядок NPY «сначала query, затем gallery». Это конкретизация выданного архива; общее ТЗ называет один `test.csv`. Фактический train содержит camera_id с 96 значениями вопреки §5. Эта колонка не поступает в inference, но участвует в подготовке обучения/sampler/MCNL. Утверждать, что камера вообще нигде не использована, нельзя. Время/геокоординаты в найденных входах не обнаружены. [Inventory], [P]:29–44, [Train].

Batch сохраняет BBox каждой строки и NPY по строкам. Однако контракт ID и HTTP `bbox_of(image_id)` неоднозначен, если один image_id связан с несколькими BBox: выбирается первая строка. Фактический README архива обещает один объект на image_id, в отличие от общего ТЗ о нескольких ТС на кадре. На текущем наборе это не показанный сбой; на другом допустимом по ТЗ наборе нужен object ID/согласованный контракт. [Store]:68–90, [Submit]:19–37.

`candidates.csv` имеет **2048** строк принятых пар, покрывает **1076** query; для **34** отказов строк нет. Оценки конечны, в диапазоне 0.528464–0.998920; порядок query/состав пар воспроизведён. В API корректный отказ — HTTP 200 и пустой `candidates`. Для CSV отсутствие строк логично представляет пустой список, но официальный parser/sentinel не предоставлен, поэтому T08.4 частичен. Submission при этом содержит top-10 для всех query, включая отказанные: это отдельные артефакты с разным назначением. [Inventory], [Fresh], [Submit]:40–64, [API]:159–181.

Не следует смешивать модельный отказ с инфраструктурной ошибкой. Недоступная Qdrant возвращает **503**, пустая галерея — **409**, невалидный image/BBox — **422**; это не «машина отсутствует в базе». Пустой входной batch завершается ошибкой, OOM не преобразуется в корректный CSV-отказ. Перед порогом используется полная точность score, а confidence округляется только в ответе/CSV. [API]:145–181, [Batch]:69–71, [Submit]:40–64.

### 2.4. Внешние ресурсы и остаточные признаки номера

Исходный ONNX размером 8 836 743 байта сверён по SHA-384 с [pinned-карточкой Open Model Zoo 2022.1.0](https://raw.githubusercontent.com/openvinotoolkit/open_model_zoo/2022.1.0/models/public/vehicle-reid-0001/model.yml): [машинная сверка](evidence/omz-source-check.json). Она ссылается на MIT-лицензию модели; Apache-2.0 в заголовке YAML нельзя автоматически переносить на веса. [MIT исходной ветки](https://raw.githubusercontent.com/sovrasov/deep-person-reid/vehicle_reid/LICENSE) требует сохранить уведомления об авторстве и разрешении. Отдельного notice для OSNet в поставке не найдено.

[University of Bath](https://researchdata.bath.ac.uk/1574/) маркирует RoundaboutHD.zip как «Software: MIT License», Version 1. Это полезное подтверждение опубликованного экземпляра, но соответствие исторической HuggingFace-выгрузке команды ещё нужно установить. [CARLA-ReID автора](https://github.com/sekilab/VehicleReIdentificationDataset) содержит Apache-2.0 для репозитория и ссылку на внешний архив; отдельные условия каждого изображения из ZIP не установлены. Все **6068 + 7260 = 13 328** реально использованных внешних кадров сопоставлены с локальными архивами в имеющихся source-checks. Это доказывает состав, но не восстанавливает отсутствующую историческую revision или неизвестные upstream-данные OSNet.

В [исходной реализации k-reciprocal](https://github.com/zhunzhong07/person-re-ranking) при проверке не найден LICENSE; локальный [RR]:8–11 прямо называет реализацию портом. Ссылка на статью сама по себе не устанавливает право распространения кода. Права на конкретный код и возможность независимо реализовать опубликованный алгоритм — разные вопросы. В комплекте при этом **есть** FastReID/Torchreid LICENSE и лицензионные файлы wheels; утверждать полное отсутствие лицензий было бы неверно. Полный реестр с первичными ссылками и границами выводов — [LicenseReview]. Решение о конкурсном допуске принадлежит организатору; неизвестность не объявляется доказанным нарушением.

Runtime обрезает автомобиль целиком; маскирования номера нет. OCR отсутствует, но это не доказывает неиспользование residual-пикселей номера. В d1_j48 plate-ablation все шесть парных 95%-интервалов включают ноль; например, gray/cosine даёт ΔmAP −0.008218, CI [−0.016975; +0.000289], p=0.0625. Это отсутствие статистически установленного эффекта в данном опыте, а не доказанная независимость модели от номера. Детектор не нашёл пластину на 6 query и 7 gallery; эти 13 изображений остались без маски. Полные входы/экстракторы опыта не поставлены в Git, что также мешает независимому повторению. [Plate] и [Doc]:352–399.

### 2.5. Поставка и расхождения документации

Подтверждены настоящая Docker-сборка и работа с настоящей Qdrant, а не только Podman/воспроизведение metric-скрипта. Первичный прогон использовал Docker Engine 29.7.2, Compose v2.40.3, Buildx 0.37.1, BuildKit 0.32.2, изолированный от внешней сети daemon. Полный validation-инференс занял **1456,549 с**, batch целиком — **1461,778 с**, `oom_kill=0`. Общий лимит slice там был **6 GiB**, поэтому этот конкретный лог не является доказательством полного Docker-стека в 4 GiB. 4 GiB подтверждены отдельным прежним прогоном inference; новый job_77 тоже ограничен 4 GiB, но пересчитывает только ранжирование/метрики. [DockerProof], [ReproProof].

В Docker-прогоне ядро SELinux было Enforcing, но daemon работал без `--selinux-enabled`.
