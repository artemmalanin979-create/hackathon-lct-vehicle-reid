# Docker-путь пройден, и порог переранжирования зависит не от размера галереи

22.09.2026. До этого вся офлайн-сборка проверялась только на Podman: инструкция для Docker
была написана и ни разу не выполнена. Заодно закрыт второй пробел — сценарий проверялся на
десяти контрольных объектах вместо штатных 750.

## Docker

Стенд: Fedora 44, **Moby/Docker Engine 29.7.2**, Buildx 0.37.1, BuildKit 0.32.2, containerd
2.3.5, Compose **V2 2.40.3** (в репозиториях Fedora уже 5.5.1, для буквальной проверки V2
поставлен официальный бинарник с проверкой SHA-256). Настоящий демон Docker, не совместимый
CLI Podman.

Путь пройден целиком: пустое хранилище образов → загрузка обоих архивов из `offline/` →
проверка весов из клона → сборка без кэша → `pip check` и совпадение всех 31 версии с
lock-файлом → запуск через Compose → работающий сервис.

**Команда сборки из `SOLUTION.md` §3 оказалась верной** — `docker build --no-cache
--pull=false --network none`. Отдельно подтверждено, что `--pull=never` в Docker не
работает: парсер отвергает `never` как неверное булево значение (это флаг Podman).

**Чего в документации не хватало** — как именно изолировать сам демон. `--network none`
отрезает сеть у шагов `RUN`, но базовый образ тянет демон, до них. Проверенный способ на
systemd, не трогающий сеть узла и SSH:

```bash
sudo systemd-run --unit=job75-docker --slice=job75.slice \
  --property=PrivateNetwork=yes --property=Delegate=yes \
  --property=TasksMax=infinity --property=Restart=no \
  /usr/bin/dockerd --config-file="$TASK/docker-daemon.json" \
  --data-root="$TASK/docker-data" --exec-root=/run/job75-docker \
  --pidfile="$TASK/dockerd.pid" --host="unix://$TASK/docker.sock" \
  --cgroup-parent=job75.slice --debug
```

Отрицательный контроль сделан: при отсутствующем базовом образе Docker пытается получить
манифест и упирается в отключённую сеть демона — то есть изоляция проверена не только на
успешном прогоне.

## Полная галерея

Полный пакет 1110 × 750 пересчитан заново в свежем Docker-образе, с извлечением признаков
из исходных JPEG и отключённой сетью. Метрики совпали с опубликованными: **mAP
0,7740915539 / Rank-1 0,7307692308**, отказ F1 0,8090787717 / TNR 0,7841726619. Штатная
калибровка на новых векторах повторно выбрала те же пороги с расхождением 1,0·10⁻⁸ и
2,7·10⁻⁹ — это дрожание float32, а не смещение.

## Главное: порог переранжирования зависит от состава пакета запросов

Прошлый аудит нашёл на галерее из 10 объектов, что переранжирование принимает то, что
косинус отказывает. Проверка на 750 показала, что дело **не в размере галереи**.

Взят настоящий чужой автомобиль — кадр `64a7b342e5654ac38e16ab1cc2d58037`, vehicle_id 397,
которого нет ни в одной из 750 записей галереи. Векторы запроса и галереи во всех строках
одни и те же; меняется только то, какие **другие** запросы поданы вместе с ним:

| Контекст | Косинус | Переранжирование |
|---|---|---|
| один запрос × 750 | 0,4667 — отказ | **0,8639 — ложное принятие** |
| пять запросов × 750 | 0,4667 — отказ | **0,8639 — ложное принятие** |
| все 1110 запросов × 750 | 0,4667 — отказ | 0,3039 — отказ |

Это свойство k-reciprocal: он трансдуктивный и строит взаимные окрестности по всему пакету
запросов. Порог `t_rr` откалиброван на полном пакете из 1110 запросов и на него же
переносится корректно — но **на одиночный запрос или небольшой пакет он не переносится**.

Практически нас это не ломает: одиночный путь в API работает на косинусе, который во всех
строках таблицы отказал правильно. Переранжирование применяется в пакетном режиме, где
контекст полный. Но ограничение в `SOLUTION.md` §2 должно остаться, и формулировать его
надо через **состав пакета запросов**, а не через размер галереи: условия «в галерее 750»
недостаточно.

Серый кадр, который на маленькой галерее принимался, на 750 отказывается во всех
контекстах — тот конкретный пример был эффектом малого набора, но вывод от этого не
меняется.
