# Задание: пройти путь жюри — собрать решение с нуля как посторонний человек

Работай молча. Веди `journal.md`, **дописывая отчёт по ходу**. Один финальный
структурированный отчёт по-русски. Никаких фоновых задач.

## Зачем

ТЗ (разд. 9): решения, **не воспроизводящиеся из предоставленного кода, к оценке не
допускаются**. Организатор запускает наше решение сам, на своей машине, по нашей
документации, не задавая вопросов.

За последние сутки в решение внесли много правок: переранжирование в пакетный прогон,
новый порог отказа, переработанный веб-интерфейс, колёса зависимостей для офлайн-сборки.
Каждая проверялась по отдельности. **Никто не проходил весь путь целиком после них.**

## Правило этой работы

**Ты — посторонний человек.** Ты не знаешь, как устроен проект, и не имеешь права
догадываться. Единственный источник — документация:
`SOLUTION.md` (копия рядом: `context-solution.md`) и README внутри репозитория.

Если команда из документации не работает — это **находка**, а не повод найти обходной
путь по своему разумению. Записывай: что запускал, что ожидал, что получил.

## Что сделать

### 1. Чистый клон

Склонируй репозиторий в **новый каталог вне рабочего дерева** (например,
`/tmp/claude-1000/.../job_32/clean/`), из локального origin:

```
git clone /home/artem/projects/hackathon-lct-vehicle-reid clean
```

Клон покажет ровно то, что уедет жюри: **без** всего, что в `.gitignore` — без данных,
без весов, без векторов.

### 2. Пройти документацию сверху вниз

Выполняй команды из `SOLUTION.md` по порядку, как написано, и отмечай результат каждой.
Особое внимание:

- получение весов (их в клоне нет);
- сборка образа — **и с сетью, и без сети** (в решении есть каталог колёс);
- запуск пакетного прогона на тестовом наборе;
- поднятие сервиса и веб-интерфейса;
- воспроизведение чисел из таблицы «число → команда».

Данные организатора в клон не попадут (они в `.gitignore`) — возьми их по пути
`/home/artem/projects/hackathon-lct-vehicle-reid/data`, **только на чтение**. Это
законно: жюри получит данные со своей стороны.

### 3. Сверить результат

Сдаваемые файлы, полученные твоим прогоном из чистого клона, сравни с
`04-solution/service/artifacts-final/` в рабочем дереве. Должны совпасть побайтово
(`submission.csv`, `candidates.csv`) и бит-в-бит (`embeddings.npy`).

**Расхождение — самая важная находка этой работы.** Оно означает, что то, что мы
сдаём, не воспроизводится из того, что мы отдаём.

### 4. Проверить, что заявленные числа получаются

Возьми главные числа решения — mAP 0,694, Rank-1 0,663, F1 0,806, TNR 0,777 — и
проверь, что команды из документации их дают. Не «примерно», а точно.

## Чего не делать

- Не чинить найденное. Твоя работа — найти и описать, чинить будут отдельно.
- Не подглядывать в рабочее дерево, чтобы «понять, как надо». Только документация.
  Исключение — данные (п. 2) и сверка результата (п. 3).
- Не оставлять после себя поднятых контейнеров и мусора: прибери за собой, клон удали
  в конце (сначала сняв всё нужное для отчёта).

## Про окружение

Docker на машине нет — есть `podman` 5.8.2 и `podman-compose` 1.6.0. Команды в
документации докеровские; выполняй их подменой, но **отмечай каждое место**, где
подмена понадобилась: у жюри будет docker, и разница может быть значимой.

## Формат отчёта

`REPORT.md`: таблица «шаг документации → команда → результат → вердикт»; список находок
по убыванию тяжести; результат сверки артефактов; какие заявленные числа
воспроизвелись, а какие нет; сколько времени занял весь путь.
