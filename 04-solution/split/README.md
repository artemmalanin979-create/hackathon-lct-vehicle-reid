# Проверочный сплит

Выданный тест мерить нечем — в нём нет `vehicle_id`. Проверочную выборку строим сами,
из обучающей, по правилам организатора.

**Если сплит нечестен, все дальнейшие числа врут в приятную сторону** — и узнаем мы об
этом от жюри, а не от себя. Поэтому сплит сделан первым, до всякой модели.

Полный отчёт — [`REPORT.md`](REPORT.md).

## Что получилось

| Роль | Кадров | Идентичностей |
|---|---:|---:|
| `train_fit` | 7 248 | 1 171 |
| `val_query` | 1 110 | 369 (832 запроса с парой + 278 отказных) |
| `val_gallery` | 750 | 294 |
| не используется | 448 | кадры проверочных идентичностей вне протокола |

448 кадров выброшены сознательно: это кадры проверочных машин, и отдать их в обучение
значило бы устроить утечку. Цена честности — 4,7 % данных.

Структура повторяет выданный тест: те же 1110 запросов на 750 объектов галереи, та же
дедупликация галереи (747 «серий» на 750 кадров против 748 на 750 у организатора).

## Чем это честно

| Свойство | Результат |
|---|---|
| Идентичности обучения и проверки не пересекаются | 1171 ∩ 370 = ∅ |
| У каждого запроса с парой есть совпадение **с другой камеры** | 832 из 832 |
| Часть запросов заведомо без пары — материал для режима отказа | 278, расхождений с разметкой 0 |
| Пары скопированных кадров не разъехались по разные стороны | 9 из 9 |
| Воспроизводимость | двойной запуск даёт совпадающие sha256 |

Доля отказных запросов — 25 %, параметр `--p-refusal`. Выбрана **до** любых прогонов
метрик: истинная доля в тесте неизвестна, гарантировано лишь, что отказные там есть
(иначе метрика TNR из ТЗ не имела бы смысла).

## Чем доказано, что проверяльщик работает

Проверяльщик не подтверждает, что всё хорошо, — он обязан падать, когда плохо. Сплит
намеренно испортили четырьмя способами, и каждый раз падала **ровно та** проверка,
которая должна:

| Порча | На чём упал |
|---|---|
| Кадр проверочной машины переложен в обучение | «идентичности в обеих частях: [397]» |
| У машины удалён кадр со второй камеры | «2 запроса: совпадения только с той же камеры» |
| Пара скопированных кадров разведена по сторонам | названы оба `image_id` разошедшейся копии |
| «Отказному» запросу подложена пара в галерее | «3 запроса: has_mate=0, но идентичность есть в галерее» |

## Как выглядит метрика, когда мерить нечего

Два вырожденных прогона через измерительный контур:

| Метрика | Случайные векторы, ожидание | Получено (3 seed) | Идеальные векторы |
|---|---:|---|---:|
| mAP | 0.0103 | 0.0134 / 0.0096 / 0.0114 | **1.0** |
| Rank-1 | 0.0020 | 0.0048 / 0.0012 / 0.0036 | **1.0** |
| mINP | 0.0081 | 0.0113 / 0.0076 / 0.0095 | **1.0** |

Ожидания посчитаны аналитически из состава галереи, а не взяты на глаз. Все отклонения
в пределах 1,5 стандартной ошибки.

Отдельно: `filtered_queries = 0` — ни один запрос не остался без верных совпадений после
исключения своей камеры. Это подтверждает кросс-камерность сплита уже средствами контура,
независимо от проверяльщика.

## Запуск

```bash
python3 make_split.py [--out DIR] [--seed N] [--p-refusal F]
python3 check_split.py files/ [--full-scan]
python3 eval_degenerate.py     # вырожденные прогоны
```

## Открытое

Порог отказа калибруется на доле 25 %, а истинная доля в тесте неизвестна —
чувствительность к ней стоит проверить прогонами с 10 % и 40 %.

Семантика `camera_id` не документирована: часть меток, возможно, дробит или склеивает
физические точки. Если две «разные» камеры — на деле одна точка, часть наших
кросс-камерных пар окажется одноместными, и метрика будет слегка завышена. На выданном
тесте это не проверить.
