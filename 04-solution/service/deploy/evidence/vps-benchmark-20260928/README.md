## Метод и результат

Перед каждым прогоном было 2 прогрева. Затем 10 последовательных и 8 запросов
при concurrency=2. В каждой серии поровну принимаемый и отказной демо-кадр;
меток истинной идентичности у этих изображений нет.
Клиент измерял время от начала HTTP-запроса до полного чтения JSON; новая
TCP/TLS-сессия возможна для каждого запроса. p95 = nearest-rank, поэтому при
`n=8` и `n=10` это просто максимум выборки. Полные времена и коды — в JSON.

| Путь | c | n | HTTP | p50, с | p95, с | Запросов/с |
|---|---:|---:|---|---:|---:|---:|
| На VM, `127.0.0.1:18071` → API | 1 | 10 | 10 × 200 | 0.141 | 0.149 | 7.05 |
| На VM, `127.0.0.1:18071` → API | 2 | 8 | 8 × 200 | 0.281 | 0.282 | 7.12 |
| С dev-машины, HTTPS к **84.201.146.191** с SNI `iamcp.ru` | 1 | 10 | 10 × 200 | 0.833 | 1.422 | 1.10 |
| С dev-машины, HTTPS к **84.201.146.191** с SNI `iamcp.ru` | 2 | 8 | 8 × 200 | 0.696 | 1.362 | 2.42 |

Loopback включает обработку API, ONNX и Qdrant, но не внешнюю сеть и Caddy.
HTTPS включает также сеть, TLS, Caddy и загрузку JPEG. **Разность времен не
является измерением «чистого сетевого RTT» или отдельно ONNX-инференса**:
прогоны последовательны, клиентские хосты и версии Python различаются, выборка
мала. При concurrency=2 медианная задержка на VM выросла, общий
throughput остался примерно 7 запросов/с. Поведение при большей конкуренции,
пик RAM, холодный старт и аппаратная скорость по официальному протоколу не
измерены.

## Команды и DNS

Команды ничего не записывали на VM и не перезапускали контейнеры. Файл
[`benchmark.py`](benchmark.py) использует только стандартную библиотеку Python.

```bash
ssh -o BatchMode=yes lct2026-vps 'python3 - http://127.0.0.1:18071' \
  < benchmark.py > direct-localhost.json
LCT_PINNED_IPV4=84.201.146.191 python3 benchmark.py https://iamcp.ru \
  > pinned-https.json
curl --resolve iamcp.ru:443:84.201.146.191 \
  https://iamcp.ru/api/health
```

На dev-машине системный DNS и прямые `dig @1.1.1.1` / `@8.8.8.8` в это время
отдавали старый `89.35.130.50`, тогда как DoH Google и Cloudflare и DNS самой
VM отдавали новый `84.201.146.191`. Это расхождение резолверов/кэша; тест
HTTPS закрепил новый IP, сохранив имя для TLS. Предыдущий
[`20260928-live-http.json`](../20260928-live-http.json) не записал фактически
использованный IP, поэтому его нельзя уверенно приписать прямому маршруту на
новую VM. Реальная доступность по обычному DNS требует проверки из нескольких
внешних сетей.

Независимая проверка маршрута в 22:43 UTC после бенчмарка:
`curl --noproxy '*' --resolve iamcp.ru:443:84.201.146.191 ... /api/health`
вернул `remote_ip=84.201.146.191 http_code=200`. Сам `benchmark.py` записывает
настроенный `pinned_ipv4`, но не IP каждого состоявшегося соединения;
раздельный `curl` не заменяет этот отсутствующий per-request лог.

[`pinned-https.json`](pinned-https.json). Exit code обеих команд: **0**;
