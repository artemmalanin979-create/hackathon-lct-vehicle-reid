# Веб-интерфейс сервиса: что сделано и как проверено

Правки на месте: `/home/artem/projects/hackathon-lct-vehicle-reid/04-solution/service/`.
Снимки экрана — `shots/`, выгруженные из интерфейса файлы — `exports/`,
протоколы проверок — `checks/`, ход работы — `journal.md`.

## Что появилось

Было: `app/static/index.html`, 78 строк — одна форма, один `POST /api/search`,
таблица «идентификатор + число». Стало: рабочее место оператора на трёх файлах
без единой внешней зависимости (`index.html`, `app.css`, `app.js`).

### 1. Кандидаты картинками, с читаемой оценкой

Каждый кандидат — карточка: кроп объекта, ранг, идентификатор, уверенность
крупно, запас до порога числом и полоса, на которой порог отмечен риской.
Переключатель **«кадр целиком»** показывает тот же объект в сцене камеры —
оператор видит не только машину, но и обстановку, в которой её сняли.

Картинки отдаёт новый метод `GET /api/gallery/{id}/crop?view=crop|frame&size=`.
Рамка берётся из payload точки Qdrant — из того же источника, по которому шёл
поиск, поэтому показанный кроп не может разойтись с тем, что сравнивала модель.

Снимки: `shots/03-match.png`, `shots/08-frame-view.png`.

### 2. Отказ как ответ, а не как пустой экран

Отдельная панель: шкала косинуса от 0 до 1 с отметками достигнутой близости и
порога, чего именно не хватило (`−0.172195`), сколько объектов просмотрено
(750). Формулировка прямая: «Галерея просмотрена целиком, ни один объект не
прошёл порог. Это ответ системы, а не сбой».

По явному действию оператора — **«Показать ближайшие ниже порога»**: тот же
`/api/search` с порогом −1, кандидаты помечены «ниже порога», синей полосой и
предупреждением, что совпадением они не являются. Отказ при этом остаётся на
экране: это материал для ручной проверки, а не отмена решения.

Снимки: `shots/04-refusal.png`, `shots/05-below.png`.

### 3. Выгрузка результата

Кнопки **CSV** и **JSON** в заголовке результата. Файл собирается в браузере из
того же ответа API — ничего не пересчитывается.

CSV: `query_image, query_x, query_y, query_w, query_h, top_k, threshold,
refusal, best_confidence, rank, gallery_id, confidence, above_threshold`.
Отказ выгружается строкой без кандидата — файл фиксирует «проверено,
совпадения нет», а не остаётся пустым. Если оператор раскрыл кандидатов ниже
порога, они попадают в выгрузку с `above_threshold=0`.

JSON: то же плюс версия сервиса, модель, шкала оценки, размер галереи и метка
времени.

Готовые файлы из прогона — `exports/` (`match.*`, `refusal.*`,
`refusal-with-below.*`).

### 4. Запрос задаётся по-человечески

Кадр выбирается файлом или перетаскиванием. Рамка обводится **мышью прямо по
кадру**: протяжка создаёт рамку, перетаскивание внутри двигает, восемь ручек
растягивают; область вне рамки затемняется. Поля `x/y/w/h` синхронны с рамкой в
обе стороны — если координаты известны точно, их вводят числами. Кнопка «весь
кадр» — для готовых кропов.

Снимок: `shots/02-query.png`.

### 5. Состояния сервиса вместо ошибок в консоли

Новый метод `GET /api/ui/state` отдаёт клиенту одним запросом состояние
хранилища, порог, доступность кадров и разбора. Интерфейс показывает:

| Состояние | Что видит оператор |
|---|---|
| галерея загружена | метка «галерея: 750 объектов», форма активна |
| галерея не загружена (409) | полоса «Галерея не загружена» + команда загрузки, кнопка поиска заблокирована |
| хранилище недоступно | полоса «Хранилище галереи не отвечает» + команда запуска |
| кадры не смонтированы | поиск работает, в карточках вместо картинок — пояснение |

Снимки: `shots/07-no-gallery.png`, `shots/09-no-storage.png`.

### 6. Объяснимость: на что смотрела модель

Кнопка **«разбор»** у кандидата открывает точное разложение оценки близости по
областям обоих изображений: `POST /api/explain`. Красным — области, которые
поддерживают совпадение, синим — которые его снижают; величину несёт
прозрачность, шкала подписана числами в единицах близости. Палитра и правило
отрисовки те же, что в листах `04-solution/explainability/pics/`, — показ в
браузере и иллюстрации к защите выглядят одинаково.

Рядом с картой — числа, по которым видно, чего карта стоит: близость пары,
сетка признаков 13×13, доля вклада 10 % самых горячих ячеек и **невязка
разложения** (2,4·10⁻⁸). Разложение — тождество, а не приближение, и сервис
показывает это на каждом вызове.

Снимок: `shots/06-explain.png`.

**Как это сделано без новых зависимостей.** Эталон
(`04-solution/explainability/scripts/contrib.py`) импортирует пакет `onnx`:
правит граф ради карты признаков и читает инициализаторы аффинной головы. В
сервисе `onnx` нет, а добавлять его в проверенный офлайновый набор wheels ради
необязательной возможности неправильно. Поэтому `app/core/explain.py` делает то
же на стандартной библиотеке: минимальный разбор protobuf читает из файла весов
веса головы и `epsilon` узлов BatchNormalization, а копия графа с дополнительным
выходом собирается в памяти (`onnxruntime` принимает `bytes`). Производных
артефактов на диске не появляется — всё выводится из тех же весов, чья sha256
проверяется при запуске.
