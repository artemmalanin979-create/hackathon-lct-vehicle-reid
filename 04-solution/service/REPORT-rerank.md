# Отчёт job_14 — переранжирование в сдаваемом сервисе и порог на новой шкале

Дата: 2026-09-15. Правки — в рабочем каталоге репозитория
`04-solution/service/` (не закоммичены, см. § 8). Свидетельства прогонов — в
`work/`, ход работы — в `journal.md`, скрипты — в `scripts/`.

Короткий итог: переранжирование встроено в пакетный прогон и включено по
умолчанию; при выключенном флаге прогон даёт **побайтово прежние** файлы;
`embeddings.npy` во всех режимах **бит-в-бит** один и тот же. Порог отказа
перекалиброван на новой шкале тем же правилом, что и прежний, и оказался лучше
прежнего **сразу по обоим показателям**: F1 0,806 против 0,733, TNR 0,777 против
0,698. Предупреждённый в задании риск («разделение стало хуже») не наступил —
наступил другой, названный в § 6.

## 1. Что изменено в сервисе

| Файл | Что сделано |
|---|---|
| `app/core/rerank.py` | **новый**: k-reciprocal (Zhong 2017) на numpy + перевод дистанции в уверенность `1 − d` |
| `app/core/config.py` | параметры `RERANK_*` (6, 3, 0,3) и **второй** порог `DEFAULT_THRESHOLD_RERANK`; у каждого числа указано происхождение |
| `app/batch.py` | флаги `--rerank / --no-rerank`, порог по умолчанию выбирается под шкалу, в `run_info.json` добавлены шкала, параметры и `rank_elapsed_s` |
| `app/core/ranking.py`, `app/core/submission.py` | только докстроки: «косинус» → «скор выбранной шкалы». Код не тронут |
| `app/api/main.py` | `/api/version` печатает обе шкалы и оба порога; в `_search_by_vector` зафиксировано, почему онлайновый путь остаётся косинусным |
| `tools/eval_split.py`, `tools/calibrate_threshold.py` | **новые**, в образ не копируются: воспроизведение чисел README (метрики контуром, калибровка порога) |
| `README.md` | переранжирование, два порога, поведение на выданном тесте, команды воспроизведения |

Конструктивное решение одно и оно влияет на всё остальное: переранжирование
возвращает **дистанцию**, а сервис живёт в шкале «больше = лучше», поэтому сразу
после расчёта дистанция переводится в уверенность `1 − d`. Благодаря этому
`ranking.py` и `submission.py` не менялись, и выключенный флаг ведёт прогон
ровно прежним кодом. Проверено, что перевод ничего не портит: на матрице
1110×750 порядок по убыванию `1 − d` совпал с порядком по возрастанию `d` **во
всех 1110 строках**, число различимых значений одинаково (832 015).

Порт переранжирования сверен с экспериментальной реализацией
`postproc/scripts/common.py::rerank`: **max|diff| = 0,0, матрицы бит-в-бит равны**
(`work/split/check_port_split.json`).

Требования задания, выполнение по пунктам:

- `embeddings.npy` не меняется — файл пишется **до** переранжирования; проверено
  сравнением (§ 2);
- переранжирование отключается флагом `--no-rerank` (или `REID_RERANK=0`) —
  проверены оба способа, а также `--threshold` и `REID_THRESHOLD_RERANK`
  (прогоны на урезанном наборе 20×20, `work/mini/`);
- пакетный прогон не зависит от хранилища и сети: после `import app.batch` в
  `sys.modules` нет ни FastAPI, ни qdrant-client, ни http-клиентов; прогон в
  контейнере с `--network none` проходит (§ 5).

Прогон сервиса на нашем сплите (`split/files/val_query.csv`, `val_gallery.csv`),

Сверка с экспериментом (`postproc/out/final_val.json`): числа совпадают **до

скриптов.

Два контроля шкалы:

- та же матрица, поданная контуру как **дистанция** (`score_kind="distance"`, это

Цена переранжирования по времени (из `run_info.json`): 0,98–1,83 с на полный
прогон против 69–128 с извлечения векторов. Замеряемое организатором время
«изображение → вектор» не затронуто. Память на 1860 объектах: пик выделений
169 МиБ, maxRSS 219 МиБ.

(импорт без изменений) поверх неизменённого контура; правило зафиксировано до
просмотра результатов — **максимум от `min(TNR, F1 при долях отказных 0,10 /
0,25 / 0,40)`**. Каждая объявленная рабочая точка сверена напрямую с контуром:
185 сверок, max |ошибка| < 2·10⁻¹².

## 5. Прогон в контейнере с отключённой сетью

1. `podman build --no-cache -t vehicle-reid-service ./service` — успех, на шаге
   проверки печатается «веса модели в образе, sha256 OK». Образ пересобран
   **после** последней правки исходников, и сверка ниже повторена на нём.
2. Негативный контроль: `podman run --rm --network none … urlopen('https://example.com')`
   → `URLError: Temporary failure in name resolution` — сеть действительно отрезана.
3. Пакетный прогон офлайн, режим по умолчанию: успех за 100,5 с,
   `{"queries": 1110, "gallery": 750, "embeddings_shape": [1860,512], "rerank": true,
   "queries_refused": 32}`; Qdrant не поднимался.
4. Тот же прогон с `--no-rerank`: успех, 48 отказов.
5. Сверка с хостом: в обоих режимах `submission.csv`, `candidates.csv`,
   `embeddings.npy` **побайтово** совпали с хостовыми файлами, несмотря на другой
   python (3.13.15 в образе против 3.13.13 в venv). Файлы офлайн-прогона с
   `--no-rerank` побайтово равны артефактам «до».
6. Дополнительно поднят API из того же образа: `/api/version` отвечает и печатает
   обе шкалы и оба порога (`work/container/api_version.json`).

## 6. Поведение порога на выданном тесте

| Порог | Отказов из 1110 | Доля |
|---|---:|---:|
| новый, переранжирование (0,4994) | **32** | 2,9 % |
| прежний калиброванный, косинус (0,5496) | 48 | 4,3 % |
| черновой argmax F1, косинус (0,3492) | 3 | 0,27 % |

Незакрытый вопрос прошлой волны («на тесте доля запросов без пары около 1 %, а
порог отказывает в 0,27 %») закрыт наполовину: число отказов теперь 2,9 %, то
есть того же порядка, что и оценка доли «чужих», — но причина расхождения
оказалась не в пороге, а в **протоколе**.

Измерено: в выданных CSV нет камер, поэтому пакетный прогон не применяет
камерный фильтр. На нашем сплите тот же порог без фильтра отказывает в 20,5 %
запросов при recall 0,986 (то есть теряет 1,4 % запросов с парой), а с
камерным фильтром — в 40,1 % при recall 0,725. Распределения сходятся: медиана
уверенности топ-1 на выданном тесте 0,975, на сплите без фильтра у запросов
**с парой** — 0,976 (у запросов без пары — 0,252). Простая арифметика при 1 %
«чужих» даёт ожидаемые 2,2 % отказов против наблюдаемых 2,9 % — порядок сходится.

**Это и есть главная находка, которую нельзя сглаживать.** Правило выбора,
применённое к тому же сплиту **без** камерного фильтра, выбрало бы порог 0,813
(F1 0,941, TNR 0,978 в этом протоколе); на выданном тесте он отказал бы в 121
запросе из 1110. Разница между 32 и 121 — это цена незнания того, как жюри
исключает камеры. Мы оставили порог, откалиброванный в камерном протоколе
(тот же, в котором калибровался прежний), чтобы сравнение «было/стало» осталось
честным, и назвали альтернативу числом.

## 7. Что осталось незакрытым

- **Протокол камер на закрытом тесте неизвестен.** Обе ветки посчитаны (§ 6):
  порог 0,4994 для камерного протокола, 0,813 — если фильтра нет. Ответ
  постановщика применяется заменой одного числа в `config.py`, новой работы не
  требуется.
- **Онлайновый путь остаётся на косинусе.** k-reciprocal определён на множестве
  «все запросы прогона + галерея»; для одиночного запроса API это была бы другая
  величина, а смешивать шкалы нельзя. Следствие: `/api/search` и пакетный прогон
  дают одинаковый порядок топ-1 не всегда (на выданном тесте топ-1 разошёлся бы у
  28 запросов из 1110). Согласование потребует либо батчевого метода API, либо
  отдельной калибровки онлайнового порога.
- **Устойчивость нового порога не проверялась бутстрэпом и кроссфитом** — в
  прошлой калибровке это делалось (`refusal/results/bootstrap*.csv`). Здесь
  посчитаны только точечные значения и три доли отказных; доверительных
  интервалов для разности 0,806 − 0,733 у нас нет.
- **Отрыв первого кандидата от второго** на новой шкале не пересчитывался: в
  прошлый раз он проиграл абсолютному значению, но на другой шкале вывод мог
  измениться.
- **Масштабирование.** Квадратичная память подтверждена замером (169 МиБ на 1860
  объектов); для тай-брейка на 10⁶ объектов нужен разреженный вариант — не делался.

## 8. Как это воспроизвести

Из каталога `04-solution/service/`, интерпретатор — `.venv/bin/python` проекта:

```bash
# сдаваемые файлы и векторы на проверочном сплите
python -m app.batch --images-dir ../../data/images \
    --query ../split/files/val_query.csv \
    --gallery ../split/files/val_gallery.csv --out-dir /tmp/val_run
python tools/eval_split.py /tmp/val_run/embeddings.npy          # § 3
python tools/calibrate_threshold.py /tmp/val_run/embeddings.npy /tmp/calib  # § 4
```

Обе команды прогонялись из репозитория и дали числа этого отчёта. Прогон на
выданном тесте и контейнерные проверки — команды в § 5 и в README сервиса.

Веса модели (`service/model/*.onnx`, 8,4 МБ) в git не хранятся; для прогонов они
положены в каталог сервиса, sha256 совпал с зашитым в `config.py` и Dockerfile.

Правки лежат в рабочем дереве **незакоммиченными**: во время работы в репозитории
появились чужие коммиты (`ddde286`, `564e8dd`), поэтому коммит оставлен
координатору. Изменённые файлы: `service/README.md`, `service/app/api/main.py`,
`service/app/batch.py`, `service/app/core/{config,ranking,submission}.py`;
новые: `service/app/core/rerank.py`, `service/tools/`.
