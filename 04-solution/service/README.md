# Сервис Vehicle ReID — инференс, хранилище, тонкий клиент

Сервис формирует цифровой признак транспортного средства (512-мерный вектор)
по кадру и bbox и ищет совпадения в галерее. OCR и ввод номера в вычислительный
путь не входят; область пластины остаётся частью изображения, проверена
ограниченной абляцией (см. SOLUTION.md §11). Архитектура микросервисная:

| Компонент | Технология | Роль |
|---|---|---|
| `api` | Python, FastAPI, onnxruntime (CPU) | инференс модели, HTTP-API (OpenAPI), тонкий клиент |
| `qdrant` | Qdrant (свободная векторная СУБД) | хранение векторов и метаданных галереи |
| `app.batch` | тот же образ, без API и СУБД | пакетный прогон тестового набора → сдаваемые файлы |

Порядок в пакетном `submission.csv` строится независимым top-50
k-reciprocal (см. ниже). `candidates.csv` и HTTP API используют cosine;
векторы модели от выбора ранжирования не меняются.

Модель (сдаваемая конфигурация **d1_j48**, с 20.09.2026): две ONNX-модели на одном
препроцессинге — **OSNet-AIN x1.0** (`vehicle-reid-0001`, Open Model Zoo 2022.1, лицензия
MIT, 8,4 МБ) и **combined_v1** — наш дообученный OSNet-AIN (LP-FT на RoundaboutHD MIT +
CARLA Apache-2.0 + train организатора; журнал — `../training/combined/`), 8,3 МБ.
Конвейер: L2-нормировка каждого вектора `512` → среднее → L2 среднего → whitening (матрица
`lw_ens_j48_rho0.5.npz`, ρ=0,5, train_fit) → L2. Все три файла весов лежат в `model/`,
попадают **внутрь образа при сборке** и проверяются по sha256 дважды — при сборке и при
старте процесса. На запуске интернет не нужен. Объяснимость (`/api/explain`)
осознанно остаётся на первой модели (OSNet) — см. `app/core/explain.py`.

## Запуск одной командой

Файл `docker-compose.yml` лежит **в этом каталоге** (`04-solution/service/`), в
корне репозитория его нет. Поэтому либо перейдите сюда:

```bash
cd 04-solution/service
docker compose up --build -d
```

либо укажите файл явно — тогда команда работает из любого каталога (пути внутри
файла считаются от него самого):

```bash
docker compose -f 04-solution/service/docker-compose.yml up --build -d
```

`up` поднимает хранилище, API **и загружает галерею**: сервис `loader` стартует
после healthcheck Qdrant, отрабатывает и выходит. Каталог данных задаётся
переменной `DATA_DIR` (по умолчанию `data/` в корне репозитория; должен
содержать `images/` и `test_gallery.csv`). Загрузка 750 объектов занимает около
минуты — до её конца поиск честно отвечает 409 «галерея не загружена».
Готовность видна по health:

```bash
curl --fail http://localhost:8000/api/health   # storage.gallery_points > 0
```

- тонкий клиент: <http://localhost:8000/> — см. раздел ниже;
- документация API (Swagger UI, работает офлайн): <http://localhost:8000/docs>;
- спецификация OpenAPI: <http://localhost:8000/openapi.json>.

## Тонкий клиент

Рабочее место оператора, обычная страница в браузере: `app/static/index.html`,
`app.css`, `app.js`. Без фреймворков и без обращения наружу — шрифты и другие ресурсы
локальные, значок страницы встроен в разметку, все запросы идут на пути того же
сервиса. Решение остаётся работоспособным в изолированной сети.

Что делает оператор:

1. **Задаёт запрос.** Можно взять разрешённый демонстрационный query-кадр
   из `GET /api/demo` либо выбрать свой файл/перетащить его. Демо скачивает
   оригинальные байты и bbox из CSV; результаты идут через обычный API.
   Кадр выбирается файлом или перетаскиванием, рамка ТС
   обводится мышью прямо по кадру (создание, перенос, восемь ручек растяжения);
   поля `x/y/w/h` синхронны с рамкой в обе стороны, если координаты известны
   точно. Кнопка «весь кадр» — для готовых кропов.
2. **Видит кандидатов картинками.** У каждого — оценка близости, запас до
   порога и полоса, на которой порог отмечен риской. Переключатель «кадр
   целиком» показывает объект в сцене камеры.
3. **Видит отказ как ответ, а не как пустоту.** Отдельная панель: шкала
   косинуса с отметками достигнутой близости и порога, чего именно не хватило,
   сколько объектов просмотрено. По явному действию можно посмотреть ближайших
   **ниже** порога — они помечены и совпадением не считаются.
4. **Забирает результат.** Выгрузка CSV и JSON собирается в браузере из
   того же ответа API: контекст запроса, порог, признак отказа, лучшая
   близость, кандидаты с рангами. Отказ тоже выгружается — строкой без
   кандидата, то есть «проверено, совпадения нет».
5. **Смотрит, на что смотрела модель.** Кнопка «разбор» у кандидата открывает
   карты вклада областей в оценку близости (см. следующий раздел).

Рабочее пространство группирует поиск, сравнение/разбор, метод и материалы.
`GET /api/materials` показывает только установленные публичные файлы: PDF
документации, технические слайды без контактов, manifest и артефакты прогона.
Полный PPTX/PDF с контактами через этот endpoint не отдаются.

Состояния сервиса показываются до того, как оператор упрётся в ошибку:
загрузка, хранилище недоступно, галерея не загружена (409), кадры не
смонтированы, неверный файл, отказ по порогу и успех. Старый поиск/экспорт
сбрасываются при смене кадра, bbox и новом запросе; ошибка разбора не уничтожает
уже полученную выдачу. После 409, 503 и сетевого сбоя клиент повторно проверяет
состояние API. Пока открыт результат, он проверяет модель и галерею каждые 12 с,
а перед выгрузкой делает ещё одну проверку: при изменении условий старый
результат нельзя скачать. В каждом состоянии показан доступный следующий шаг.

`/api/ui/state` сейчас передаёт число объектов галереи, но не её версию.
Замена галереи на другую с тем же числом объектов и прежней моделью внутри
открытой вкладки не распознаётся; после такой административной операции страницу
надо обновить. Для автоматического обнаружения нужен отдельный идентификатор
версии галереи в API.

Демо-проверка на изолированном стенде и скриншоты двух тем, 390/768/1440,
клавиатуры и 200% zoom — в `ui-checks/REPORT-20260925.md`. Публичный сервис
работает на `https://demo.lct.iamcp.ru/`; состав VPS, замеры и порядок отката —
в [инструкции развёртывания](deploy/README.md).

### Объяснимость в сервисе

`POST /api/explain` раскладывает **косинус первой модели OSNet-AIN (OMZ)**
по позициям её карты признаков. Поиск использует **d1_j48: OSNet-AIN +
combined_v1 + whitening**. Поэтому косинус объяснения не является численной
оценкой поиска; это показано рядом с картами в интерфейсе. На контрольной паре
аудита поиск дал 0,053297, объяснение OSNet — 0,131823
([аудит, D7](../audit/jury-path-2/REPORT.md)). Это не приближение: после глобального пулинга голова сети аффинна,
поэтому `cos = Σ вкладов + свободный член` — тождество, проверяемое на каждом
вызове (невязка возвращается в ответе и показывается оператору). Метод, его
проверки и иллюстрации — в `04-solution/explainability/`.

Расчёт в сервисе не тянет новых зависимостей: `app/core/explain.py` читает
нужные веса и собирает копию графа с дополнительным выходом минимальным
разбором protobuf, на стандартной библиотеке. Сессия создаётся лениво, при
первом разборе, — обычный поиск за необязательную возможность не платит.

Для показа кропов и карт каталог кадров монтируется в контейнер `api` на
чтение (`DATA_DIR`, внутри — `/data/images`). Без него поиск и API работают
как прежде, клиент показывает идентификаторы и оценки без картинок.

### Повторная загрузка галереи (другой каталог данных)

```bash
DATA_DIR=/абсолютный/путь/к/data docker compose run --rm loader
```

Шаг идемпотентен: коллекция пересоздаётся, повторный запуск даёт то же
состояние. Загрузчик сам ждёт готовности хранилища (`--wait`, по умолчанию
120 с), поэтому его можно запускать сразу после `up`.

> Podman вместо Docker: `podman-compose up -d` запускает тот же набор сервисов
> (профилей в файле больше нет); при SELinux (Fedora) каталогу данных нужна
> метка контейнера (`chcon -Rt container_file_t "$DATA_DIR"`) либо монтирование
> с `:z`. Ожидание `condition: service_healthy` podman-compose не выполняет —
> его закрывает собственное ожидание внутри загрузчика.

## Пакетный прогон (закрытый тест организатора)

Одна команда; все пути — аргументы, в коде ничего не зашито. Хранилище **не
требуется**, сеть **не требуется** (проверено с `--network none`):

```bash
docker build -t vehicle-reid-service .
docker run --rm --network none \
  -v /путь/к/тестовому/набору:/data:ro \
  -v /путь/к/выводу:/out \
  vehicle-reid-service \
  python -m app.batch --images-dir /data/images \
      --query /data/test_query.csv --gallery /data/test_gallery.csv \
      --out-dir /out
```

После успешного batch в `/out` находятся три сдаваемых файла. Полная схема
submission требует минимум десяти объектов галереи; для однозначного
сопоставления результатов нужны уникальные `image_id` отдельно в query и
gallery. Пустые CSV не поддержаны; остальные известные границы —
[SOLUTION.md §5](../../SOLUTION.md#known-behavior-limits).

- `submission.csv` — **без заголовка**, `query_id, gallery_id_1…gallery_id_10`
  по убыванию скора (по умолчанию — независимый top-50 KR, при
  `--no-rerank` — косинус); при gallery меньше десяти объектов строки
  короче одиннадцати полей;
- `embeddings.npy` — float32 `(N_query+N_gallery, 512)`: сначала все строки
  query-CSV по порядку файла, затем все строки gallery-CSV. **От режима
  переранжирования не зависит** — это сырые векторы модели;
- `candidates.csv` — **с заголовком** `query_id,gallery_id,confidence`: все
  кандидаты с косинусной оценкой ≥ порога, по убыванию, без лимита десятью; confidence
  округлён до шести знаков и может быть ниже полного порога. Запрос без строк
  означает отказ только при успешном batch и уникальном query ID;
- `run_info.json` — счётчики, версии, время, косинусная шкала отказа и параметры ранжирования
  (служебный, к сдаче не требуется).

При отсутствии входных CSV или хотя бы одного используемого изображения
`app.batch` и `app.load_gallery` завершаются с кодом **2** до ML-импортов,
инференса и подключения к Qdrant. Сообщение перечисляет входы и объясняет,
где взять набор; для Compose проверьте `DATA_DIR`. Допускаются `.jpg`, `.jpeg`,
`.png` и полное имя файла в `image_id`, как и при обычном чтении кадров.
**Имя с известным расширением изображения трактуется буквально:** `named.png`
(в любом регистре расширения) означает только `named.png`; ни наличие, ни
отсутствие этого файла не разрешает выбрать `named.png.jpg`. При отсутствии
точного файла — ранний код 2, при повреждении точного файла исправный сосед
также не используется. Точка в других позициях — часть ID: `frame.v1` или
`cam.2026.09.24` ищутся прежним детерминированным перебором `.jpg`, `.jpeg`,
`.png`, затем файл с точным именем; символические ссылки допустимы. Регистр
имени не меняется. Предварительная проверка и чтение кропа используют одно
правило.

Без Docker то же самое: `python -m app.batch ...` из каталога сервиса
(зависимости пакетного прогона — только `numpy`, `pillow`, `onnxruntime`;
ни FastAPI, ни Qdrant не импортируются — проверено по `sys.modules`).

Числовые параметры проверяются до чтения данных, создания моделей и подключения
к хранилищу: `--batch` — целое **> 0** (штатно 32), `--threads` — целое **≥ 0**
(0 сохраняет выбор ONNX Runtime), `app.load_gallery --wait` — конечное **≥ 0**
(0 — одна проверка готовности без ожидания). Ошибка параметра даёт код **2**
и не меняет прежние выходные файлы/коллекцию. Порог обязан быть конечным, в том
числе при чтении из env; конечные значения вне [0, 1] допустимы для явного
принятия/отклонения всех пар. В режиме KR до инференса проверяются
`REID_RERANK_K1/K2 ≥ 1`, конечная `REID_RERANK_LAMBDA ∈ [0, 1]`.

Перед публикацией проверяются число строк, размерность, конечность и L2-норма
векторов (допуск `1e-6`). Векторы не перенормируются. Пропущенный инференс
оставляет NaN-сентинел и завершается ошибкой; неполный или ненормированный
выход не сохраняется как успешный результат. Эта проверка не доказывает
происхождение произвольного уже нормированного вектора и не делает комплект
атомарным при последующей ошибке записи или ранжирования.

## Переранжирование `submission.csv`

Включено по умолчанию только для **ранжирования**: для каждого query выбирается
cosine top-50 из статичной gallery, затем k-reciprocal (k1=6, k2=3, λ=0.3)
обрабатывает группу «текущий query + эти 50 gallery». Остальные объекты стоят
после выбранных в косинусном порядке. Никакие другие test-query не участвуют
в ответе на текущий запрос. Реализация — `app/core/rerank.py`; при
`--no-rerank` `submission.csv` сортируется только по косинусу.

| Режим на validation 1110×750 | mAP@10 | Rank-1 | Rank-5 |
|---|---:|---:|---:|
| Независимый top-50 KR, сдаваемый | **0.7411030506** | **0.7079326923** | 0.8605769231 |
| Cosine (`--no-rerank`) | 0.7242262382 | 0.6850961538 | **0.8822115385** |

Числа получены официальным `evaluate.py` по `submission.csv` из исходных
validation-изображений. Из 1110 запросов в mAP входят 832 с допустимой
межкамерной парой; оставшиеся 278 проверяются через отказ. Валидатор усекал
каждый ответ до десяти позиций после удаления junk; AP делился на
`min(n_pos,10)`. Этот сплит уже использовался в разработке и не является
независимой оценкой скрытого test. Старое число mAP **0.7741** получено
исследовательским KR на объединении *всех* query и gallery; такой режим
нарушает опубликованное условие независимого query и в сдаче не используется.
[Хеши входов и точные результаты](../reproduce/evidence/official-validation-20260929.json)
сохранены вместе с протоколом.

`embeddings.npy` и `candidates.csv` не меняются от флага `--no-rerank`:
переранжирование действует после извлечения признаков, а отказ всегда
считается по косинусу. Память локальной матрицы KR ограничена 51 объектом,
но перед этим нужен косинусный поиск по всей gallery. HTTP API выполняет
точный cosine-поиск Qdrant; порядок его ответа может отличаться от batch
`submission.csv`, порог и шкала отказа совпадают с `candidates.csv`.

## Методы API

| Метод | Что делает |
|---|---|
| `GET /api/health` | состояние сервиса и хранилища |
| `GET /api/version` | модель, sha256 весов, размерности, косинусный порог отказа и параметры независимого top-50 ранжирования batch |
| `POST /api/embed` | кадр + bbox → вектор признака |
| `POST /api/search` | кадр + bbox → кандидаты с уверенностью либо отказ |
| `POST /api/search/vector` | то же по готовому вектору (например, из `/api/embed`) |

Методы тонкого клиента (существующие ответы выше ими не затрагиваются):

| Метод | Что делает |
|---|---|
| `GET /api/ui/state` | состояние для клиента одним запросом: хранилище, порог, доступность кадров и разбора |
| `GET /api/gallery/{id}/crop` | кроп объекта галереи (`view=crop`) или кадр целиком с рамкой (`view=frame`) |
| `POST /api/explain` | карты вклада областей в оценку близости пары «запрос — кандидат» |

Все методы описаны в OpenAPI (`/openapi.json`, интерактивно — `/docs`).

## Порог режима отказа

`candidates.csv` и HTTP API принимают оценки cosine ≥
**0.5141976914190476**. В `candidates.csv` попадают все прошедшие пары,
без лимита top-10; отсутствие строк запроса — отказ. Порог был выбран на
validation по правилу максимизации `min(TNR, F1_0.10, F1_0.25, F1_0.40)`
при камерной политике `market`: `F1_p = 2(1−p)r / ((1−p)(1+r)+pf)` для recall
`r`, доли ложных принятий `f` и предполагаемой доли open-set запросов `p`.
Выбранное число после публикации официального оценщика не подгонялось заново.

Официальный `evaluate.py` считает F1/TNR **по запросам**, проверяя истинность
верхнего принятого кандидата. На нашей многократно использованной валидации
получены TP/FP/FN/TN **803/84/20/203**, F1 **0.9391812865** и TNR
**0.7302158273**. При оценке исходным исследовательским `market + presence`
контуром тот же порог давал F1 0.7684996606 / TNR 0.7302158273: смысл
верного принятия у двух оценщиков различается. Прежний порог общего KR
0.5282812306342437 и F1 0.8090787717 / TNR 0.7841726619 —
**исторический эксперимент**, в сдаваемом `candidates.csv` они не применяются.
На другом наборе ни F1, ни TNR не гарантированы; у закрытого test нет
доступных меток для их оценки.

Порог переопределяется `--threshold` в batch, параметром `threshold` в API
или переменной `REID_THRESHOLD` процесса. Это меняет только решение об
отказе, а не порядок `submission.csv`. Confidence — мера близости, не
вероятность идентичности. Шесть знаков в CSV записываются **после** сравнения
с полным порогом.

## Воспроизводимость и численная эквивалентность

Конвейер сервиса численно повторяет измерительный контур: кроп по bbox → RGB →
resize 208×208 (PIL bilinear) → float32 0..255 → NCHW → **две ONNX-модели** (CPU) →
L2 каждого вектора → среднее → L2 среднего → whitening (float32) → L2-нормировка с накоплением в
float64; косинусы считаются в float64 по формуле измерительного контура.
Векторы d1_j48 воспроизводят исторические метрики `tools/eval_split.py`:
cosine full-ranking mAP 0.7316093422; исследовательский общий KR mAP
0.7740915539. **Сдаваемый порядок** проверен отдельно официальным
`evaluate.py`: top-50 KR mAP@10 0.7411030506. Соответствие трёх файлов
текущему запуску и SHA-256 фиксируется в [`artifacts-final/`](artifacts-final/).
Дельта метрик от float32-хранения матрицы
whitening против f64-оригинала — 0.0 во всех печатных цифрах (max |Δвектор| 1.43e-8).

Основные числа пересчитывает [контур воспроизведения](../reproduce/README.md),
который проверяет наличие и SHA-256 входов **до инференса**. Из корня репозитория,
в окружении с runtime-зависимостями (контейнерная команда — в SOLUTION.md §7):

```bash
python 04-solution/reproduce/run.py --mode val --data-dir "$DATA_DIR" --out-dir "$OUT_DIR"
python 04-solution/reproduce/run.py --mode test --data-dir "$DATA_DIR" --out-dir "$OUT_DIR"
```

Validation требует только 1860 кадров по `split/files/val_{query,gallery}.csv`;
test-CSV и test-изображения ему не нужны. Test отдельно создаёт сдаваемые файлы,
но не метрики качества: его идентичности не выданы. Данные организатора в Git
отсутствуют. Структура, получение участником/жюри и все индивидуальные отпечатки —
[reproduce/README.md](../reproduce/README.md).

Полная дополнительная калибровка: `python tools/calibrate_threshold.py
"$OUT_DIR/val/embeddings.npy" "$OUT_DIR/calibration"` из `service/`.
Она сверяет 187 выбранных точек с контуром; сохранённый прогон —
[calib-d1_j48/](calib-d1_j48/).

Версии зафиксированы в `requirements.txt` (семь прямых зависимостей) и
`requirements-lock.txt` (полный `pip freeze --all` проверенного образа — 31
пакет, подставляется в сборку как constraints); python 3.13
(`python:3.13-slim`).

## Релизная конфигурация d1_j48

Модель с 20.09.2026: OSNet-AIN OMZ + дообученная combined_v1 → L2 каждого
признака → среднее → L2 среднего → whitening → L2. С 29.09 пакетная сдача
использует независимый top-50 KR только для `submission.csv`, а отказ по
косинусу с порогом 0.5141976914190476. Кандидат собственного отдельного
ML-ядра после обучения не обошёл этот ансамбль по качеству; отрицательный
результат сохранён в [отчёте](../training/owncore-distill-20260926/REPORT.md).
Актуальные выходы тестового набора, manifest и SHA-256 — в
[`artifacts-final/`](artifacts-final/). Старый комплект от 21.09 применял общий
KR и не является текущей сдачей.

**Оба ONNX и матрица whitening входят в Git**: для `service/model/*.onnx`
есть явное исключение в `.gitignore`. Перед сборкой `model/fetch_model.sh`
проверяет SHA-256 всех трёх файлов; OSNet скачивается только при отсутствии
локального файла. В полном клоне скрипт проходит без сети. Для combined_v1
нет внешнего URL: отсутствующий файл восстанавливают из репозитория.

**Сборка и запуск — разные вещи, и требования к сети у них разные.**

- **Пакеты на сборке из сети не тянутся:** зависимости лежат колёсами в
  [`wheels/`](wheels/) (30 файлов, 57 МБ), `Dockerfile` по умолчанию собирается с
  `ARG PIP_SOURCE=offline` → `pip install --no-index --find-links=/wheels`. Запасной
  путь — `--build-arg PIP_SOURCE=network`. Как пересобрать каталог колёс — в
  [`wheels/README.md`](wheels/README.md).
- **Базовые образы нужно получить заранее:** `python:3.13-slim` для сборки и
  `qdrant/qdrant:v1.15.5` для хранилища. Из сети — через `docker pull`; офлайн — из
  [offline/](offline/README.md), где каждый образ лежит своим архивом
  (`python-3.13-slim.tar.gz`, `qdrant-v1.15.5.tar.gz`) с отпечатками в `SHA256SUMS`.
  После загрузки сверяют идентификаторы и размеры: `51cce855bb6e` / 130 МБ и
  `0ad2e23181e5` / 181 МБ.

Колёса в сдаваемый образ не попадают: зависимости ставятся в отдельной стадии сборки,
наружу уходит только каталог установленных пакетов. Для сдачи это означает: образ можно
собрать и на машине без выхода в интернет, если базовый образ уже есть локально.
