# Сервис Vehicle ReID — инференс, хранилище, тонкий клиент

Сервис формирует цифровой признак транспортного средства (512-мерный вектор)
по кадру и bbox и ищет совпадения в галерее — без использования
государственного номера. Архитектура микросервисная:

| Компонент | Технология | Роль |
|---|---|---|
| `api` | Python, FastAPI, onnxruntime (CPU) | инференс модели, HTTP-API (OpenAPI), тонкий клиент |
| `qdrant` | Qdrant (свободная векторная СУБД) | хранение векторов и метаданных галереи |
| `app.batch` | тот же образ, без API и СУБД | пакетный прогон тестового набора → сдаваемые файлы |

Порядок кандидатов в пакетном прогоне строится **переранжированием** (k-reciprocal,
см. ниже); векторы модели от этого не меняются.

Модель (сдаваемая конфигурация **d1_j48**, с 20.09.2026): две ONNX-модели на одном
препроцессинге — **OSNet-AIN x1.0** (`vehicle-reid-0001`, Open Model Zoo 2022.1, лицензия
MIT, 8,4 МБ) и **combined_v1** — наш дообученный OSNet-AIN (LP-FT на RoundaboutHD MIT +
CARLA Apache-2.0 + train организатора; журнал — `../training/combined/`), 8,3 МБ.
Конвейер: L2-нормировка каждого вектора `512` → среднее → L2 среднего → whitening (матрица
`lw_ens_j48_rho0.5.npz`, ρ=0,5, train_fit) → L2. Все три файла весов лежат в `model/`,
попадают **внутрь образа при сборке** и проверяются по sha256 дважды — при сборке и при
старте процесса. На запуске интернет не нужен. Объяснимость (`/api/explain`)
осознанно остаётся на первой модели (OSNet) — см. `app/core/explain.py`.

## Запуск одной командой

Файл `docker-compose.yml` лежит **в этом каталоге** (`04-solution/service/`), в
корне репозитория его нет. Поэтому либо перейдите сюда:

```bash
cd 04-solution/service
docker compose up --build -d
```

либо укажите файл явно — тогда команда работает из любого каталога (пути внутри
файла считаются от него самого):

```bash
docker compose -f 04-solution/service/docker-compose.yml up --build -d
```

`up` поднимает хранилище, API **и загружает галерею**: сервис `loader` стартует
после healthcheck Qdrant, отрабатывает и выходит. Каталог данных задаётся
переменной `DATA_DIR` (по умолчанию `data/` в корне репозитория; должен
содержать `images/` и `test_gallery.csv`). Загрузка 750 объектов занимает около
минуты — до её конца поиск честно отвечает 409 «галерея не загружена».
Готовность видна по health:

```bash
curl --fail http://localhost:8000/api/health   # storage.gallery_points > 0
```

- тонкий клиент: <http://localhost:8000/> — см. раздел ниже;
- документация API (Swagger UI, работает офлайн): <http://localhost:8000/docs>;
- спецификация OpenAPI: <http://localhost:8000/openapi.json>.

## Тонкий клиент

Рабочее место оператора, обычная страница в браузере: `app/static/index.html`,
`app.css`, `app.js`. Без фреймворков и без единого обращения наружу — шрифты
системные, значок страницы встроен в разметку, все запросы идут на пути того же
сервиса. Решение остаётся работоспособным в изолированной сети.

Что делает оператор:

1. **Задаёт запрос.** Кадр выбирается файлом или перетаскиванием, рамка ТС
   обводится мышью прямо по кадру (создание, перенос, восемь ручек растяжения);
   поля `x/y/w/h` синхронны с рамкой в обе стороны, если координаты известны
   точно. Кнопка «весь кадр» — для готовых кропов.
2. **Видит кандидатов картинками.** У каждого — оценка уверенности, запас до
   порога и полоса, на которой порог отмечен риской. Переключатель «кадр
   целиком» показывает объект в сцене камеры.
3. **Видит отказ как ответ, а не как пустоту.** Отдельная панель: шкала
   косинуса с отметками достигнутой близости и порога, чего именно не хватило,
   сколько объектов просмотрено. По явному действию можно посмотреть ближайших
   **ниже** порога — они помечены и совпадением не считаются.
4. **Забирает результат.** Выгрузка CSV и JSON собирается в браузере из
   того же ответа API: контекст запроса, порог, признак отказа, лучшая
   близость, кандидаты с рангами. Отказ тоже выгружается — строкой без
   кандидата, то есть «проверено, совпадения нет».
5. **Смотрит, на что смотрела модель.** Кнопка «разбор» у кандидата открывает
   карты вклада областей в оценку близости (см. следующий раздел).

Состояния сервиса показываются до того, как оператор упрётся в ошибку:
хранилище не поднято, галерея не загружена (тот самый 409), кадры не
смонтированы. В каждом случае — что именно сделать, командой.

### Объяснимость в сервисе

`POST /api/explain` раскладывает **косинус первой модели OSNet-AIN (OMZ)**
по позициям её карты признаков. Поиск использует **d1_j48: OSNet-AIN +
combined_v1 + whitening**. Поэтому косинус объяснения не является численной
оценкой поиска; это показано рядом с картами в интерфейсе. На контрольной паре
аудита поиск дал 0,053297, объяснение OSNet — 0,131823
([аудит, D7](../audit/jury-path-2/REPORT.md)). Это не приближение: после глобального пулинга голова сети аффинна,
поэтому `cos = Σ вкладов + свободный член` — тождество, проверяемое на каждом
вызове (невязка возвращается в ответе и показывается оператору). Метод, его
проверки и иллюстрации — в `04-solution/explainability/`.

Расчёт в сервисе не тянет новых зависимостей: `app/core/explain.py` читает
нужные веса и собирает копию графа с дополнительным выходом минимальным
разбором protobuf, на стандартной библиотеке. Сессия создаётся лениво, при
первом разборе, — обычный поиск за необязательную возможность не платит.

Для показа кропов и карт каталог кадров монтируется в контейнер `api` на
чтение (`DATA_DIR`, внутри — `/data/images`). Без него поиск и API работают
как прежде, клиент показывает идентификаторы и оценки без картинок.

### Повторная загрузка галереи (другой каталог данных)

```bash
DATA_DIR=/абсолютный/путь/к/data docker compose run --rm loader
```

Шаг идемпотентен: коллекция пересоздаётся, повторный запуск даёт то же
состояние. Загрузчик сам ждёт готовности хранилища (`--wait`, по умолчанию
120 с), поэтому его можно запускать сразу после `up`.

> Podman вместо Docker: `podman-compose up -d` запускает тот же набор сервисов
> (профилей в файле больше нет); при SELinux (Fedora) каталогу данных нужна
> метка контейнера (`chcon -Rt container_file_t "$DATA_DIR"`) либо монтирование
> с `:z`. Ожидание `condition: service_healthy` podman-compose не выполняет —
> его закрывает собственное ожидание внутри загрузчика.

## Пакетный прогон (закрытый тест организатора)

Одна команда; все пути — аргументы, в коде ничего не зашито. Хранилище **не
требуется**, сеть **не требуется** (проверено с `--network none`):

```bash
docker build -t vehicle-reid-service .
docker run --rm --network none \
  -v /путь/к/тестовому/набору:/data:ro \
  -v /путь/к/выводу:/out \
  vehicle-reid-service \
  python -m app.batch --images-dir /data/images \
      --query /data/test_query.csv --gallery /data/test_gallery.csv \
      --out-dir /out
```

Выход в `/out` — три сдаваемых файла точно по схемам README датасета:

- `submission.csv` — `query_id, gallery_id_1…gallery_id_10` по убыванию скора
  (по умолчанию — уверенности переранжирования, при `--no-rerank` — косинуса);
- `embeddings.npy` — float32 `(N_query+N_gallery, 512)`: сначала все строки
  query-CSV по порядку файла, затем все строки gallery-CSV. **От режима
  переранжирования не зависит** — это сырые векторы модели;
- `candidates.csv` — `query_id, gallery_id, confidence`: все кандидаты со
  скором ≥ порога, по убыванию; запрос без строк = отказ;
- `run_info.json` — счётчики, версии, время, шкала и параметры переранжирования
  (служебный, к сдаче не требуется).

Без Docker то же самое: `python -m app.batch ...` из каталога сервиса
(зависимости пакетного прогона — только `numpy`, `pillow`, `onnxruntime`;
ни FastAPI, ни Qdrant не импортируются — проверено по `sys.modules`).

## Переранжирование кандидатов

Включено по умолчанию. k-reciprocal re-ranking (Zhong et al., CVPR 2017),
параметры **k1 = 6, k2 = 3, λ = 0.3**, реализация — `app/core/rerank.py`
(numpy, без внешних зависимостей). Считается на объединении «все запросы
прогона + вся галерея», то есть ровно так, как формируется сдача одним прогоном.

| | mAP | Rank-1 | mAP@10 |
|---|---:|---:|---:|
| d1_j48, `--no-rerank` (косинус) | 0.7316 | 0.6851 | 0.7242 |
| d1_j48, по умолчанию (переранжирование) | **0.7741** | **0.7308** | **0.7685** |

Числа — на проверочном сплите (`../split/files/`, 1110 запросов / 750 галерея,
камерная политика market), получены измерительным контуром `../eval/` на
векторах пакетного прогона; источник — [s02_metrics.json](../training/combined/s02_metrics.json),
команда — в разделе «Воспроизводимость». Прежние 0,6566 / 0,6937 относятся к
одной OSNet до переключения 20.09, а не к текущей сборке.

Что важно знать про этот приём:

- **Время «изображение → вектор» не меняется**: переранжирование работает после
  извлечения векторов. В финальном выпуске 21.09 его цена — 2,785 с на весь
  прогон (1110 запросов × 750 объектов) против 765,252 с извлечения при 2 CPU /
  2 потоках ([run_info.json](artifacts-final/run_info.json)); в
  `run_info.json` это поле `rank_elapsed_s`.
- **`embeddings.npy` не затрагивается** — файл пишется до переранжирования.
  Проверено: прогоны с флагом и без дают бит-в-бит одинаковый `embeddings.npy`.
- **Память квадратична** по числу объектов: (Q+G)² float64 на матрицу, несколько
  матриц одновременно. Исторический замер одной OSNet на выданном тесте (1860 объектов): пик выделений
  169 МиБ, maxRSS процесса 219 МиБ. Отсюда потолок обычной реализации — порядка
  10⁴ объектов (≈5 ГБ); для масштаба 10⁶ нужен разреженный вариант.
- Параметры подбирались на отдельном протоколе из `train_fit` (другие
  идентичности) и лишь потом один раз проверялись на валидации. Параметры из
  статьи (20, 6, 0.3) в историческом подборе одной OSNet давали mAP 0.6666.
  Это не новый подбор d1_j48.

Как включить косинусный режим текущего d1_j48:

```bash
python -m app.batch ... --no-rerank        # флаг
REID_RERANK=0 python -m app.batch ...      # переменная окружения
```

Параметры переопределяются переменными `REID_RERANK_K1`, `REID_RERANK_K2`,
`REID_RERANK_LAMBDA`.

**API переранжирование не использует** — сознательно. k-reciprocal определено на
множестве «все запросы прогона + галерея», и для одиночного запроса это была бы
другая величина. Поэтому `/api/search` работает на шкале косинуса с косинусным
порогом; обе шкалы и оба порога печатает `GET /api/version`.

### Где применим порог переранжирования

`t_rr=0.5282812306342437` калиброван только на полном validation-сплите:
**1110 запросов × 750 объектов галереи**, 832 запроса с парой / 278 без,
d1_j48, KR(6,3,0,3), `market`, `presence`. Перенос на выданный test той же
размерности — рабочая настройка; его F1/TNR неизвестны. Даже одинаковый размер
другой галереи не подтверждает перенос порога: важен весь состав query/gallery.
Минимального «безопасного размера» не установлено.

На контроле **4 запроса × 10 объектов** batch с этим порогом принял два чужих
автомобиля (0,541908 / 0,768959) и серый кадр (0,801990); косинусный поиск их
отклонил. Источник: [jury-path-2/REPORT.md](../audit/jury-path-2/REPORT.md).
Для малой/произвольной галереи используйте HTTP API или `batch --no-rerank`
с косинусной шкалой и `t_cos=0.5141976914190476`. Этот fallback устраняет
зависимость оценки от соседних запросов, но не гарантирует опубликованные F1/TNR
на новом наборе. Для применения rerank к нему требуется отдельная калибровка на
представительных размеченных положительных и отрицательных запросах.
Автоматического переключения режима по размеру галереи в коде нет.

## Методы API

| Метод | Что делает |
|---|---|
| `GET /api/health` | состояние сервиса и хранилища |
| `GET /api/version` | модель, sha256 весов, размерности, обе шкалы и оба порога |
| `POST /api/embed` | кадр + bbox → вектор признака |
| `POST /api/search` | кадр + bbox → кандидаты с уверенностью либо отказ |
| `POST /api/search/vector` | то же по готовому вектору (например, из `/api/embed`) |

Методы тонкого клиента (существующие ответы выше ими не затрагиваются):

| Метод | Что делает |
|---|---|
| `GET /api/ui/state` | состояние для клиента одним запросом: хранилище, порог, доступность кадров и разбора |
| `GET /api/gallery/{id}/crop` | кроп объекта галереи (`view=crop`) или кадр целиком с рамкой (`view=frame`) |
| `POST /api/explain` | карты вклада областей в оценку близости пары «запрос — кандидат» |

Все методы описаны в OpenAPI (`/openapi.json`, интерактивно — `/docs`).

## Порог режима отказа

Шкалы две, поэтому и порогов два: перенос числа с одной шкалы на другую смысла
не имеет.

| Режим | Шкала уверенности | Порог по умолчанию | F1 | TNR |
|---|---|---:|---:|---:|
| по умолчанию (переранжирование) | 1 − переранжированная дистанция | **0.5282812306342437** | **0.809** | **0.784** |
| `--no-rerank` | косинус | 0.5141976914190476 | 0.768 | 0.730 |

Оба выбраны **одним правилом, зафиксированным до просмотра результатов**:
максимум от `min(TNR, F1 при долях отказных 0.10 / 0.25 / 0.40)` — равная защита
обоих показателей при неизвестном составе закрытого теста. ТЗ (разд. 9) вводит
TNR именно затем, чтобы решение не возвращало топ-1 всегда: максимум F1 на
косинусе давал бы F1 0.867 при TNR 0.302, то есть принимал 70 % запросов без пары.

Переранжирование улучшает не только ранжирование, но и **разделимость** «есть
пара / нет пары»: AUC-PR 0.918 против 0.909 на косинусе (на векторах d1_j48).
Пороги перекалиброваны 20.09.2026 на эмбеддингах новой конфигурации; прежние
значения (OSNet+KR: 0.49937235233589916 → F1 0.806 / TNR 0.777; 0.5495953464415451
→ F1 0.733 / TNR 0.698) — в истории `../refusal/` и в корневом SOLUTION.md.

Цена решения названа явно: при новом пороге на валидации принято 606 запросов с
парой из 832 (recall 0.728) и отклонено 218 из 278 без пары (TNR 0.784).

Порог переопределяется флагом `--threshold` (batch), параметром `threshold`
(API) или переменными `REID_THRESHOLD` / `REID_THRESHOLD_RERANK`.

### Поведение на выданном тесте

На выданном тесте (1110 запросов, 750 объектов галереи) прогон с порогом по
умолчанию отказывает в **34 запросах из 1110 (3,1 %)**; косинусная ветвь
(`--no-rerank`, порог `t_cos`) — в 48 (4,3 %), черновой argmax-F1 на косинусе
(0.36877167085460877, не рабочая точка) — в 14 (1,3 %). Числа пересчитаны
21.09.2026 на векторах d1_j48 из прогона команды R; до переключения на d1_j48
здесь стояли 32 / 48 / 3 — они относились к прежней модели OSNet.

Это не противоречие, а следствие двух вещей. Во-первых, в выданном тесте доля
запросов без пары, судя по распределению уверенности, около процента, а не 25 %,
как в нашем сплите. Во-вторых, в выданных CSV **нет камер**, поэтому пакетный
прогон не применяет камерный фильтр, и у запроса с парой почти всегда есть
близкий двойник с той же точки. Прямая проверка: на нашем сплите тот же порог
без камерного фильтра отказывает в 20,9 % запросов при recall 0.983, а с
камерным фильтром — в 40,0 % при recall 0.728; распределение уверенности топ-1
на выданном тесте (медиана 0.977) совпадает с распределением запросов **с
парой** на сплите без фильтра (медиана 0.977), а не без пары (медиана 0.249).

Отсюда прямое следствие, которое стоит знать заранее: если жюри считает TNR на
наборе, где камерный фильтр не применяется, наш порог окажется мягче
заявленного. Правило выбора, применённое к сплиту без камерного фильтра, дало бы
порог 0.8698135812778872 (F1 0.943, TNR 0.989 в том же протоколе); он отказал бы
на выданном тесте в 135 запросах из 1110. Мы оставляем порог, калиброванный в камерном
протоколе (он же использовался при прежней калибровке), потому что протокол
организатора неизвестен, а менять его вместе со шкалой — значит сравнивать
несравнимое.

## Воспроизводимость и численная эквивалентность

Конвейер сервиса численно повторяет измерительный контур: кроп по bbox → RGB →
resize 208×208 (PIL bilinear) → float32 0..255 → NCHW → **две ONNX-модели** (CPU) →
L2 каждого вектора → среднее → L2 среднего → whitening (float32) → L2-нормировка с накоплением в
float64; косинусы считаются в float64 по формуле измерительного контура. На
проверочном сплите метрики по векторам сервиса воспроизводят контур до всех 16 цифр
(`tools/eval_split.py`: KR mAP 0.7740915539438481 / R1 0.7307692307692307, косинус
0.7316093422310448), а выдаваемые файлы прогона по выданному тесту побайтово
воспроизводятся из отдельного чистого дерева (офлайн-сборка образа, та же команда —
см. корневой SOLUTION.md, раздел 8). Дельта метрик от float32-хранения матрицы
whitening против f64-оригинала — 0.0 во всех печатных цифрах (max |Δвектор| 1.43e-8).

Основные числа пересчитывает [контур воспроизведения](../reproduce/README.md),

в окружении с runtime-зависимостями (контейнерная команда — в SOLUTION.md §7):

```bash
python 04-solution/reproduce/run.py --mode val --data-dir "$DATA_DIR" --out-dir "$OUT_DIR"
python 04-solution/reproduce/run.py --mode test --data-dir "$DATA_DIR" --out-dir "$OUT_DIR"
```

Validation требует только 1860 кадров по `split/files/val_{query,gallery}.csv`;
test-CSV и test-изображения ему не нужны. Test отдельно создаёт сдаваемые файлы,
но не метрики качества: его идентичности не выданы. Данные организатора в Git
отсутствуют. Структура, получение участником/жюри и все индивидуальные отпечатки —
[reproduce/README.md](../reproduce/README.md).

Полная дополнительная калибровка: `python tools/calibrate_threshold.py

Она сверяет 187 выбранных точек с контуром; сохранённый прогон —
[calib-d1_j48/](calib-d1_j48/).

побайтово одинаковыми.

**Оба ONNX и матрица whitening входят в Git**: для `service/model/*.onnx`
есть явное исключение в `.gitignore`. Перед сборкой `model/fetch_model.sh`
проверяет SHA-256 всех трёх файлов; OSNet скачивается только при отсутствии
локального файла. В полном клоне скрипт проходит без сети. Для combined_v1
нет внешнего URL: отсутствующий файл восстанавливают из репозитория.

**Сборка и запуск — разные вещи, и требования к сети у них разные.**

- **Пакеты на сборке из сети не тянутся:** зависимости лежат колёсами в
  [`wheels/`](wheels/) (30 файлов, 57 МБ), `Dockerfile` по умолчанию собирается с
  `ARG PIP_SOURCE=offline` → `pip install --no-index --find-links=/wheels`. Запасной
  путь — `--build-arg PIP_SOURCE=network`. Как пересобрать каталог колёс — в
  [`wheels/README.md`](wheels/README.md).
- **Базовые образы нужно получить заранее:** `python:3.13-slim` для сборки и
  `qdrant/qdrant:v1.15.5` для хранилища. Из сети — через `docker pull`;
  офлайн — корректным архивом `docker save`. В текущем [offline/](offline/README.md)
  обнаружен один Python-образ с двумя тегами: настоящий Qdrant в архиве отсутствует.
  Такой архив пока нельзя использовать как полный комплект.
- **`--network none` изолированность не проверяет:** этот флаг отрезает сеть только у
  шагов `RUN`, а базовый образ процесс сборки тянет из реестра поверх сети хоста.
  Проверенный Podman-вариант: `podman build --no-cache --pull=never --network none .`
  с локальным Python base; в аудите внешний процесс сборки дополнительно
  изолирован через `unshare --net`. У Docker `--pull` — булев флаг, значения
  `never` у `docker build` нет. Для Docker нужны импортированный base и
  отключённый внешний доступ **у daemon/BuildKit**, затем
  `docker build --no-cache --pull=false --network none .`; этот вариант
  ещё требует приёмки именно на Docker. См. [SOLUTION.md §3](../../SOLUTION.md).
- **Запуск и инференс сети не требуют:** веса копируются внутрь образа на этапе сборки,
  и пакетный прогон проходит в контейнере с `--network none` — проверено, вместе с
  негативным контролем, что сеть действительно отрезана.

Колёса в сдаваемый образ не попадают: зависимости ставятся в отдельной стадии сборки,
наружу уходит только каталог установленных пакетов. Для сдачи это означает: образ можно
собрать и на машине без выхода в интернет, если базовый образ уже есть локально.
