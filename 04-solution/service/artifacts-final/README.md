# Сдаваемые артефакты — финальные

**Все три файла получены одним прогоном.** Это принципиально: организатор проверяет
`submission.csv` через `embeddings.npy` (разд. 8 ТЗ — порядок строк строго соответствует
выданному CSV), и так убеждается, что ранжирование получено настоящей моделью. Если
файлы окажутся из разных прогонов, сверка у жюри не сойдётся, и это прочтётся как
невоспроизводимость.

| Файл | Что это |
|---|---|
| `submission.csv` | по 10 кандидатов на каждый из 1110 запросов, по убыванию близости |
| `embeddings.npy` | 1860 × 512, сначала все запросы по порядку `test_query.csv`, затем вся галерея |
| `candidates.csv` | режим отказа: принятые кандидаты с оценкой уверенности; запрос без строк = отказ |
| `run_info.json` | параметры прогона, которым всё это получено |

## Параметры этого прогона

| | |
|---|---|
| Порог отказа | 0,49937235233589916 |
| Переранжирование | включено, k1=6, k2=3, λ=0,3 |
| Шкала оценок | уверенность как 1 − переранжированная дистанция |
| Отказов | 32 из 1110 (2,9 %) |
| Время извлечения векторов | 89,7 с |
| Время переранжирования | 1,06 с |

## Воспроизведение

```bash
cd 04-solution/service
python -m app.batch \
  --images-dir ../../data/images \
  --query ../../data/test_query.csv \
  --gallery ../../data/test_gallery.csv \
  --out-dir <каталог>
```

Одна команда создаёт все три файла разом — согласованность обеспечена тем, что они
пишутся из одного прогона, а не собираются из разных мест.

## Чем это отличается от `../../baseline/artifacts/`

Те файлы — **исторические**, от первого сквозного прогона: без переранжирования и со
старым черновым порогом 0,349. Они сохранены для сверки «было / стало» и **в сдачу не
идут**.

Показательно, что `embeddings.npy` в обоих комплектах **совпадает побайтово**:
переранжирование меняет только порядок кандидатов, а сырые векторы модели — нет. Именно
поэтому эмбеддинги можно было бы взять и оттуда, но полагаться на это не нужно —
правильный способ один: брать всё из финального прогона.
