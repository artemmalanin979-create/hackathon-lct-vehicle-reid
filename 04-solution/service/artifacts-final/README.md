# Сдаваемые артефакты — финальные

**Все четыре файла получены одним прогоном.** Это принципиально: организатор проверяет
`submission.csv` через `embeddings.npy` (разд. 8 ТЗ — порядок строк строго соответствует
выданному CSV), и так убеждается, что ранжирование получено настоящей моделью. Если
файлы окажутся из разных прогонов, сверка у жюри не сойдётся, и это прочтётся как
невоспроизводимость.

| Файл | Что это |
|---|---|
| `submission.csv` | по 10 кандидатов на каждый из 1110 запросов, по убыванию близости |
| `embeddings.npy` | 1860 × 512, сначала все запросы по порядку `test_query.csv`, затем вся галерея |
| `candidates.csv` | режим отказа: принятые кандидаты с оценкой уверенности; запрос без строк = отказ |
| `run_info.json` | параметры прогона, которым всё это получено |

## Параметры этого прогона

Прогон 21.09.2026, конфигурация **d1_j48** (сдаваемая с 20.09.2026).

| | |
|---|---|
| Модель | `d1_j48`: среднее L2-нормированных векторов OSNet-AIN (OMZ) и `combined_v1` → whitening ρ=0,5 → L2 |
| Порог отказа | 0,5282812306342437 (`DEFAULT_THRESHOLD_RERANK`) |
| Переранжирование | включено, k1=6, k2=3, λ=0,3 |
| Шкала оценок | уверенность как 1 − переранжированная дистанция |
| Отказов | 34 из 1110 (3,1 %) |
| Время извлечения векторов | 765,3 с |
| Время переранжирования | 2,79 с |

Время — при `--cpus 2` и `--threads 2` внутри чистого образа; это условия проверки
воспроизводимости, а не замер скорости. Прежний комплект (OSNet без дообучения,
16.09.2026) извлекал векторы за 89,7 с на хосте без ограничения CPU; числа несравнимы.

## Воспроизведение

Эти файлы — ровно выход test-ветви **команды R** (`SOLUTION.md`, разд. 7): пересчёт из
изображений в чистом образе, без кэшей. Их SHA-256 и размеры записаны в `metrics.json`
той же команды (`files.test/*`). Проверка выполнена: два независимых прогона R в чистом
образе на одной машине дали `submission.csv`, `embeddings.npy` и `candidates.csv`
**побайтово одинаковыми** (`run_info.json` отличается только полями времени).

Отдельно те же четыре файла даёт прямой вызов пакетного прогона:

```bash
cd 04-solution/service
python -m app.batch \
  --images-dir ../../data/images \
  --query ../../data/test_query.csv \
  --gallery ../../data/test_gallery.csv \
  --out-dir <каталог>
```

Одна команда создаёт все файлы разом — согласованность обеспечена тем, что они
пишутся из одного прогона, а не собираются из разных мест. Побайтовое совпадение с
этим комплектом гарантировано только при тех же ограничениях CPU и числе потоков:
последние биты float32-инференса зависят от разбиения работы (измеренное расхождение
векторов между прогонами на 2 и на 4 потоках — до 1,2e-07).

## Чем это отличается от `../../baseline/artifacts/`

Те файлы — **исторические**, от первого сквозного прогона: модель OSNet-AIN без
дообучения, без переранжирования и со старым черновым порогом 0,349. Они сохранены для
сверки «было / стало» и **в сдачу не идут**.

До 20.09.2026 здесь лежал промежуточный комплект той же модели OSNet (переранжирование
включено, порог 0,49937235233589916, 32 отказа) — у него `embeddings.npy` совпадал с
`baseline/artifacts/` побайтово, потому что переранжирование меняет только порядок
кандидатов, а сырые векторы — нет. После переключения на `d1_j48` это больше не так:
модель другая, и векторы отличаются во всех строках. Брать `embeddings.npy` откуда-либо,
кроме финального прогона, теперь нельзя.
