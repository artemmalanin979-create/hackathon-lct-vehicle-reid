## 1. Что ТЗ зафиксировало

### Постановка (разд. 3)

Поиск по изображению в открытом множестве. Дана галерея с известной идентичностью и
запрос. Нужно: извлечь эмбеддинг из кропа по выданному bbox → ранжировать галерею →
вернуть топ-N кандидатов **или пустой ответ**, если уверенного кандидата нет.

> **В задачу НЕ входит детекция ТС, распознавание номеров и трекинг.** BBox выдаются
> и на train, и на test.

### Данные (разд. 5)

| Что | Как в ТЗ |
|---|---|
| Изображения | Полные кадры JPEG/PNG в исходном разрешении камеры, плоский каталог `images/`, имена — случайные идентификаторы |
| Аннотации | `train.csv`, `test.csv`: `image_id`, bbox `(x, y, w, h)` в пикселях исходного кадра, `vehicle_id` — **только для train** |
| Несколько ТС в кадре | Один кадр может содержать несколько размеченных ТС |
| Камера, время, гео | **Не передаются участникам** — «чтобы задача решалась исключительно по визуальным признакам» |
| Анонимизация | ГРЗ и лица **уже размыты организаторами**. Использование остаточных признаков номерной пластины **строго запрещено** |
| Open-set | Множества `vehicle_id` train и test **гарантированно не пересекаются** |
| Покрытие | Разное время суток, погода, ракурсы (фронт/бок/зад), частичные перекрытия, низкое качество. **Каждое ТС в тесте снято минимум с двух точек наблюдения** |
| Описание формата | В `README.md` **внутри архива с данными** |

### Оценка (разд. 9)

**Совпадения в пределах одной камеры из расчёта исключаются** — засчитываются только
кросс-камерные. Основная метрика — **mAP**. Дополнительно (отдельными столбцами) —
Rank-1 и Rank-5.

Режим предложения кандидатов: **F1 при пороге, выбранном командой** (основная),
**TNR** — доля корректных отказов на запросах без совпадения в галерее, и
**mINP либо AUC по PR-кривой**.

Веса критериев:

| Критерий | Вес |
|---|---|
| Точность на **закрытом** тесте (mAP) | **45 %** |
| Производительность и применимость | 20 % |
| Инженерное качество | 15 % |
| Корректность режима отказа (F1, TNR) | 10 % |
| Защита решения на питче | 10 % |

**Дисквалификация:** решение не воспроизводится из кода **либо** использует признаки ГРЗ.

### Производительность (разд. 7)

- Тестируется на **едином оборудовании организаторов**; конфигурация «доводится до
  сведения участников перед началом хакатона».
- Меряют: **время на одно ТС при батче 1** и **пропускную способность (FPS)** при
  пакетной обработке без роста очереди и деградации памяти.
- **Суммарный размер весов ≤ 2 ГБ.** RAM — без OOM на тестовой выборке.
- Замеры делают **организаторы своим стандартизированным скриптом**; наши числа о
  скорости баллов не дают.
- Публичные предобученные веса и открытые датасеты **разрешены и приветствуются**,
  но обязаны быть перечислены в `Readme.md`. Закрытые/невоспроизводимые данные —
  к оценке не допускаются.

### Формат сдачи (разд. 8)

| Артефакт | Что внутри |
|---|---|
| `submission.csv` | Для каждого запроса — упорядоченные **первые 10 кандидатов** галереи по убыванию близости |
| `embeddings.npy` | Матрица векторов **для всех объектов тестовой выборки**, в порядке, **строго соответствующем выданному CSV** |
| `candidates.csv` | Результат режима отказа: принятые кандидаты с числовыми оценками уверенности **либо пустой ответ** |
| Код и окружение | Обучение + инференс, `Dockerfile`, `docker-compose.yml`, файл зависимостей. Запуск инференса — **одной командой**, **без доступа в интернет**, все веса внутри решения |

Проверка — вручную организаторами после хакатона, запуском наших решений на **закрытой**
части теста **эталонным скриптом расчёта метрики, который будет предоставлен участникам
заранее**.

### Архитектура (разд. 6), документация (разд. 12), сдача на платформе (разд. 13)

Обязательно: микросервисы (инференс / БД / клиент раздельно); backend на Python, C++ или
Rust; предпочтение свободному ПО и реестру отечественного ПО под Linux; векторная или
реляционная СУБД (названы pgvector, FAISS, Milvus); **OpenAPI (Swagger)** на все методы;
**доступ через браузер — тонкий клиент**; Docker + compose, запуск одной командой;
открытый неофусцированный код с комментариями.

Документация: `Readme.md` + при необходимости PDF. Обязаны быть описаны архитектура,
методы, пошаговая сборка, достигнутые метрики и **обоснование выбранного порога отказа**,
полный список библиотек и датасетов **с версиями**.

На платформу сдаются **четыре ссылки**: git-репозиторий, файл презентации,
**работающий прототип**, документация.

### Тай-брейк при равных метриках (разд. 10)

Баллов не добавляет, но решает при равенстве: демо-веб-интерфейс с экспортом
результатов; интерпретируемость (Grad-CAM / attention maps); ANN-поиск на галерее
порядка **10⁶**; глубокий разбор ошибок.

### Презентация (разд. 11)

PDF или PPTX. Обязательно: обоснование backbone и работы с ракурсом/освещением; схема
пользовательского пути; план масштабирования; **честный разбор ошибок с примерами из
тестовой выборки**.

| Было в наших документах | Стало по ТЗ |

| «Компактный слепок» = жёсткое ограничение размера | Ограничения на размерность вектора в ТЗ **нет**. Ограничен только **суммарный размер весов (2 ГБ)** |
| Веб-интерфейс — приятное дополнение | **Обязателен** (разд. 6: тонкий клиент через браузер; разд. 13: ссылка на работающий прототип) |
| Rust — если останется время | Остаётся необязательным: разрешён Python. В комиссии есть Rust-разработчик, но ТЗ выбор языка не навязывает |
| Метрику выбираем сами | Метрика **зафиксирована**: mAP основная, кросс-камерный протокол, плюс F1/TNR для отказа |

## 3. Главные риски, которые ТЗ создаёт

### 3.1. Мы не знаем, из чего считают наши 45 %

ТЗ требует и `embeddings.npy`, и `submission.csv`. Если mAP считается **эталонным
скриптом организаторов по нашим эмбеддингам**, то всё, что мы делаем поверх вектора
(переранжирование, фильтрация по атрибутам, сложные правила сравнения), **в основную
метрику не попадает** — считается только качество самого эмбеддинга при их мере близости.
Если же mAP считается по нашему `submission.csv`, то переранжирование даёт прямой
прирост. Это разные проекты. Вопрос №1 к постановщику.

### 3.2. Кросс-камерность мы не можем воспроизвести у себя напрямую

Организатор исключает совпадения внутри камеры — у него есть `camera_id`. У нас его нет
ни в train, ни в test. Значит наша собственная валидация по умолчанию **завышена**:
в галерею попадут снимки той же камеры (и даже того же кадра), которые организатор бы
выбросил.

Что у нас есть бесплатно: объекты из **одного `image_id` заведомо с одной камеры и из
одного момента**. Это нижняя граница суррогата камеры, но её мало: одна камера даёт много
разных кадров. Построение суррогата «точки наблюдения» на train — **отдельная задача,
и она должна быть решена до первого числа**, иначе все наши метрики будут врать в
приятную сторону.

### 3.3. Запрет на признаки ГРЗ под дисквалификацией

Пластины размыты, но **область размытия сама по себе — признак**: её положение, размер,
форма рамки, характер блюра. Плюс размытие могло применяться разными способами на разных
камерах. Проверка обязательна: абляция «область пластины дополнительно закрыта наглухо
vs как есть». Если метрика заметно падает — мы опираемся на пластину и рискуем
дисквалификацией. Это не перестраховка, а прямое требование разд. 5.3 и разд. 9.

### 3.4. Режим отказа нечем валидировать на выданном тесте

`vehicle_id` в test нет. Значит TNR/F1 на выданных данных мы посчитать не можем —
только на собственном сплите train. Порог, откалиброванный на train-сплите, переносится
на закрытый тест **вслепую**; при этом за режим отказа дают 10 %, и его защита —
обязательная часть питча.

## 4. Чего ТЗ не отвечает

Вынесено в [`../03-plan/questions.md`](../03-plan/questions.md) — на отправку экспертам.
Кратко: конфигурация железа организаторов (обещана «перед началом хакатона», не объявлена);
когда будет эталонный скрипт метрики; из какого артефакта считается mAP; как в тесте
разделены запрос и галерея; точные колонки `submission.csv` / `candidates.csv` и способ
записи отказа; как адресуется объект, когда в кадре несколько ТС; откуда берутся запросы
без совпадения для TNR.

Часть этих вопросов может быть закрыта в `README.md` внутри архива с данными — **сверить
по нему до отправки**.
